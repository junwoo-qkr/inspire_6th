## Part 1. 실행 과정과 변수의 값

소스 파일은 개발자가 작성하는 코드이고, 바이트코드는 JVM이 실행하는 컴파일 결과이다. 실행 중 변수에 저장되는 값까지 함께 관찰한다.

### 핵심 개념

| 개념 | 실습에서 확인할 것 |
| --- | --- |
| JDK / JVM | `javac`로 컴파일하고 `java`로 실행 |
| 인스턴스 필드 | 객체를 생성하면 기본값이 부여됨 |
| 지역 변수 | 읽기 전에 값을 대입 |
| 캐스팅 | 실수에서 정수로 변환하면 소수 부분 제거 |
| 박싱·언박싱 | 기본값과 래퍼 객체 사이의 변환 |

### Step 1-1. 변수 출력과 바이트코드 생성

`main`에서 객체를 생성한 뒤 필드의 초기값과 지역 변수의 값을 출력한다. 이 과정으로 클래스 정의와 실행 시작점을 연결한다.

**목표**: 필드 기본값, 지역 변수 초기화, 캐스팅과 박싱을 출력으로 비교한다.

**사용 파일**: 아래 코드를 새 파일로 저장한다.

스터디 실습 가이드/실습/0811/VariablePractice.java

```java
public class VariablePractice {
    private int count; // 인스턴스 필드: 기본값 0

    public static void main(String[] args) {
        VariablePractice sample = new VariablePractice();
        String title = "Java"; // 참조 타입 변수
        int local = 3; // 지역 변수는 사용 전에 초기화
        char letter = 'A';
        boolean ready = true;
        int truncated = (int) 3.8; // 명시적 캐스팅: 3
        Integer boxed = local; // int에서 Integer로 박싱
        int unboxed = boxed; // Integer에서 int로 언박싱
        System.out.println(sample.count); // 0
        System.out.println(title + ":" + local + ":" + ready); // Java:3:true
        System.out.println((int) letter); // 65
        System.out.println(truncated + ":" + unboxed); // 3:3
    }
}
```

**따라 해보기**

1. `VariablePractice.java`를 UTF-8로 저장한다.
2. 현재 실습 폴더에서 아래 명령으로 컴파일 후 실행한다.
3. 필드 `count`에 `= 5`를 추가해 첫 번째 출력이 바뀌는지 확인한다.
4. 지역 변수 `local`의 `= 3`만 제거하고 컴파일 오류를 확인한 다음 복구한다.

```powershell
# 실행 위치: 프로젝트의 '스터디 실습 가이드\실습\0811'
# 소스를 컴파일한 다음 생성된 클래스를 실행한다.
& "$jdk\javac.exe" -encoding UTF-8 VariablePractice.java
& "$jdk\java.exe" -cp . VariablePractice
```

**확인할 것**

- [ ] `VariablePractice.class`가 생성된다.
- [ ] 기본 코드의 출력이 `0`, `Java:3:true`, `65`, `3:3` 순서이다.
- [ ] 필드 초기값 변경과 지역 변수의 초기화 생략이 다른 결과를 만든다.

**발표 포인트**: 변수에 타입을 지정하는 이유와 `.java → .class → JVM 실행` 순서를 연결한다.

## Part 2. 생성자와 캡슐화

생성자는 객체의 초기 상태를 만들고, 캡슐화는 외부 코드가 상태를 다루는 경로를 정리한다. 객체를 가리키는 참조와 객체 자체도 구별한다.

### 핵심 개념

| 기능 | 역할 |
| --- | --- |
| 무인자 생성자 | 인자 없이 객체 생성 |
| 생성자 오버로딩 | 서로 다른 인자 조합 지원 |
| `this.brand` | 현재 객체의 필드 지정 |
| `private` | 외부 클래스의 직접 필드 접근 제한 |
| getter·setter | 필드 조회·수정 통로 제공 |

### Step 2-1. 세 가지 방법으로 Car 만들기

하나의 파일 안에 실행 클래스와 보조 클래스 `Car`를 둔다. 객체마다 상태가 독립적이며 참조값을 복사하면 같은 객체를 공유한다는 점을 확인한다.

**목표**: 무인자·1인자·2인자 생성자와 필드 접근을 비교한다.

**사용 파일**: 공개 클래스 이름과 파일 이름을 맞춰 저장한다.

스터디 실습 가이드/실습/0811/CarPractice.java

```java
class Car {
    private String brand;
    private String model;
    public Car() {} // 무인자로 생성: 필드들은 null
    public Car(String brand) { this.brand = brand; }
    public Car(String brand, String model) {
        this.brand = brand;
        this.model = model;
    }
    public String getBrand() { return brand; } // 브랜드 반환
    public void setBrand(String brand) { this.brand = brand; } // 브랜드 변경
    public String carInfo() { return brand + ":" + model; } // 두 필드 조합
}

public class CarPractice {
    public static void main(String[] args) {
        Car first = new Car();
        first.setBrand("Audi");
        Car second = new Car("BMW");
        Car third = new Car("Benz", "C200");
        System.out.println(first.carInfo());  // Audi:null
        System.out.println(second.carInfo()); // BMW:null
        System.out.println(third.carInfo());  // Benz:C200
        Car alias = third; // 같은 객체의 참조값 복사
        alias.setBrand("Changed");
        System.out.println(third.getBrand()); // Changed
        System.out.println(alias == third);   // true
        // System.out.println(third.brand); // 주석 해제 시 private 접근 오류
    }
}
```

**따라 해보기**

1. 같은 실습 폴더에서 다음 명령으로 실행한다.
2. `alias`를 통한 변경이 `third`에서도 보이는지 확인한다.
3. 마지막 주석을 해제해 직접 필드 접근 오류를 확인하고 다시 주석 처리한다.
4. `public Car() {}`를 지운 상태에서 `new Car()` 호출을 컴파일한 뒤 생성자를 복구한다.

```powershell
# 실행 위치: '스터디 실습 가이드\실습\0811'
& "$jdk\javac.exe" -encoding UTF-8 CarPractice.java
& "$jdk\java.exe" -cp . CarPractice
```

**확인할 것**

- [ ] 서로 다른 생성자에 따라 객체의 초기 상태가 달라진다.
- [ ] `alias`와 `third`는 동일한 객체의 변경을 함께 관찰한다.
- [ ] `private` 필드는 다른 클래스에서 직접 읽을 수 없다.
- [ ] 인자 있는 생성자가 남아 있으면 무인자 생성자는 자동 추가되지 않는다.

**발표 포인트**: setter는 값을 바꾸는 경로이며, 값 검증은 그 안에 작성하는 별도 로직이다.

## Part 3. Lombok과 DTO 생성

DTO는 함께 전달할 데이터를 하나로 묶는다. Lombok은 어노테이션에 맞는 생성자와 메서드를 만들어 반복 작성을 줄인다.

### 핵심 개념

| 어노테이션 | 역할 |
| --- | --- |
| `@Getter`, `@Setter` | 조회·변경 메서드 생성 |
| `@NoArgsConstructor` | 무인자 생성자 생성 |
| `@AllArgsConstructor` | 필드 순서에 맞는 전체 인자 생성자 생성 |
| `@Builder` | 필드 이름으로 값을 설정하는 빌더 생성 |

### Step 3-1. 생성자와 Builder를 비교하기

생성자는 필드의 순서에 맞춰 값을 전달하고, Builder는 메서드 이름으로 필드를 지정한다. 빌더에서 생략한 참조 필드와 생성 이후 setter 호출도 관찰한다.

**목표**: 기존 Lombok을 이용해 세 가지 생성 방법을 실행한다.

**사용 파일**: 기존 라이브러리를 사용하므로 새 의존성을 설치하지 않는다.

스터디 실습 가이드/실습/0811/DtoPractice.java

```java
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;

@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder
class BlogRequestDTO {
    private Integer id;
    private String title;
    private String content;
    private String email;
}

public class DtoPractice {
    public static void main(String[] args) {
        BlogRequestDTO empty = new BlogRequestDTO();
        // 전체 인자 생성자는 id, title, content, email 순서이다.
        BlogRequestDTO full = new BlogRequestDTO(1, "First", "Body", "mail");
        // build()가 DTO를 반환하며, 생략한 email은 null이다.
        BlogRequestDTO built = BlogRequestDTO.builder()
            .title("ABC").content("Hi").id(3).build();
        System.out.println(empty.getId());    // null
        System.out.println(full.getTitle());  // First
        System.out.println(built.getEmail()); // null
        built.setEmail("study@example.com"); // 생성한 뒤 필드 변경
        System.out.println(built.getContent()); // Hi
        System.out.println(built.getEmail()); // study@example.com
    }
}
```

**따라 해보기**

1. 준비 단계에서 지정한 `$lombok` 경로를 유지한 터미널에서 컴파일한다. `-cp`는 클래스 검색 경로, `-processorpath`는 어노테이션 처리기 검색 경로이다.
2. 결과를 확인한 뒤 빌더의 필드 지정 순서를 바꿔 같은 결과가 나오는지 비교한다.
3. `@Setter`를 지워 컴파일하고 `setEmail` 호출과의 관계를 확인한 뒤 복구한다.

```powershell
# 실행 위치: '스터디 실습 가이드\실습\0811'
& "$jdk\javac.exe" -encoding UTF-8 -cp "$lombok" -processorpath "$lombok" DtoPractice.java
& "$jdk\java.exe" -cp ".;$lombok" DtoPractice
```

**확인할 것**

- [ ] `null`, `First`, `null`, `Hi`, `study@example.com`이 순서대로 출력된다.
- [ ] 빌더의 호출 순서를 바꿔도 지정한 필드에 같은 값이 들어간다.
- [ ] getter·setter와 Builder가 서로 다른 어노테이션의 역할임을 설명할 수 있다.

**발표 포인트**: 빌더 사용과 객체 불변성은 구별한다. 이 예제는 setter를 통해 수정 가능한 DTO이다.

## 트러블슈팅 케이스

### 무인자 생성자 호출과 선언의 불일치

**증상**: 블로그의 설명용 `Car` 코드에는 2인자 생성자만 있는데 `new Car()` 호출이 함께 있다.

**원인**: 직접 생성자를 선언한 클래스에는 기본 생성자가 자동으로 추가되지 않는다.

**해결**: 무인자로 만들려면 `public Car() {}`를 선언한다. 무인자 생성이 필요 없다면 선언된 생성자에 맞는 인자를 전달한다. Step 2-1에서 두 경우를 비교한다.

### 수업 JDK와 기존 설치 버전의 차이

**증상**: 블로그에 기존 JDK 26을 수업용 JDK 17로 맞춘 경험이 기록되어 있다.

**원인**: 수업과 기존 환경의 버전이 달랐다. 구체적인 충돌 오류 메시지는 자료에 없다.

**해결**: 준비 단계처럼 JDK 17의 `java`와 `javac`를 명시적으로 실행해 버전을 일치시킨다.
