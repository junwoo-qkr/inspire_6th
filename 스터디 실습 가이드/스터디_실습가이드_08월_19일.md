## Part 1. try-catch-finally로 예외 처리하기

예외 처리는 실행 중 예상하지 못한 상황이 발생했을 때 프로그램의 흐름을 제어하는 방법이다. 먼저 `try-catch-finally`로 현재 위치에서 예외를 처리하고, 이후 `throw`와 `throws`를 이용해 예외를 직접 발생시키거나 호출자에게 전달하는 흐름을 확인한다.

### 핵심 개념

| 구문 | 역할 | 실행 시점 |
|---|---|---|
| `try` | 예외가 발생할 수 있는 코드 작성 | 먼저 실행 |
| `catch` | 지정한 예외가 발생했을 때 처리 | try에서 해당 예외가 발생했을 때 실행 |
| `finally` | 처리 후 필요한 마무리 작업 | 예외 발생 여부와 관계없이 실행 |

`catch`는 처리할 예외 종류에 따라 여러 개 작성할 수 있다. 여러 예외가 상속 관계라면 더 구체적인 하위 예외를 먼저 작성한다. `finally`는 정상 실행과 예외 처리 뒤에 모두 실행되지만, `System.exit`로 JVM이 종료되는 경우에는 실행이 보장되지 않는다.

`try-catch-finally`의 실행 흐름을 확인한 다음에는 예외를 현재 메서드에서 잡지 않고 호출자에게 전달하는 방법을 다룬다.

| 구분 | throw | throws |
|---|---|---|
| 위치 | 메서드 본문 | 메서드 선언부 |
| 뒤에 오는 대상 | 예외 객체 | 전달할 수 있는 예외 클래스 |
| 역할 | 실행 흐름에서 실제로 예외를 던짐 | 호출자가 처리하거나 다시 전달해야 할 가능성을 선언 |
| 실습 코드 | `throw new CustomException("양의 정수를 입력하세요.");` | `sample(int x) throws CustomException` |

**throws만 쓴다고 예외가 발생하거나 처리되지는 않는다.** 이번 코드에서는 음수일 때 throw 문이 실행되어 예외가 발생하고, 메서드 안에서 잡지 않은 예외가 호출자에게 전달된다.

### Step 1-1. 배열 범위 예외를 재현하고 반복 조건 수정하기

배열 인덱스는 0부터 길이보다 1 작은 값까지다. 마지막 반복 조건을 잘못 쓰면 존재하지 않는 요소에 접근한다.

**목표**: 예외를 잡은 뒤 finally와 다음 코드가 실행되는지 확인한다.

**사용 파일**: `ExceptionApp.main`의 첫 번째 실습 구간.

.study/08-19/be/javaPractice/src/ExceptionApp.java

```java
String[] strArr = {"Oasis", "Maroon 5", "YOASOBI"};
try {
    for (int i = 0; i <= strArr.length; i++) { // Before: 인덱스 3까지 접근
        System.out.println(strArr[i]); // 이름 세 개 출력 후 예외 발생
    }
} catch (ArrayIndexOutOfBoundsException e) {
    e.printStackTrace(); // 예외 타입과 발생 위치를 표준 오류에 출력
} finally {
    System.out.println("예외 발생 여부와 상관없이 실행");
}
```

**따라 해보기**

1. `& "$jdkBin\java.exe" -Dfile.encoding=UTF-8 -cp study-bin ExceptionApp`을 실행한다.
2. 이름 세 개, 배열 예외, finally 문구를 확인한다. 메시지 입력을 기다리면 `hello`를 입력하고 Enter를 누른다.
3. 아래 After처럼 조건의 `<=`만 `<`로 바꾸고 다시 컴파일·실행한다.

.study/08-19/be/javaPractice/src/ExceptionApp.java

```java

for (int i = 0; i < strArr.length; i++) {
    System.out.println(strArr[i]); // 세 이름만 출력하고 배열 예외 없이 종료
}
```

**확인할 것**

- [ ] 수정 전에는 인덱스 3 접근에서 배열 예외가 발생한다.
- [ ] 수정 후에는 배열 예외가 사라지고 finally는 계속 실행된다.
- [ ] 뒤쪽 사용자 정의 예외 실습은 여전히 별도로 실행된다.

**발표 포인트**: `printStackTrace`의 표준 오류와 `println`의 표준 출력은 화면에서 섞일 수 있다. 화면에 보이는 두 출력의 배치만으로 실행 순서를 판단하지 않는다.

### Step 1-2. IOException의 처리 의무 확인하기

입력 읽기 메서드는 읽기 실패 가능성을 checked exception으로 선언한다. 호출자는 실패에 대비한 처리나 전달 선언을 작성해야 한다.

예외 분류는 이 단계에서 처리 의무를 이해하기 위한 보조 개념으로 사용한다.

| 구분 | 컴파일러의 검사 | 이 실습의 예 |
|---|---|---|
| Checked exception | `catch`로 처리하거나 `throws`로 전달해야 함 | `IOException`, `CustomException` |
| Unchecked exception | 처리 선언을 강제하지 않음 | `ArrayIndexOutOfBoundsException`, `NumberFormatException` |

두 종류 모두 실행 중 발생한다. 차이는 예외가 발생하는 시점이 아니라 컴파일러가 처리 또는 전달 선언을 요구하는지에 있다.

**목표**: 컴파일러가 검사하는 것은 예외 발생 시점이 아니라 처리 여부임을 설명한다.

**사용 파일**: `ExceptionApp.java`. `BufferedReader`, `InputStreamReader`, `IOException`의 import는 원본에 있다.

.study/08-19/be/javaPractice/src/ExceptionApp.java

```java
BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
String line = null;
try {
    System.out.print("메시지를 입력하세요: ");
    line = br.readLine(); // 한 줄 읽기; IOException 처리 필요
} catch (IOException e) {
    e.printStackTrace(); // 읽기 실패 정보를 출력
}
System.out.println(line); // hello를 입력하면 hello 출력
```

**따라 해보기**

1. ExceptionApp을 실행하고 메시지 입력에 `hello`를 넣는다.
2. 위 코드의 `try-catch` 부분만 임시로 `line = br.readLine();` 한 줄로 바꿔 컴파일한다. `main`에는 throws를 추가하지 않는다.
3. IOException을 처리하지 않았다는 컴파일 오류를 확인하고 원래 try-catch를 복원한다.

**확인할 것**

- [ ] 정상 입력은 hello로 출력된다.
- [ ] 처리를 없애면 실행 전에 컴파일이 실패한다.
- [ ] 정상 입력에서 IOException이 발생했다고 해석하지 않는다.

### Step 1-3. 사용자 정의 예외와 finally 실행 확인하기

직접 정의한 예외를 사용하면 업무상 거부해야 하는 입력을 호출자에게 알릴 수 있다. 이번 조건은 음수만 거부하므로 0은 통과한다.

**목표**: throw가 실행되는 위치, throws가 선언된 위치, 호출자의 catch를 연결한다.

**사용 파일**: 다음 두 파일은 전체 코드다. 호출 코드는 기존 `ExceptionApp.main`의 마지막에 있다.

.study/08-19/be/javaPractice/src/features/exception/util/CustomException.java

```java
package features.exception.util;

public class CustomException extends Exception {
    public CustomException() {
    }
    public CustomException(String msg) {
        super(msg); // 받은 메시지를 부모 Exception에 전달
    }
}
```

.study/08-19/be/javaPractice/src/features/exception/ExceptionDemo.java

```java
package features.exception;

import features.exception.util.CustomException;

public class ExceptionDemo {
    public void sample(int x) throws CustomException {
        System.out.println("sample 시작");
        try {
            if (x < 0) {
                throw new CustomException("양의 정수를 입력하세요.");
            }
        } finally {
            System.out.println("sample 끝"); // 예외 전달 전에 실행
        }
    } // -1: 시작·끝 출력 후 예외 전달, 0과 1: 시작·끝 출력 후 정상 반환
}
```

.study/08-19/be/javaPractice/src/ExceptionApp.java

```java
ExceptionDemo demo = new ExceptionDemo();
try {
    demo.sample(-1); // 호출한 메서드에서 예외가 넘어온다.
} catch (CustomException e) {
    e.printStackTrace(); // CustomException과 저장된 메시지 출력
}
```

| 호출 | sample 내부 | 호출한 ExceptionApp |
|---|---|---|
| `sample(-1)` | throw 실행 → finally의 끝 문구 출력 → 예외 전달 | catch 실행 |
| `sample(0)` | throw 실행 안 함 → finally 출력 → 정상 반환 | catch 실행 안 함 |
| `sample(1)` | throw 실행 안 함 → finally 출력 → 정상 반환 | catch 실행 안 함 |

`throws CustomException` 선언은 세 경우에 모두 그대로다. 실행 결과를 가르는 것은 `x < 0` 조건과 그 안의 throw 문이다. 예외 메시지는 `CustomException`의 생성자 → `super(msg)`를 거쳐 저장되며, 호출자는 `e.getMessage()`로 메시지만 읽거나 `e.printStackTrace()`로 발생 위치까지 확인할 수 있다.

**따라 해보기**

1. `sample(-1)` 상태에서 컴파일·실행하고 메시지 입력을 마친다.
2. sample의 시작·끝 출력과 호출자의 CustomException 출력을 확인한다.
3. 인자를 0, 1로 각각 바꿔 컴파일·실행한다. 두 경우 모두 CustomException 없이 반환된다.
4. `throws CustomException`은 바꾸지 않았는데 예외 발생 여부가 달라지는 이유를 위 표로 설명한다.
5. 음수만 거부할 목적이라면 메시지를 `0 이상을 입력하세요.`로 바꿔 실제 조건과 맞춘다.

**확인할 것**

- [ ] `throws` 자체가 예외를 처리하는 것은 아니다.
- [ ] 음수에서는 finally 실행 후 호출자의 catch로 이동한다.
- [ ] 0과 1에서는 finally 실행 후 정상적으로 반환한다.

## Part 2. 콘솔 MVC의 요청·응답 연결하기

MVC는 화면·입력과 데이터·처리의 책임을 나누는 관점이다. 이번 코드는 콘솔 View에서 시작해 Controller·Service·DAO로 요청을 전달하고 DTO 목록을 다시 출력한다. 먼저 객체들을 연결하는 준비 과정을 보고, 그다음 이미 연결된 객체들 사이에서 메서드가 호출되는 과정을 따라간다.

### 핵심 개념

| 구성 요소 | 역할 | 실제 연결 |
|---|---|---|
| 실행 진입점 | View 생성 후 메뉴 시작 | `BlogReactApp.main()` → `landingPage()` |
| View | 메뉴 입력과 출력 | `BlogReactView.list()` |
| FrontController | 공통 요청 진입점 | `front.list("list.posts")` |
| Factory | 객체 생성·연결·조회 | `getBean("list.posts")` |
| Controller | 서비스 호출 | `ListController.list()` |
| Service 인터페이스 | 게시글 관련 기능의 계약 | `BlogReactService` |
| Service 구현체 | 선언한 기능의 실제 처리 | `BlogReactSerciveImpl.list()` |
| DAO | 데이터 접근 | `BlogReactDao.printAll()` |
| DTO | 조회 결과를 계층 사이에 전달 | `List<BlogResponseDTO>` |

생성자 주입은 사용할 객체를 밖에서 전달받는 방식이다. DTO는 계층 사이에 전달할 데이터를 담는다. 이 실습의 DAO는 DB 대신 메모리의 게시글 네 건을 보관하며 `List.of(...)`를 수정 가능한 `ArrayList`로 감싼다. Entity나 ORM 연동은 구현하지 않았다.

| 시점 | 일어나는 일 | 남는 결과 |
|---|---|---|
| 프로그램 시작과 팩토리 최초 생성 | DAO 생성 → Service에 DAO 전달 → Controller에 Service 전달 | 서로 연결된 객체와 `list.posts` 매핑 |
| 메뉴 1을 선택할 때마다 | View에서 조회 요청 → 팩토리로 Controller 조회 → Service·DAO 호출 | DTO 목록이 호출 경로를 거슬러 View로 반환 |

생성자에 Service나 DAO를 전달하는 일은 객체를 조립할 때 한다. 매번 `list()`를 호출할 때 객체들을 인자로 다시 전달하는 구조가 아니다.

### Step 2-1. 팩토리에서 객체를 만들고 연결하기

객체를 사용하는 쪽과 객체들을 조립하는 쪽을 나누면 연결 관계를 한곳에서 확인할 수 있다. 팩토리는 DAO부터 만들고 서비스와 컨트롤러의 생성자로 차례로 전달한다.

**목표**: 생성자 주입 순서와 `list.posts`에 등록된 객체의 관계를 설명한다.

**사용 파일**: `BlogBeanFactory.java`의 필드·생성자·두 메서드다. 전체 클래스의 package와 import는 복사한 원본을 유지한다.

```java
private static BlogBeanFactory instance;
private Map<String, Object> map;
private BlogReactService service;
private BlogReactDao dao;

private BlogBeanFactory() {
    map = new HashMap<>();
    dao = new BlogReactDao(); // 1. 게시글 목록을 가진 DAO 생성
    service = new BlogReactSerciveImpl(dao); // 2. 서비스에 DAO 전달
    map.put("list.posts", new ListController(service)); // 3. 컨트롤러에 서비스 전달
}

public static BlogBeanFactory getInstance() {
    if (instance == null) {
        instance = new BlogBeanFactory(); // 최초 호출에서 팩토리 생성
    }
    return instance; // 이후에는 같은 팩토리 반환
}

public Object getBean(String endPoint) {
    return map.get(endPoint); // list.posts이면 저장된 ListController
}
```

**따라 해보기**

1. DAO → Service → Controller 생성 순서를 따라 읽는다.
2. `ListController(BlogReactService service)`와 `BlogReactSerciveImpl(BlogReactDao dao)`에서 필드에 인자를 저장하는 부분을 찾는다.
3. 두 클래스의 인자 없는 생성자는 해당 필드를 초기화하지 않음을 비교한다.
4. `getInstance()`가 처음과 이후 호출에서 어느 분기를 지나는지 설명한다.

**확인할 것**

- [ ] Controller는 인터페이스 `BlogReactService` 타입으로 서비스를 받는다.
- [ ] 팩토리가 DAO와 서비스를 만들어 공유한다.
- [ ] 싱글톤 생성 방식이 직접 구현된 클래스는 BlogBeanFactory다.

**발표 포인트**: 이 팩토리에는 동시 초기화를 막는 처리가 없다. 단일 스레드 콘솔에서 관찰한 재사용을 멀티스레드 보장으로 확대하지 않는다.

### Step 2-2. 서비스 인터페이스와 구현체 연결하기

인터페이스는 호출 가능한 기능과 입출력 타입을 정한다. 구현체는 그 기능이 실제로 무엇을 할지 작성하며, Controller는 인터페이스 타입으로 전달받은 구현체를 사용한다.

**목표**: `BlogReactService`의 선언, `BlogReactSerciveImpl`의 구현, `ListController`의 호출을 연결한다.

**사용 파일**: 아래 인터페이스는 전체 코드이며 필요한 두 DTO도 사전 준비에서 확보했다. 구현체와 Controller는 학습에 필요한 필드·생성자·메서드 발췌이므로 기존 package, import 및 나머지 코드는 유지한다.

### Step 2-3. 요청의 호출·반환을 추적하고 게시글 조회하기

View는 입력을 정수로 변환하고, 전체 조회를 선택하면 요청 키를 전달한다. 조회 결과는 DTO 목록으로 돌아오며 스트림의 forEach로 출력한다.

**목표**: 입력 복구와 `View → FrontController → Controller → Service → DAO → 결과 반환` 흐름을 확인한다.

**사용 파일**: `BlogReactApp.java`의 전체 코드와 FrontController·View의 관련 메서드다. Controller와 Service는 바로 앞 단계에서 읽은 메서드로 연결된다.

|---|---|---|
| 1. 요청 시작 | View의 `front.list("list.posts")` | FrontController로 이동 |
| 2. 담당 객체 조회 | `factory.getBean(endPoint)` | Map에서 ListController를 찾아 FrontController에 반환 |
| 3. 컨트롤러 실행 | `((ListController) controller).list()` | Controller의 메서드 실행 |
| 4. 서비스 실행 | Controller의 `service.list()` | 구현체의 메서드 실행 |
| 5. 데이터 조회 | Service의 `dao.printAll()` | DAO가 보관한 DTO 목록 반환 |
| 6. 결과 전달 | DAO → Service → Controller → FrontController → View | 각 메서드의 return을 따라 같은 목록 전달 |
| 7. 화면 출력 | View의 `response.stream().forEach(...)` | 게시글 네 줄 출력 |

## 트러블슈팅 케이스

### throws와 예외 발생 동작의 혼동

**증상**: throws가 어떻게 예외를 발생시키는지 이해하기 어렵다. 블로그에서 기록한 혼동을 이 실습의 확인 대상으로 삼는다.

**원인**: 메서드 선언부의 전달 가능성 표시와 본문에서 실제로 예외를 던지는 동작을 구분해야 한다.

**해결**: throws 선언은 유지하고 `sample(-1)`과 `sample(0)`을 비교한다. 전자는 throw가 실행되어 호출자의 catch로 이동하고, 후자는 throw를 지나지 않아 정상 반환한다.

### MVC에서 여러 객체를 거치는 흐름의 혼동

**증상**: 조회 한 번에 여러 객체가 등장하여 누가 객체를 만들고 누가 메서드를 실행하는지 헷갈린다.

**원인**: 시작할 때의 객체 조립과 요청할 때의 메서드 호출·결과 반환을 한 과정으로 읽으면 역할이 섞인다.

**해결**: 먼저 Factory의 생성자에서 DAO·Service·Controller 연결을 확인하고, 별도로 Step 2-3의 표를 따라 요청과 반환을 추적한다. Controller 조회는 Factory, 게시글 데이터 조회는 DAO, 출력은 View의 역할이다.

### 배열의 마지막 인덱스 초과

**증상**: 이름 세 개 출력 후 `ArrayIndexOutOfBoundsException`이 발생한다.

**원인**: `i <= strArr.length`가 길이와 같은 인덱스까지 허용한다.

**해결**: 조건을 `i < strArr.length`로 바꾼다.

### 숫자가 아닌 메뉴 입력

**증상**: `abc`를 입력하면 올바른 숫자를 입력하라는 안내가 나온다.

**원인**: `Integer.parseInt`가 숫자로 변환하지 못해 `NumberFormatException`을 던진다.

**해결**: 원본 View의 catch가 안내하고 반복 메뉴로 복귀하므로 `1` 또는 `99`를 다시 입력한다.
