## Part 2. 메모리와 클래스·객체의 상태

인스턴스 필드는 객체별 상태이고 static 멤버는 클래스에 속한다. 이를 이해하려면 객체, 메서드 호출, 클래스 정보와 문자열 리터럴이 JVM에서 어떤 역할의 메모리와 연결되는지 구분해야 한다. 아래 구분은 학습을 위한 논리적 역할이며 실제 메모리 배치와 GC 방식은 JVM 구현과 설정에 따라 달라질 수 있다.

### 핵심 개념

| 영역 | 생성·공유 단위 | 저장하거나 관리하는 내용 | 이 실습과의 연결 |
| --- | --- | --- | --- |
| Heap | 생성된 인스턴스가 저장되며 참조가 끊긴 인스턴스는 Garbage Collector의 정리 대상이 됨 | `new`로 만든 인스턴스와 배열 | `new StaticDemo()`로 생성한 객체와 객체별 `message` 상태 |
| Execution Stack(JVM Stack) | 스레드마다 별도로 생성 | 실행 중인 메서드 정보가 LIFO 방식으로 쌓임 | `main`, `nonStaticMethod`, `statMethod`를 호출하고 반환하는 순서 |
| Method Area | JVM 안에서 여러 스레드가 공유 | 클래스 정보와 static 멤버가 저장됨 | `StaticDemo`의 클래스 정보와 static 멤버를 사용하는 기반 |
| Literal Pool | 같은 리터럴을 재사용하기 위한 관리 구조 | 소스에 직접 적은 문자열 등의 상수 표현 | `"그냥 변수"`, `"static 변수"`, `"메시지 변경"` 같은 문자열 리터럴 |

#### Heap

Heap은 객체와 배열이 생성되는 영역이다. `StaticDemo demo = new StaticDemo()`에서 참조 변수 `demo`는 생성된 객체를 가리키고, 객체에는 인스턴스 필드 `message`가 포함된다. `demo.message`를 `"메시지 변경"`으로 바꾸어도 이후 `new StaticDemo().message`는 새 객체의 초기값인 `"그냥 변수"`를 가진다. 서로 다른 객체의 인스턴스 상태가 분리되기 때문이다.

객체를 가리키는 경로가 없어지면 GC의 회수 대상이 될 수 있지만, 대상이 된 즉시 회수된다는 뜻은 아니다. GC 실행 시점과 회수 방식은 JVM이 결정한다.

#### Execution Stack

Execution Stack은 현재 실행 중인 메서드의 호출 상태를 스레드별로 관리한다. 메서드가 호출될 때 프레임이 쌓이고, 메서드가 끝나면 가장 최근 프레임부터 제거되는 LIFO 구조이다. `StaticApp.main()`이 `demo.nonStaticMethod()`를 호출하면 `main` 프레임 위에 `nonStaticMethod` 프레임이 생기고, 실행이 끝나면 다시 `main`으로 돌아온다.

지역 변수와 매개변수는 해당 호출 프레임의 실행 문맥에 속한다. 참조 타입 지역 변수는 객체 자체가 아니라 Heap의 객체를 가리키는 참조값을 다룬다.

#### Method Area

Method Area는 JVM이 로드한 클래스의 구조, 메서드 코드와 필드 정보 등 클래스 단위 정보를 관리하는 논리적 영역이다. `StaticDemo.staticMessage`와 `StaticDemo.PI`처럼 클래스 이름으로 접근하는 static 멤버는 특정 객체 하나가 아니라 클래스에 속한다. 인스턴스를 여러 개 만들어도 클래스 멤버를 사용하는 기준은 같다.

`final`은 메모리 영역의 이름이 아니라 변수에 한 번 값을 대입한 뒤 재대입하지 못하게 하는 언어 규칙이다. `static final double PI = 3.14`는 클래스에 속하며 다시 대입할 수 없는 변수를 선언한다.

#### Literal Pool

Literal Pool은 소스에 직접 작성한 리터럴을 관리하고 재사용하는 구조이다. 문자열 리터럴 `"AAA"`를 여러 번 사용하면 같은 문자열 객체를 공유할 수 있어 Part 4의 `str01 == str02`가 `true`가 된다. 반면 `new String("AAA")`는 리터럴의 내용을 이용해 새 String 객체를 명시적으로 만들기 때문에 두 새 객체의 참조는 서로 다르다.

리터럴 풀은 개념적으로 Method Area와 함께 설명되는 경우가 많지만, JVM 버전과 구현에 따른 실제 저장 위치를 하나의 고정된 주소처럼 외우기보다 **리터럴 재사용**, **객체 생성**, **참조 비교**의 차이를 이해하는 것이 핵심이다.

```java
// 가이드 설명: nonStaticMethod는 현재 객체의 값, static 값, PI를 출력한다. statMethod는 새 객체를 만들어 그냥 변수를 출력한 뒤 static 변수와 3.14를 출력한다.
package features.stat;

public class StaticDemo {
    public String message = "그냥 변수";
    public static String staticMessage = "static 변수";
    public static final double PI = 3.14;

    public StaticDemo() {}

    public void nonStaticMethod() {
        System.out.println(message);
        System.out.println(staticMessage);
        System.out.println(PI);
    }

    public static void statMethod() {
        // System.out.println(message);
        System.out.println(new StaticDemo().message);
        System.out.println(staticMessage);
        System.out.println(PI);
    }
}
```

## Part 3. 연산자와 실행 흐름 제어

조건문은 실행 경로를 선택하고 반복문은 계산과 출력을 되풀이한다. 당일 코드는 합계와 구구단, 문자열 역순 순회로 이를 실습한다.

### 핵심 개념

#### switch-case 문법

switch는 하나의 값을 여러 case와 비교해 실행할 경로를 선택한다. 모든 case에 해당하지 않을 때의 처리는 `default`에 작성한다. 이 커밋에는 콜론 방식의 switch문, 화살표 규칙을 사용한 switch문, 값을 직접 반환하는 switch 표현식이 모두 있다.

| 문법 | 결과 사용 방식 | 다음 case로 이어질 가능성 | 커밋의 메서드 |
| --- | --- | --- | --- |
| `case 값:` | case 안에서 대입·출력·반환 수행 | `break`나 `return`이 없으면 이어질 수 있음 | `WoodMan` |
| `case 값 -> 문장` | 화살표 오른쪽 문장 실행 | 이어지지 않음 | `WoodMan2` |
| `return switch (...)` | 선택된 case의 값을 switch 결과로 반환 | 이어지지 않음 | `WoodMan3` |

#### 반복문

반복문은 같은 처리를 조건에 따라 여러 번 실행한다. 반복 횟수가 분명하면 for가 읽기 쉽고, 조건을 중심으로 반복하면 while이 알맞다. do-while은 본문을 먼저 실행하므로 조건이 처음부터 거짓이어도 최소 한 번 실행한다.

| 반복문 | 조건 검사 시점 | 구성 | 커밋의 사용 예 |
| --- | --- | --- | --- |
| `for` | 본문 실행 전 | 초기화 → 조건 검사 → 본문 → 증감 | `sumRandom`, 구구단, `popStr` |
| `while` | 본문 실행 전 | 초기화는 밖에 두고 본문에서 상태 변경 | `sumRandom2` |
| `do-while` | 본문 실행 후 | 본문을 먼저 실행한 뒤 계속할지 검사 | `sumRandom3` |

| 제어문 | 역할 | 커밋의 사용 예 |
| --- | --- | --- |
| `break` | 가장 가까운 반복문이나 switch를 종료 | `printGuGuDan3`에서 지정한 단까지 출력 후 바깥 for 종료 |
| `continue` | 현재 회차의 나머지를 건너뛰고 다음 회차 진행 | 이 날짜의 커밋에는 실제 사용 없음 |
| 레이블 | 중첩 반복문에서 제어 대상을 이름으로 지정 | `outer:`, `inner:`가 선언됐지만 원본 `break`는 레이블을 지정하지 않음 |

`sumRandom`, `sumRandom2`, `sumRandom3`은 각각 별도의 난수를 생성하므로 세 결과가 서로 같을 필요는 없다. 세 메서드 모두 1부터 생성한 난수까지 더하고, 반복이 끝나도록 증감 위치를 유지한다. while이나 do-while에서 `i++`를 빠뜨리면 조건이 계속 참인 무한 반복이 될 수 있다.

### Step 3-1. 합계와 반복 메서드 따라가기

조건문은 실행 경로를 선택하고 반복문은 계산과 출력을 되풀이한다. 당일 코드는 합계와 구구단, 문자열 역순 순회로 이를 실습한다.

**목표**: 실제 호출과 반복 종료 위치를 설명한다.

#### switch의 콜론 규칙과 화살표 규칙

커밋의 `WoodMan2`와 `WoodMan3`에서 사용하는 `case 값 ->`는 람다식이 아니라 **switch의 화살표 규칙**이다. 화살표 오른쪽의 식이나 문장만 실행한 뒤 해당 switch 규칙이 끝나며, 다음 case로 이어지는 fall-through가 발생하지 않는다. 따라서 각 case 뒤에 `break`를 작성하지 않는다.

| case 문법 | 일치한 case 실행 후 동작 | `break` 필요 여부 | 커밋 코드 |
| --- | --- | --- | --- |
| `case 값:` | `break`, `return` 등을 만나지 않으면 다음 case로 이어질 수 있음 | 다음 case 실행을 막으려면 필요 | `WoodMan` |
| `case 값 ->` | 화살표 오른쪽만 실행하고 다음 case로 이어지지 않음 | 필요 없음 | `WoodMan2`, `WoodMan3` |

`WoodMan2`는 화살표 규칙으로 `result`에 값을 대입한 뒤 switch 밖에서 반환한다. `WoodMan3`는 switch 자체가 선택한 문자열을 만들어 곧바로 반환하는 **switch 표현식**이다. 두 메서드 모두 화살표 규칙이므로 case마다 `break`가 필요 없다.

반면 `WoodMan`은 콜론 규칙을 사용하지만 각 case에서 즉시 `return`한다. `return`이 메서드 실행 자체를 끝내므로 이 코드에도 별도의 `break`가 필요 없다. 콜론 규칙에서 대입이나 출력만 하고 다음 case로 넘어가면 안 되는 경우에는 `break`를 작성해야 한다.

`->` 기호는 람다식에서도 사용되지만, 문법은 사용 위치로 구분한다. `case 1 ->`처럼 switch의 case 뒤에 있으면 화살표 case 규칙이고, `(value) -> value * 2`처럼 함수형 인터페이스의 구현을 표현하면 람다식이다.

```java
        switch (number) {
            case 1:
                return "거짓말 ㄴㄴ";

            case 2:
                return "또 거짓말 ㄴㄴ";

            case 3:
                return "착하네";

            default:
                return null;
        }
    }

    public String WoodMan2(int number) {
        String result = null;
        switch (number) {
            case 1 -> result = "거짓말 ㄴㄴ";
            case 2 -> result = "또 거짓말 ㄴㄴ";
            case 3 -> result = "착하네";
            default -> result = null;
        }
        return result;
    }

    // 람다식 사용 2
    public String WoodMan3(int number) {
        return switch (number) {
            case 1 -> "거짓말 ㄴㄴ";
            case 2 -> "또 거짓말 ㄴㄴ";
            case 3 -> "착하네";
            default -> null;
        }
    }

    public int sumNumber(int start, int end) {
        int result = 0;
        int temp = 0;
        if (start > end) {
            temp = start;
            start = end;
            end = temp;
        }

        for (int i = start; i <= end; i++) {
            result += i;
        }

        return result;
    }

    // for 문
    public static int sumRandom() {
        int nan = (int)(Math.random() * 100) + 1;
        int result = 0;

        for (int i = 1; i <= nan; i++) {
            result += i;
        }

        return result;
    }

    // while 문
    public static int sumRandom2() {
        int nan = (int)(Math.random() * 100) + 1;
        int result = 0;
        int i = 1;

        while (i <= nan) {
            result += i;
            i++;
        }

        return result;
    }

    // do ~ while 문
    public static int sumRandom3() {
        int nan = (int)(Math.random() * 100) + 1;
        int result = 0;
        int i = 1;

        do {
            result += i;
            i++;
        } while (i <= nan);

        return result;
```

## Part 4. 문자열 비교

String은 문자들의 순서를 표현하는 참조 타입이며, 한 번 만들어진 String 객체의 내용은 바뀌지 않는 불변 객체이다. 문자열을 수정하는 것처럼 보이는 연산도 기존 객체를 변경하는 대신 새로운 문자열을 만든다. 이 파트에서는 문자열을 만드는 두 방식과 `==`, `equals()`의 비교 기준을 구분한다.

### 핵심 개념

#### 문자열 리터럴과 new String

`String str01 = "AAA"`처럼 문자열 리터럴을 사용하면 JVM은 리터럴 풀에서 같은 내용을 재사용할 수 있다. 따라서 같은 리터럴을 대입한 `str01`과 `str02`는 같은 객체를 가리키며 이 커밋에서는 `str01 == str02`가 `true`이다.

`new String("AAA")`는 내용이 같은 문자열이 리터럴 풀에 있어도 새 String 객체를 명시적으로 생성한다. `str03`과 `str04`는 각각 다른 객체를 가리키므로 `str03 == str04`는 `false`이다. 두 객체의 문자 내용은 모두 `AAA`이므로 `str03.equals(str04)`는 `true`이다.

| 비교 방식 | 확인하는 것 | 이 커밋의 결과 |
| --- | --- | --- |
| `str01 == str02` | 두 변수가 같은 객체를 가리키는지 | 같은 리터럴을 공유하므로 `true` |
| `str03 == str04` | `new`로 생성한 두 객체의 참조가 같은지 | 서로 다른 객체이므로 `false` |
| `str03.equals(str04)` | 두 String의 문자 내용이 같은지 | 내용이 모두 `AAA`이므로 `true` |

문자열의 내용이 같은지 판단하는 프로그램 로직에는 `equals()`를 사용한다. `==`의 결과를 문자열 내용 비교에 사용하면 문자열이 만들어진 방식에 따라 결과가 달라질 수 있다. 비교 대상이 `null`일 수 있다면 `"AAA".equals(value)`처럼 확실히 null이 아닌 문자열에서 호출하면 `NullPointerException`을 피할 수 있다.

#### String의 불변성

String 메서드와 연결 연산은 원래 객체의 내용을 수정하지 않는다. 예를 들어 `text.concat("B")`의 반환값을 저장하지 않으면 `text`는 이전 값 그대로이다. 불변 문자열은 한 객체의 내용을 다른 코드가 예상하지 못하게 바꾸는 일을 막고, 같은 리터럴을 안전하게 공유할 수 있게 한다.

이 날짜의 커밋에는 StringBuffer나 StringBuilder를 사용하는 코드가 없다. 따라서 이 파트에서는 당일 코드에서 확인되는 리터럴 풀, `new String`, 참조 비교와 내용 비교에 집중한다.

### Step 4-1. StringApp 실행

같은 `AAA`를 리터럴과 생성자로 각각 만들고 세 번 비교한다. 주석의 예상 결과를 따라가며 객체의 동일성과 문자열 내용의 같음을 구별한다.

**목표**: 객체의 동일성과 내용의 같음을 구별한다.

```java
// 가이드 설명: main의 세 if문은 차례로 OK, FAIL, OK를 출력한다.
public class StringApp {
    public static void main(String[] args) {
        // 같은 문자열 리터럴은 리터럴 풀의 동일한 String 객체를 공유할 수 있다.
        String str01 = "AAA";
        String str02 = "AAA";

        // ==는 문자열 내용이 아니라 두 참조가 같은 객체를 가리키는지 비교한다.
        if (str01 == str02) {
            System.out.println("OK");   // 실행됨: str01과 str02가 같은 리터럴 객체 참조
        } else {
            System.out.println("FAIL");
        }

        // new를 두 번 호출해 내용은 같지만 서로 다른 String 객체를 생성한다.
        String str03 = new String("AAA");
        String str04 = new String("AAA");

        // 두 객체의 참조가 다르므로 == 비교 결과는 false이다.
        if (str03 == str04) {
            System.out.println("OK");
        } else {
            System.out.println("FAIL"); // 실행됨: 서로 다른 객체 참조
        }

        // equals()는 String 객체에 저장된 문자 내용을 비교한다.
        if (str03.equals(str04)) {
            System.out.println("OK");   // 실행됨: 두 객체의 내용은 모두 AAA
        } else {
            System.out.println("FAIL");
        }
    }
}
```

## Part 5. 세 반복문으로 숫자 맞추기

GuessGameCore는 입력을 정답과 비교해 힌트를 출력하고 성공 여부를 반환한다. 세 게임 메서드는 이 함수를 최대 열 번 호출한다.

### 핵심 개념

| 구성 | 동작 |
| --- | --- |
| Math.random 식 | 1~100 정답을 게임마다 새로 생성 |
| Scanner.nextInt | 정수 토큰 입력 |
| GuessGameCore | 작으면 UP, 크면 DOWN, 같으면 true |
| gameFor / gameWhile / gameDoWhile | 세 반복 방식으로 최대 10회 시도 |

원본은 정수 여부·입력 종료·범위를 검증하지 않는다. 실습에는 1~100의 정수를 입력한다.

### Step 5-1. GuessGameApp의 세 게임 실행

GuessGameCore는 입력을 정답과 비교해 힌트를 출력하고 성공 여부를 반환한다. 세 게임 메서드는 이 함수를 최대 열 번 호출한다.

**목표**: 정답 반환과 반복 횟수 제한을 비교한다.

**사용 파일**: 아래 경로의 커밋 코드를 확인한다.

be/javaPractice/src/features/game/GuessGame.java

```java
// 가이드 설명: GuessGameCore는 정답일 때 true를 반환한다. 각 게임은 성공 시 You got it in 횟수 tries.와 The answer was 정답을 반환하고, 10회 실패하면 You lost. The answer was 정답을 반환한다. tries++는 이 위치에서 tries=tries+1이다.
package features.game;
import java.lang.Math;
import java.util.Scanner;

public class GuessGame {
    Scanner scanner = new Scanner(System.in);

    public GuessGame() {}


    public boolean GuessGameCore(int answer) {
        System.out.print("Enter number: ");
        int guess = scanner.nextInt();

        if (answer > guess) {
            System.out.println("UP");
        } else if (answer < guess) {
            System.out.println("DOWN");
        } else {
            return true;
        }
        return false;
    }


    public String gameFor() {
        int answer = (int)(Math.random() * 100) + 1;

        for (int tries = 1; tries <= 10; tries++) {
            boolean isClear = GuessGameCore(answer);
            if (isClear) {
                return "You got it in " + tries + " tries.\nThe answer was " + answer;
            }
        }
        return "You lost. The answer was " + answer;
    }


    public String gameWhile() {
        int answer = (int)(Math.random() * 100) + 1;
        int tries = 1;

        while (tries <= 10) {
            boolean isClear = GuessGameCore(answer);
            if (isClear) {
                return "You got it in " + tries + " tries.\nThe answer was " + answer;
            }
            tries++;
        }

        return "You lost. The answer was " + answer;
    }


    public String gameDoWhile() {
        int answer = (int)(Math.random() * 100) + 1;
        int tries = 1;

        do {
            boolean isClear = GuessGameCore(answer);
            if (isClear) {
                return "You got it in " + tries + " tries.\nThe answer was " + answer;
            }
            tries++;
        } while (tries <= 10);

        return "You lost. The answer was " + answer;
    }
}
```

```java
// 가이드 설명: main은 for, while, do-while 게임을 순서대로 실행한다. 한 게임의 성공·실패 후 다음 게임이 새 정답으로 시작된다.
import features.game.GuessGame;

public class GuessGameApp {
    public static void main(String[] args) {
        GuessGame game = new GuessGame();

        String result1 = game.gameFor();
        System.out.println(result1);

    }
}
```

## 트러블슈팅 케이스

### switch 표현식의 세미콜론 누락

**증상**: 원본 전체를 컴파일하면 OperatorDemo.java의 WoodMan3에서 `';' expected` 오류가 발생한다.

**원인**: `return switch (...) { ... }` 뒤에 return 문을 끝내는 세미콜론이 없다.

**해결**: 사전 준비의 수정 예시처럼 switch를 닫는 `}`를 `};`로 바꾸고 다시 컴파일한다. 커밋 원문과 실행용 수정 사항을 구분한다.

### 문자열 내용과 참조 비교의 차이

**증상**: register에 new String("title1")을 전달하면 내용이 같아도 400/FAIL을 반환한다. register2에 new String("")을 전달하면 빈 내용이어도 201/OK를 반환한다.

**원인**: 원본은 ==와 !=로 참조를 비교한다.

**해결**: 내용 기준으로 동작을 수정하는 경우 register의 조건은 `"title1".equals(title)`, register2의 조건은 `!"".equals(request.getTitle())`로 바꾼다. 위 코드 블록은 당시 커밋을 보존했다.

### 게임에 정수가 아닌 입력 제공

**증상**: abc를 입력하면 InputMismatchException으로 종료된다.

**원인**: 원본은 nextInt 전에 정수 여부를 검사하지 않는다. 입력이 끝나면 NoSuchElementException도 발생할 수 있다.

**해결**: 원본 실습에서는 정수를 입력한다. 입력 처리를 개선할 때에는 hasNextInt 등의 검사와 잘못된 토큰 소비를 추가한다. 원본에는 1~100 범위 검사도 없다.
