# 제목: Spring Boot·MyBatis 회원 인증 API 구현과 React 연동

## 오늘의 한 줄 요약

- `@RequiredArgsConstructor`와 `final` 필드를 이용해 Controller → Service → Mapper 의존성을 생성자로 주입했다.
- MyBatis Mapper 인터페이스와 XML을 연결해 회원가입과 로그인 SQL을 실행하는 구조를 만들었다.
- JSON 요청 본문은 `@RequestBody`, GET 요청의 쿼리스트링은 `@RequestParam`으로 받는 차이를 확인했다.
- Swagger 어노테이션으로 사용자 API와 요청·응답 명세를 문서화했다.
- 로그인 성공 결과와 Access Token·Refresh Token을 응답 본문 및 HTTP 헤더에 나누어 담았다.
- React와 Spring Boot의 포트가 달라 발생하는 CORS 문제를 설정으로 해결하고, Axios 요청 경로를 백엔드 API와 일치시켰다.

## 키워드 정리

| 키워드 | 설명 또는 예시 |
| --- | --- |
| 의존성 주입(DI) | 객체가 필요한 의존 객체를 직접 생성하지 않고 외부에서 전달받는 방식 |
| `@RequiredArgsConstructor` | 초기화되지 않은 `final` 필드를 인자로 받는 생성자를 Lombok이 생성한다. |
| `@Mapper` | MyBatis가 Mapper 인터페이스의 프록시 구현체를 만들고 Spring에서 주입할 수 있게 한다. |
| Mapper XML | Mapper 인터페이스와 SQL을 `namespace`와 구문 `id`로 연결한다. |
| `@RequestBody` | JSON 요청 본문을 DTO로 변환해 받는다. 예: `signUp(@RequestBody UserRequestDTO request)` |
| `@RequestParam` | URL의 쿼리스트링 값을 받는다. 예: `signIn(@RequestParam("email") String email)` |
| `ResponseEntity` | 상태 코드, 응답 헤더, 응답 본문을 함께 구성한다. |
| `@Configuration` | Java 클래스를 Spring 설정 클래스로 등록한다. |
| CORS | 출처가 다른 프론트엔드와 백엔드 사이의 브라우저 요청 허용 규칙 |
| Preflight | 브라우저가 실제 교차 출처 요청 전에 `OPTIONS`로 허용 여부를 확인하는 사전 요청 |
| `@Tag` | Swagger 문서에서 API 그룹의 이름과 설명을 작성한다. |
| `@Operation` | Swagger 문서에서 개별 엔드포인트의 기능을 설명한다. |
| `@ApiResponse` | API가 반환할 수 있는 상태 코드와 의미를 문서화한다. |
| 인증(Authentication) | 사용자가 누구인지 확인하는 과정 |
| 인가(Authorization) | 인증된 사용자가 특정 기능이나 자원에 접근할 권한이 있는지 확인하는 과정 |
| Access Token | 인증된 사용자가 API에 접근할 때 제시하는 토큰 |
| Refresh Token | Access Token을 다시 발급받는 흐름에 사용하는 토큰 |
| `HttpHeaders` | `Authorization`, `Refresh-Token` 등 HTTP 응답 헤더를 구성하는 객체 |
| `Dotenv` | `.env` 값을 읽어 시스템 프로퍼티로 등록해 YAML의 환경 변수 표현식에서 참조할 수 있게 한다. |

## 오늘 배운 것

### 생성자 기반 의존성 주입

Controller는 요청을 받고 응답을 반환하는 역할에 집중하고, 실제 회원 처리 로직은 Service에 위임한다. Service는 SQL 실행을 담당하는 Mapper와 토큰 생성을 담당하는 객체를 주입받는다. 각 클래스가 내부에서 `new`로 의존 객체를 만들지 않기 때문에 역할이 분리되고, 구현 교체와 테스트가 쉬워진다.

`@RequiredArgsConstructor`는 `final` 필드에 필요한 생성자를 자동으로 만든다. Spring은 생성자가 하나라면 `@Autowired`가 없어도 그 생성자를 이용해 Bean을 주입한다.

```java
@RequiredArgsConstructor
public class UserController {
    private final UserService userService;
}
```

`MybatispracticeApplication`처럼 애플리케이션 시작 클래스는 Controller가 실제로 사용하는 의존성이 아니다. 사용되지 않는 시작 클래스 필드와 생성자가 IDE 기능으로 추가됐다면 제거하고, Controller가 호출하는 `UserService`만 의존성으로 선언해야 한다.

---

### MyBatis Mapper 인터페이스와 XML 연결

사용자 도메인의 Mapper 인터페이스에는 Java에서 호출할 메서드 명세를 작성하고, Mapper XML에는 실행할 SQL을 작성한다. XML의 `namespace`는 Mapper 인터페이스의 전체 경로와 같아야 하고, 각 SQL의 `id`는 인터페이스 메서드명과 일치해야 한다.

| Mapper 인터페이스 | Mapper XML | 역할 |
| --- | --- | --- |
| `save(...)` | `<insert id="save">` | 회원 정보를 테이블에 저장 |
| `signIn(...)` | `<select id="signIn">` | 이메일과 비밀번호가 일치하는 사용자 조회 |

`parameterType`과 `resultType`에 적는 DTO의 패키지 경로도 실제 Java 패키지와 대소문자까지 완전히 같아야 한다. Mapper는 인터페이스이므로 직접 객체를 만들 수 없지만, MyBatis가 런타임에 프록시 구현체를 만들어 Spring에 등록하며 Service에는 이 프록시 객체가 주입된다.

---

### JSON 본문과 쿼리스트링 받기

요청 데이터가 들어오는 위치에 따라 Spring 어노테이션이 달라진다.

| 전달 방식 | 요청 예시 | Spring 어노테이션 | 적합한 사용 예 |
| --- | --- | --- | --- |
| JSON 본문 | `POST /user/signUp` + JSON | `@RequestBody` | 회원가입처럼 여러 값을 객체로 전달 |
| 쿼리스트링 | `GET /user/signIn?email=...&password=...` | `@RequestParam` | URL 뒤에 붙은 개별 파라미터 전달 |
| 경로 변수 | `GET /users/1` | `@PathVariable` | URL 경로 자체에 포함된 식별자 전달 |

```java
public ResponseEntity<?> signUp(
        @RequestBody UserRequestDTO request) {
    // JSON을 UserRequestDTO로 변환해 받는다.
}
```

```java
public ResponseEntity<?> signIn(
        @RequestParam("email") String email,
        @RequestParam("password") String password) {
    // 쿼리스트링 값을 각각 받는다.
}
```

현재 로그인 실습은 GET과 쿼리스트링으로 동작하게 구성했지만, 이 방식은 이메일과 비밀번호가 URL에 노출된다. 수업 메모에서는 추후 로그인 요청을 POST 방식으로 변경하는 방향을 확인했다.

`UserRequestDTO`는 Spring이 계속 보관하는 서비스 Bean이 아니라 요청마다 JSON에서 생성되는 데이터 객체다. `@NoArgsConstructor`와 `@AllArgsConstructor`는 객체 생성에 필요한 생성자를 Lombok으로 마련하고, `@Builder`는 쿼리 파라미터로 받은 값을 DTO로 다시 묶을 때 사용한다.

### Swagger로 API 명세 작성

Swagger UI는 `http://localhost:8000/swagger-ui/index.html`에서 확인한다. `@Tag`로 사용자 API 전체를 묶고, `@Operation`으로 회원가입과 로그인의 목적을 작성하며, `@ApiResponses`와 `@ApiResponse`로 성공·실패 상태 코드를 설명한다.

Swagger의 `@RequestBody`는 문서에 요청 본문의 설명과 스키마를 표시하고, Spring의 `@RequestBody`는 실제 JSON을 DTO로 변환한다. 이름은 같지만 역할과 패키지가 서로 다르다.

| 어노테이션 | 역할 |
| --- | --- |
| Swagger `@RequestBody` | API 문서에 요청 본문 설명 및 DTO 스키마 표시 |
| Spring `@RequestBody` | 실제 HTTP 요청 본문을 Java DTO로 변환 |

### 환경 변수와 실행 환경 분리

DB URL, 사용자 이름, 비밀번호처럼 민감하거나 환경마다 달라지는 값은 소스에 직접 작성하지 않고 `.env`로 관리한다. `Dotenv`가 `.env`의 값을 읽어 시스템 프로퍼티에 올리고, `application-dev.yml`은 `${DB_URL}`과 같은 표현식으로 값을 참조한다. `.env`는 저장소에 올라가지 않도록 `.gitignore`에 포함해야 한다.

`application.yml`에서는 기본 프로필을 `dev`로 지정하고, 개발 환경의 서버 포트와 DB 설정은 `application-dev.yml`로 분리했다. 애플리케이션을 배포할 때는 소스 코드와 라이브러리 등을 JAR로 묶어 실행할 수 있다.

---

### 로그인 처리와 토큰 응답 헤더

인증은 사용자의 신원을 확인하는 과정이고, 인가는 인증된 사용자의 접근 권한을 판단하는 과정이다. 현재 실습에서는 로그인 조회가 성공하면 `JwtProvider`의 메서드를 호출해 Access Token과 Refresh Token 자리에 사용할 문자열을 만들고, 사용자 응답과 토큰을 `Map`에 함께 담아 Controller로 전달한다.

Controller는 사용자 정보는 응답 본문에, Access Token과 Refresh Token은 각각 `Authorization`, `Refresh-Token` 헤더에 담는다. 브라우저의 JavaScript가 커스텀 응답 헤더를 읽을 수 있도록 `Access-Control-Expose-Headers`에도 두 헤더를 지정한다. 현재 `JwtProvider`가 반환하는 값은 실제 서명된 JWT가 아니라 실습용 고정 문자열이다.

---

### React와 Spring Boot 연결 및 CORS

React는 `localhost:3000`, Spring Boot는 `localhost:8000`에서 실행되므로 포트가 달라 서로 다른 출처로 판단된다. Axios 인스턴스의 `baseURL`을 백엔드 주소로 지정하고, Spring에서는 `WebMvcConfigurer`를 구현한 CORS 설정 클래스로 React 출처와 사용할 HTTP 메서드를 허용했다.

브라우저는 필요한 교차 출처 요청에 앞서 `OPTIONS` 방식의 Preflight 요청으로 서버가 실제 요청을 허용하는지 확인할 수 있다. 따라서 CORS 설정에는 실제 API 메서드뿐 아니라 `OPTIONS`도 포함했다.

React Router의 주소는 화면을 선택하는 프론트엔드 경로이고, Axios 주소는 Spring Controller를 호출하는 백엔드 경로다. 두 종류의 주소를 구분하면서도 Axios의 URL은 `@RequestMapping`과 `@PostMapping` 또는 `@GetMapping`을 조합한 서버 경로와 정확히 일치시켜야 한다.

## 오늘의 코드 3 - MyBatis 회원가입과 로그인 SQL 연결

UserMapper.java

```java
@Mapper
public interface UserMapper {
    int save(UserRequestDTO request);
    Optional<UserResponseDTO> signIn(UserRequestDTO request);
}
```

userMapper.xml

```xml
<mapper namespace="com.example.mybatispractice.features.users.repository.UserMapper">
    <insert id="save"
            parameterType="com.example.mybatispractice.features.users.domain.DTO.UserRequestDTO">
        INSERT INTO SPRING_USER_TBL(EMAIL, PASSWORD, NAME)
        VALUES(#{email}, #{password}, #{name})
    </insert>

    <select id="signIn"
            parameterType="com.example.mybatispractice.features.users.domain.DTO.UserRequestDTO"
            resultType="com.example.mybatispractice.features.users.domain.DTO.UserResponseDTO">
        SELECT EMAIL, PASSWORD, NAME FROM SPRING_USER_TBL
        WHERE EMAIL = #{email} AND PASSWORD = #{password}
    </select>
</mapper>
```

Mapper 메서드명과 XML의 SQL `id`를 맞춰 Java 호출이 회원 테이블의 SQL 실행으로 이어지도록 구성했다.

## 오늘의 코드 4 - 요청 바인딩과 Swagger API 명세

UserController.java

```java
@Operation(summary = "회원가입", description = "신규가입(email, password, name)")
@ApiResponses({
    @ApiResponse(responseCode = "201", description = "가입 성공"),
    @ApiResponse(responseCode = "400", description = "유효성 검사 실패"),
    @ApiResponse(responseCode = "500", description = "가입 실패")
})
@PostMapping("/signUp")
public ResponseEntity<?> signUp(@RequestBody UserRequestDTO request) {
    int signUpFlag = userService.signUp(request);
    if (signUpFlag != 0) {
        return ResponseEntity.status(HttpStatus.CREATED).body(null);
    }
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(null);
}
```

회원가입 JSON을 DTO로 받아 Service에 전달하고, 처리 결과에 따라 `201 Created` 또는 `500 Internal Server Error`를 반환하도록 작성했다.

## 오늘의 코드 5 - 로그인 토큰을 응답 헤더에 전달

UserService.java

```java
public Map<String, Object> signIn(UserRequestDTO request) {
    UserResponseDTO response = userMapper.signIn(request)
        .orElseThrow(() -> new RuntimeException("로그인 실패"));

    String at = jwtProvider.createAT(request.getEmail());
    String rt = jwtProvider.createRT(request.getEmail());

    Map<String, Object> map = new HashMap<>();
    map.put("response", response);
    map.put("at", at);
    map.put("rt", rt);
    return map;
}
```

UserController.java

```java
HttpHeaders headers = new HttpHeaders();
headers.add("Authorization", (String) map.get("at"));
headers.add("Refresh-Token", (String) map.get("rt"));
headers.add(
    "Access-Control-Expose-Headers",
    "Authorization, Refresh-Token"
);

return ResponseEntity
    .status(HttpStatus.OK)
    .headers(headers)
    .body((UserResponseDTO) map.get("response"));
```

로그인 결과는 본문에 담고 두 종류의 토큰은 HTTP 응답 헤더에 분리해 전달하는 흐름을 실습했다.

## 어려웠던 점 / 각종 오류

MyBatis 실행 중 `SqlSessionFactory` 생성에 실패하면서 DTO의 `wrong name` 오류가 발생했다. Mapper XML에는 `domain.DTO`가 적혀 있는데 Java DTO의 패키지가 `domain.dto`로 선언돼 있어 대소문자가 일치하지 않았던 것이 원인이었다. XML의 `parameterType`·`resultType`과 Java의 `package` 경로를 대소문자까지 동일하게 맞춰 해결했다.

`UserController`에 사용하지 않는 `MybatispracticeApplication` 필드와 생성자가 들어가 의존성 주입 대상으로 보였지만, 시작 클래스는 Controller가 사용하는 기능이 아니었다. IDE의 필드 초기화 또는 생성자 생성 기능으로 추가될 수 있는 코드와 실제 필요한 `UserService` 생성자 주입을 구분하고, 사용되지 않는 의존성은 제거해야 한다는 점을 확인했다.

회원가입 주소를 브라우저 주소창에서 직접 열었을 때 `No static resource user/signUp`이 나타났다. 주소창은 GET 요청을 보내지만 회원가입 Controller는 `POST /user/signUp`만 처리하기 때문에 일치하는 핸들러가 없었고, Spring이 정적 자원에서도 경로를 찾지 못해 오류를 반환한 것이었다. 회원가입은 브라우저 주소창이 아니라 Axios나 Swagger에서 POST 요청과 JSON 본문으로 호출해야 한다.

React 회원가입 코드가 `POST /users/signIn`을 호출하는 동안 Spring은 `POST /user/signUp`을 처리하고 있어 404가 발생했다. `/user`와 `/users`, `/signUp`과 `/signIn`이 모두 달랐기 때문에 Axios 요청을 현재 Controller 매핑과 같은 `POST /user/signUp`으로 맞췄다.

로그인을 GET 방식으로 처리하면서 JSON용 `@RequestBody`를 사용하면 요청 형식이 맞지 않았다. GET 요청의 이메일과 비밀번호는 쿼리스트링으로 보내고 Controller에서 `@RequestParam`으로 받도록 변경했다. 다만 비밀번호가 URL에 드러나는 문제가 있으므로 이후 POST 방식으로 변경할 필요가 있다.

React의 `localhost:3000`에서 Spring Boot의 `localhost:8000`으로 요청할 때 출처가 달라 CORS 정책에 막혔다. `WebMvcConfigurer`를 구현한 설정 클래스에서 React 출처와 사용할 메서드 및 Preflight용 `OPTIONS`를 허용해 연결했다.
