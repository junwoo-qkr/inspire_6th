# 제목: JPA로 회원가입·로그인 구현하기 — 엔티티 관계, Repository와 DTO 변환

## 오늘의 한 줄 요약

- 새 `jpapractice` 프로젝트에서 MyBatis로 만들었던 회원 기능을 Spring Data JPA 방식으로 구현했다.
- 사용자·게시글·댓글을 엔티티로 정의하고, 기본 키와 외래 키 관계를 어노테이션으로 연결했다.
- `JpaRepository<엔티티 타입, 기본 키 타입>`의 의미와 메서드 이름으로 조회 조건을 만드는 방법을 배웠다.
- 요청 DTO → 엔티티 → Repository → 응답 DTO로 이어지는 회원가입·로그인 흐름을 정리했다.
- 테스트의 설정 로딩, 엔티티 기본 생성자, 지연 로딩과 트랜잭션 범위를 함께 확인했다.
- 요청 파라미터를 DTO로 묶는 Spring MVC의 바인딩과 JSON 본문을 받는 방식을 구분했다.

## 키워드 정리

| 키워드 | 설명 또는 예시 |
| --- | --- |
| JPA·Hibernate | JPA는 자바 객체와 관계형 DB를 연결하는 표준이고, Hibernate는 이를 구현한다. |
| BOM | 관련 의존성의 버전을 묶어 관리하는 명세. 실습에서는 Spring AI BOM `1.0.0`을 명시했다. |
| `@Entity`·`@Table` | 엔티티와 매핑할 테이블을 지정한다. `@Table(name = "SPRING_JPA_USER_TBL")` |
| `@Id`·`@Column` | 기본 키와 컬럼 속성을 지정한다. `@Id private String email;` |
| `@GeneratedValue` | 기본 키 생성 전략을 지정한다. `@GeneratedValue(strategy = GenerationType.IDENTITY)` |
| `@OneToMany`·`@ManyToOne` | 사용자와 게시글처럼 일대다·다대일 관계를 표현한다. |
| `mappedBy` | 관계의 주인인 상대 엔티티의 필드명. `@OneToMany(mappedBy = "writer")` |
| `@JoinColumn` | 연관 객체를 연결하는 외래 키 컬럼을 지정한다. `@JoinColumn(name = "email")` |
| `fetch` | 연관 객체를 불러오는 전략. `fetch = FetchType.LAZY` |
| `optional` | 연관 객체가 반드시 있어야 하는지 정한다. `optional = false` |
| `orphanRemoval` | 부모와의 관계에서 제거된 자식 엔티티를 자동 삭제할지 정한다. |
| `JpaRepository<T, ID>` | 관리할 엔티티 타입과 기본 키 타입을 지정한다. `JpaRepository<UserEntity, String>` |
| 쿼리 메서드 | 이름으로 조회 조건을 표현한다. `findByEmailAndPassword(email, password)` |
| `Optional` | 조회 결과가 없을 수 있음을 표현한다. `result.orElseThrow(() -> new LoginFailException("로그인 실패"))` |
| DTO 변환 | `UserRequestDTO.toEntity(request)`, `UserResponseDTO.fromEntity(entity)` |
| `@Transactional` | 메서드 또는 테스트의 작업을 트랜잭션 범위로 묶는다. |
| `@NoArgsConstructor`·`@AllArgsConstructor` | Lombok으로 기본 생성자와 모든 필드를 받는 생성자를 만든다. |
| `@Autowired`·`Environment` | Spring 빈을 주입하고 설정값을 조회한다. `env.getProperty("DB_DRIVER")` |
| `spring.config.import` | 외부 설정 파일을 읽는다. `file:./.env[.properties]` |
| `@RequestParam`·`@ModelAttribute` | 요청 파라미터를 각각 받거나 DTO의 속성으로 묶어 받는다. |
| `@RequestBody` | Spring MVC에서 요청 본문을 DTO로 변환한다. Swagger의 동명 어노테이션과 구분한다. |
| `@Valid`·`BindingResult` | DTO의 유효성을 검사하고 검사 결과를 확인한다. |

### 엔티티와 테이블을 연결하는 매핑 설정

- Hibernate는 엔티티의 매핑 정보를 기준으로 DB 작업을 수행한다. `@Entity`와 `@Table`로 엔티티와 테이블을 연결하고, `@Id`와 `@Column`으로 기본 키와 컬럼 속성을 지정한다.
- 사용자는 문자열 `email`을 기본 키로 사용한다. 게시글과 댓글의 기본 키는 `Integer`이며, `GenerationType.IDENTITY`로 DB의 자동 증가 방식에 맡긴다. `@GeneratedValue`는 기본 키의 생성 전략을 지정하는 어노테이션이다.

```java
@Id
@Column(name = "email", length = 50, nullable = false)
private String email;

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Integer postId;
```

위 두 필드는 각각 사용자 엔티티와 게시글 엔티티의 기본 키를 나타낸다.

| 설정 | 역할 | 현재 실습에서 확인한 내용 |
| --- | --- | --- |
| `spring.application.name` | 애플리케이션 이름 | `jpapractice` |
| `ddl-auto: create` | 시작할 때 기존 테이블을 삭제하고 다시 생성 | 기존 데이터가 사라질 수 있는 옵션으로 학습했다. |
| `ddl-auto: none` | Hibernate의 자동 스키마 생성·변경을 수행하지 않음 | 현재 개발 설정에 적용되어 있다. |
| `physical-strategy` | 테이블·컬럼의 물리 이름을 결정 | `PhysicalNamingStrategyStandardImpl`을 지정했다. |
| `show-sql`·`format_sql` | 실행 SQL 표시와 보기 좋게 정렬 | 모두 `true`로 설정했다. |

현재 `ddl-auto` 값이 `none`이므로, 엔티티를 작성했다는 이유만으로 테이블이 자동 생성되는 상태는 아니다.

### 사용자·게시글·댓글의 연관 관계와 외래 키

- 사용자 한 명은 여러 게시글을 작성하고, 게시글 하나에는 여러 댓글이 연결된다. 객체에서는 연관 엔티티를 필드로 참조하고, DB에서는 외래 키 값으로 관계를 표현한다.

| 관계 | 여러 개를 참조하는 쪽 | 하나를 참조하는 쪽 | 외래 키 컬럼 |
| --- | --- | --- | --- |
| 사용자 ↔ 게시글 | `UserEntity.posts` | `BlogEntity.writer` | 게시글 테이블의 `email` |
| 게시글 ↔ 댓글 | `BlogEntity.comments` | `CommentEntity.post` | 댓글 테이블의 `postId` |

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "email")
private UserEntity writer;
```

- `writer`는 자바 필드명이고 `email`은 DB 외래 키 컬럼명이다. 자바 객체의 `writer`에는 `UserEntity` 참조가 들어가며, DB 컬럼에는 그 사용자의 기본 키인 이메일 값이 저장된다.
- `mappedBy = "writer"`의 `writer`는 상대 엔티티의 필드명이다. 외래 키 컬럼명을 넣는 자리가 아니다. `optional = false`는 연결할 연관 객체가 반드시 있어야 한다는 뜻이다.
- `orphanRemoval`은 관계에서 빠진 자식 엔티티의 삭제 여부와 관련된다. `false`라고 해서 외래 키 제약을 무시한 채 부모만 항상 삭제할 수 있다는 뜻은 아니다. `cascade`는 저장·삭제 등의 작업을 연관 엔티티에 전파하는 별도 설정이다. [Jakarta Persistence 관계 매핑 문서](https://jakarta.ee/specifications/persistence/3.1/apidocs/jakarta.persistence/jakarta/persistence/onetomany)

### 지연 로딩과 트랜잭션 범위

- 연관 관계가 있다고 해서 모든 데이터를 무조건 한꺼번에 가져오는 것은 아니다. `fetch` 전략과 실제 연관 데이터 접근 여부를 함께 봐야 한다.

| 전략 | 의미 | 실습 코드 |
| --- | --- | --- |
| `LAZY` | 연관 데이터 로딩을 필요할 때까지 미루는 전략 | `BlogEntity.writer`, `CommentEntity.post`에 명시했다. |
| `EAGER` | 연관 데이터를 즉시 로딩하도록 요구하는 전략 | `@ManyToOne`의 기본값이다. |

`@OneToMany`의 기본 전략은 `LAZY`다. 게시글의 `writer`를 `EAGER`로 바꾸면 게시글을 읽을 때 작성자를 로딩하는 방향에 영향을 준다. 사용자에서 게시글을 읽는 `posts`의 전략까지 함께 바뀌는 것은 아니다. [OneToMany 문서](https://jakarta.ee/specifications/persistence/3.1/apidocs/jakarta.persistence/jakarta/persistence/onetomany), [ManyToOne 문서](https://jakarta.ee/specifications/persistence/3.1/apidocs/jakarta.persistence/jakarta/persistence/manytoone)

- 아직 로딩하지 않은 연관 데이터에 접근하려면 해당 엔티티를 관리하는 영속성 컨텍스트가 열려 있어야 한다. 실습에서는 테스트에 `@Transactional`을 적용해 조회와 이후 접근을 하나의 트랜잭션 범위에서 수행하도록 했다.

```java
@SpringBootTest
@Transactional
class UserApplicationTest {
    // 테스트 메서드 안에서 조회와 연관 데이터 접근을 수행한다.
}
```

테스트 클래스에 붙인 `@Transactional`은 각 테스트 메서드에 적용되며, 기본적으로 테스트가 끝나면 롤백된다. 회원가입 테스트가 로그인 테스트용 데이터를 DB에 남긴다고 가정해서는 안 된다. [Spring 테스트 트랜잭션 문서](https://docs.spring.io/spring-framework/reference/testing/testcontext-framework/tx.html)

### JpaRepository의 제네릭과 쿼리 메서드

- `UserRepository`는 `JpaRepository`를 상속해 저장·조회·삭제 기능을 사용한다. Spring Data JPA가 저장소 구현을 제공하므로, 기본 CRUD 메서드의 구현을 직접 작성하지 않아도 된다.

```java
public interface UserRepository extends JpaRepository<UserEntity, String> {
    Optional<UserEntity> findByEmailAndPassword(String email, String password);
}
```

| 선언 부분 | 의미 |
| --- | --- |
| `extends JpaRepository` | Spring Data JPA의 저장소 기능을 상속한다. |
| `UserEntity` | 저장·조회할 엔티티 타입이다. |
| `String` | `@Id`가 붙은 `email`의 타입이다. |

`String`은 기본값이 아니라 **기본 키의 자료형**이다.

| 메서드 | 역할 | 반환값 |
| --- | --- | --- |
| `findById(email)` | 기본 키로 사용자 한 명 조회 | `Optional<UserEntity>` |
| `findByEmailAndPassword(email, password)` | 이메일과 비밀번호가 모두 일치하는 사용자 조회 | `Optional<UserEntity>` |
| `existsById(email)` | 해당 기본 키의 사용자 존재 여부 확인 | `boolean` |
| `save(entity)` | 엔티티 저장 또는 상태 병합 | 저장 처리 결과 엔티티 |
| `delete(entity)` | 전달한 엔티티 삭제 | 반환값 없음 |

- `findById()`가 인자를 하나 받는 이유는 기본 키로 조회하는 메서드이기 때문이다. 비밀번호 암호화 여부 때문에 인자 수가 정해지는 것은 아니다. 실습에서는 두 조건이 필요해 `findByEmailAndPassword()`를 선언했다.
- 쿼리 메서드의 `Email`과 `Password`는 엔티티 속성을 가리키고, `And`는 두 조건을 함께 적용한다. 조회 결과가 없을 때의 처리는 `Optional`로 명시한다.

```java
UserEntity entity = userRepository
    .findByEmailAndPassword(request.getEmail(), request.getPassword())
    .orElseThrow(() -> new LoginFailException("Sign In Failed"));
```

`save()`는 새 엔티티 여부에 따라 저장 또는 병합을 수행하므로, 항상 INSERT만 실행한다고 볼 수 없다. 반환값도 전달한 객체와 반드시 같은 인스턴스라는 보장이 없어 반환된 엔티티를 사용한다. [Spring Data JPA 저장 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html)

### 요청 DTO·엔티티·응답 DTO의 역할 분리

- 이번 실습에서는 요청과 응답에 DTO를 사용하고, DB 작업에는 엔티티를 사용하도록 흐름을 나눴다. DTO를 쓰는 방식은 JPA 프로젝트에만 한정된 기능은 아니다.

| 객체 | 역할 | 실습 메서드 |
| --- | --- | --- |
| `UserRequestDTO` | 요청 데이터 전달 | `toEntity(request)` |
| `UserEntity` | 테이블 매핑과 DB 작업 | `userRepository.save(entity)` |
| `UserResponseDTO` | 응답 데이터 구성 | `fromEntity(entity)` |

```java
UserEntity entity = UserRequestDTO.toEntity(request);
UserEntity saved = userRepository.save(entity);
UserResponseDTO response = UserResponseDTO.fromEntity(saved);
```

- 회원가입 서비스는 처리 건수 대신 `UserResponseDTO`를 반환하고, 컨트롤러는 이를 `201 Created` 응답에 담는다. 저장 실패 시에는 예외 흐름으로 넘어가기 때문에, 이전의 정수 `flag` 검사와 반환 방식이 달라졌다.
- 현재 전역 예외 처리기에 직접 등록된 것은 `LoginFailException`의 `401 Unauthorized` 처리다. 회원가입에서 발생하는 모든 예외를 이 핸들러가 개별 처리한다고 단정하지 않는다.
- 수업에서는 동일 사용자의 존재 여부를 확인한 뒤 가입시키는 흐름도 다뤘다. 다만 현재 서비스에서 `existsById()`를 사용하는 코드는 주석이므로, 실행되는 회원가입 로직에 중복 확인이 구현된 상태는 아니다.

### 요청 파라미터를 DTO로 받는 데이터 바인딩

- `@RequestParam`으로 값을 각각 받은 뒤 DTO를 직접 만들 수도 있고, Spring MVC의 데이터 바인딩으로 요청 파라미터를 DTO에 묶어 받을 수도 있다. JPA로 바꿨기 때문에 가능해진 기능은 아니다.

| 방식 | 받는 데이터 | 특징 |
| --- | --- | --- |
| `@RequestParam` | 쿼리 문자열·폼 파라미터 | 값을 각각 받는다. |
| `@ModelAttribute` | 쿼리 문자열·폼 파라미터 등 | 파라미터 이름을 DTO 속성과 연결한다. |
| Spring의 `@RequestBody` | 요청 본문 | JSON 등을 메시지 변환기로 DTO로 변환한다. |
| Swagger의 `@RequestBody` | API 문서에 표시할 설명 | 실제 요청 바인딩을 수행하지 않는다. |

DTO 바인딩의 형태를 단순화하면 다음과 같다.

```java
@GetMapping("/signIn")
public void signIn(@ModelAttribute UserRequestDTO request) {
    userService.signIn(request);
}
```

- 다른 방식으로 처리되지 않는 일반 DTO 매개변수는 `@ModelAttribute`를 생략해도 같은 방식으로 해석된다. 현재 DTO처럼 기본 생성자로 객체를 만드는 구조에서 속성 바인딩을 하려면 값을 설정할 Setter가 필요하다. `@Getter`나 `@Builder`만 붙인 것으로 이를 대신할 수는 없다. [Spring MVC 데이터 바인딩 문서](https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-controller/ann-methods/modelattrib-method-args.html)
- 현재 저장된 로그인 컨트롤러는 `@RequestParam`으로 이메일과 비밀번호를 받은 뒤 DTO를 직접 만드는 방식이다. DTO로 직접 받는 방식은 오늘 질문하며 비교한 내용으로 정리했다.
- 회원가입은 Spring의 `@RequestBody`와 `@Valid`를 사용하며, `BindingResult`에서 검증 실패를 확인해 `400 Bad Request`를 반환한다. 요청 데이터를 받는 것과 유효성을 검사하는 것은 별개의 과정이다.

### 테스트에서도 읽히는 외부 설정

- `.env` 라이브러리를 의존성에 추가하는 것과 실제로 파일을 읽는 것은 별개다. 기존 애플리케이션은 `main()` 안에서 dotenv를 실행했지만, 기본 `@SpringBootTest`는 그 `main()`을 호출하지 않는다. [Spring Boot 테스트 문서](https://docs.spring.io/spring-boot/3.5/reference/testing/spring-boot-applications.html)
- 현재는 공통 설정에 `spring.config.import`를 추가해 Spring의 설정 로딩 과정에서 `.env`를 읽도록 했다.

```yaml
spring:
  config:
    import: file:./.env[.properties]
```

`[.properties]`는 `.env`를 properties 형식으로 읽으라는 힌트다. 현재 경로는 실행 작업 디렉터리를 기준으로 하며, `Environment`는 이렇게 읽은 설정값을 조회하는 역할을 한다. `Environment`를 import하거나 주입하는 것 자체가 `.env`를 읽는 작업은 아니다. [Spring Boot 외부 설정 문서](https://docs.spring.io/spring-boot/3.5/reference/features/external-config.html)

## 어려웠던 점 / 각종 오류

`UserApplicationTest.signUp()`에서 `Failed to load ApplicationContext`가 발생했다. 이 메시지는 테스트 본문에 들어가기 전에 Spring 초기화가 실패했다는 뜻이며, 구체적인 원인은 아래쪽 `Caused by:`까지 확인해야 한다. 대화에 제공된 로그에는 해당 원인이 없어 당시 실패 원인을 확정하지는 못했다. 수업에서는 `.env` 로딩 문제를 다뤘고, 현재 설정에는 `spring.config.import`가 반영되어 있다.

처음 테스트 코드에는 `userRepository`의 `@Autowired`가 빠져 있었다. 필드를 선언하는 것만으로 의존성이 주입되지는 않는다. 다만 당시처럼 문자열과 연결해 출력하는 코드는 `null`을 출력할 뿐이므로, 이 누락을 ApplicationContext 초기화 실패와 같은 문제로 보지는 않아야 한다. 현재 테스트에는 주입 어노테이션이 추가되어 있다.

로그인 테스트에서는 연관 엔티티의 기본 생성자 문제도 다뤘다. 현재 사용자·게시글·댓글 엔티티에는 모두 `@NoArgsConstructor`와 `@AllArgsConstructor`가 추가되어 있다. JPA에 필요한 것은 public 또는 protected 기본 생성자이며, 모든 필드를 받는 생성자가 JPA의 필수 조건인 것은 아니다.

조회한 엔티티를 출력할 때 지연 로딩과 트랜잭션 범위가 연결된다는 점이 어려웠다. `Optional.get()` 자체가 게시글을 조회하는 것은 아니다. 현재 출력문에서는 엔티티의 `toString()`이 호출되며, Lombok의 `@ToString`이 연관 필드를 다루는 과정에서 지연 로딩이 발생할 수 있다. 실습에서는 테스트 클래스에 `@Transactional`을 붙여 조회 이후의 접근을 같은 범위로 묶었다.

`JpaRepository<UserEntity, String>`의 두 번째 타입을 기본값으로 이해하기 쉬웠지만, 실제로는 `@Id`가 붙은 필드의 타입이었다. `findById()`가 기본 키 하나를 받는다는 점과 함께 정리하니 제네릭과 조회 메서드의 관계를 이해할 수 있었다.

로그인 요청을 DTO로 바로 받을 수 있는 이유도 질문했다. Spring MVC의 `@ModelAttribute` 바인딩 기능과 DTO 생성·값 설정 조건을 함께 봐야 했다. 특히 Swagger의 `@RequestBody`를 Spring의 요청 본문 변환 기능과 혼동하지 않도록 구분했다. 현재 코드는 `@RequestParam` 방식으로 저장되어 있어, DTO 바인딩으로 수정하고 정상 실행까지 확인했다고 기록하지 않았다.
