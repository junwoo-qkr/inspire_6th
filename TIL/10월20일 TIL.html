오늘의 한 줄 요약

  • Micrometer로 지표를 측정하고 Actuator로 노출하며, Prometheus에서 수집·저장한 값을 Grafana에서 시각화하는 흐름을 학습했다.
  • Timer와 @Timed로 처리 시간을 측정하고, 세 서비스의 지표를 Gateway를 통해 15초마다 수집하도록 설정했다.
  • Prometheus의 수집 설정과 지표 이름을 확인하고 Windows 실행 명령 및 설정 키 오타의 오류 원인을 구분했다.

키워드 정리

키워드 설명 또는 예시
Micrometer 여러 모니터링 시스템에 공통 방식으로 애플리케이션 지표를 제공하는 계측 라이브러리
Actuator Spring Boot 애플리케이션의 상태와 지표를 엔드포인트로 제공하는 기능
Timer 완료된 작업의 횟수와 처리 시간을 기록하는 지표
@Timed 메서드 실행을 계측하는 애너테이션. value로 지표 이름 지정
longTask=true 실행 중인 작업의 개수와 진행 시간을 측정하는 LongTaskTimer 사용
Prometheus 지표를 주기적으로 수집하고 시계열 데이터로 저장·조회하는 도구
Pull 방식 수집기가 대상에 먼저 요청하여 지표를 가져오는 방식
scrape_interval 지표 수집 주기. 실습에서는 15s
metrics_path 지표 수집 요청에 사용하는 HTTP 경로
job 라벨 수집 작업을 구분하는 값. job="user-service"
Grafana 데이터 소스를 조회하여 그래프와 대시보드로 표현하는 도구

오늘 배운 것

지표 계측·노출·수집·시각화의 역할

각 마이크로서비스의 요청 처리 시간과 JVM 상태를 관찰하기 위해 지표를 만드는 부분부터 저장하고 화면에 표현하는 부분까지 역할을 나누어 구성한다.

구성 요소 역할
Micrometer 애플리케이션 내부에서 실행 횟수·처리 시간·JVM 상태 등을 계측한다.
Actuator 계측한 값을 HTTP 엔드포인트로 노출한다.
Prometheus 엔드포인트에 주기적으로 요청하고 지표를 시계열 데이터로 저장한다.
Grafana Prometheus에 질의하고 결과를 대시보드로 표현한다.

이번 구성은 애플리케이션 계측 → Actuator 노출 → Prometheus 수집·저장 → Grafana 시각화로 이어진다. Prometheus는 시간별 측정값을 보관하므로 서비스 상태의 변화를 비교할 수 있다.

Actuator에서 지표 조회와 수집 경로 준비하기

Spring Boot에서는 Actuator의 자동 설정을 통해 JVM·HTTP 요청 등의 지표를 등록한다. Prometheus용 레지스트리를 추가하고 필요한 엔드포인트를 HTTP 노출 목록에 포함하여 수집 경로를 준비한다.

경로 제공하는 내용
/actuator/metrics 현재 등록된 지표 이름의 목록
/actuator/metrics/{지표 이름} 선택한 지표의 측정값과 태그
/actuator/prometheus Prometheus가 읽을 수 있는 형식의 지표

JVM 관련 지표는 자동 등록될 수 있고, HTTP 요청처럼 실행에 따라 생성되는 지표는 해당 동작 이후 나타날 수 있다. Actuator 조회에서는 원래 지표 이름을 사용하며, Prometheus에 내보낼 때는 밑줄과 단위 접미사를 사용하는 이름으로 변환된다.

Timer와 @Timed로 처리 시간 측정하기

Timer는 완료된 작업의 실행 횟수와 총 처리 시간을 함께 기록한다. 같은 측정 구간의 횟수와 총 시간을 이용하면 호출 빈도와 처리 시간의 변화를 해석할 수 있다.

구분 측정 대상 관찰하는 값
Timer 실행을 마친 작업 완료 횟수, 누적 처리 시간 등
LongTaskTimer 현재 실행 중인 작업 실행 중인 작업 수, 진행 시간 등
  • @Timed의 value는 지표 이름이다. 현재 사용자 서비스에는 user.status와 users.welcome이 사용된다.
  • 사용자 서비스에서 management.observations.annotations.enabled를 true로 설정했다. 애너테이션 기반 계측에는 AspectJ/AOP 지원도 필요하다.
  • 일반 HTTP 요청은 Spring Boot가 자동 계측할 수 있으며, @Timed는 선택한 메서드를 별도의 이름으로 측정할 때 사용한다.
  • longTask=true는 실행 중인 작업을 관찰한다. 수집 시점 사이에 끝나는 짧은 작업은 진행 중인 상태가 Prometheus에 관측되지 않을 수 있다.

Prometheus 수집 설정과 Gateway 경로 연결

Prometheus는 Pull 방식으로 대상의 지표 경로에 주기적으로 요청한다. 서버 주소와 포트는 targets, 요청 경로는 metrics_path에서 정하며, 기본 HTTP 방식에서는 두 값을 조합한 URL에 접속한다.

설정 역할
job_name 수집 작업의 이름이며 기본 job 라벨로 붙는다.
scrape_interval 지표 수집 주기다. 작업별 값이 있으면 해당 작업에 우선 적용한다.
metrics_path 대상에서 지표를 읽을 HTTP 경로다.
static_configs 수집 대상 주소를 설정에 직접 나열한다.
targets 접속할 호스트와 포트를 지정한다.

현재 전역 수집 주기와 세 서비스의 작업별 수집 주기는 모두 15s다. 대상 주소는 모두 Gateway인 localhost:8000이며, 요청 경로를 달리하여 서비스별 지표를 가져온다.

수집 작업 수집 URL 경로 처리
user-service http://localhost:8000/user-service/actuator/prometheus USER-SERVICE로 전달하며 /user-service 접두사 제거
order-service http://localhost:8000/order-service/actuator/prometheus ORDER-SERVICE로 전달하며 /order-service 접두사 제거
apigateway-service http://localhost:8000/actuator/prometheus Gateway 자체의 Actuator 지표 제공

사용자 서비스의 Actuator 전용 경로는 일반 사용자 조회 경로보다 먼저 정의되어 있다. 주문 서비스도 Actuator 전용 라우트로 연결하며, 각 서비스가 받는 실제 지표 요청 경로는 /actuator/prometheus가 된다.

localhost는 Prometheus가 실행되는 환경을 기준으로 해석된다. 현재 설정에는 Prometheus를 Docker에서 실행하는 경우 호스트 접근 주소로 host.docker.internal:8000을 사용하는 주석이 남아 있다.

HTTP 요청 지표와 Gateway 지표 읽기

Prometheus 화면에서 지표 이름을 검색하여 시간에 따른 변화를 확인한다. 요청 처리 횟수와 처리 시간은 서로 다른 지표로 제공된다.

Prometheus 지표 의미
http_server_requests_seconds_count 해당 라벨 조합으로 기록된 완료 요청의 누적 횟수
http_server_requests_seconds_sum 완료 요청 처리 시간의 누적 합계. 단위는 초
http_server_requests_seconds_max 설정된 시간 구간에서 기록한 최대 처리 시간. 단위는 초
spring_cloud_gateway_requests_seconds_count Gateway의 라우팅 요청 Timer가 기록한 완료 요청 횟수

HTTP 요청 지표의 uri 라벨은 가능한 경우 요청을 처리한 핸들러의 URI 패턴을 나타낸다. 패턴을 얻지 못하면 상태와 경로에 따른 대체 값이 사용되며, 그중 하나가 UNKNOWN이다.

Gateway의 라우팅 지표는 spring.cloud.gateway.requests라는 Timer에서 나오며, 라우트 ID와 목적지 등의 태그로 흐름을 구분한다. job 라벨을 함께 확인하면 어느 수집 작업에서 가져온 값인지 구분할 수 있다.

Grafana 데이터 소스 연결과 대시보드 조정

Grafana는 Prometheus를 데이터 소스로 등록한 뒤 저장된 지표를 조회해 그래프로 표현한다. 수업에서는 Docker로 Grafana를 준비하고 JVM(Micrometer), Prometheus, Spring Cloud Gateway 대시보드를 연결하는 흐름을 다뤘다.

점검 대상 맞춰야 하는 내용
데이터 소스 참조 가져온 대시보드가 실제 등록한 Prometheus 데이터 소스를 가리키도록 맞춘다.
Gateway 지표 이름 패널의 검색식에 spring_cloud_gateway_requests_seconds_count 등 실제 지표 이름을 사용한다.
서비스 선택 조건 Gateway 패널의 job 조건을 apigateway-service와 맞춘다.
패널의 필드 선택 수치 데이터를 표시하는 패널에서는 Numeric fields 등 목적에 맞는 옵션을 선택한다.

가져온 대시보드의 데이터 소스, 지표 이름, 라벨 조건이 현재 수집 설정과 연결되어야 원하는 값을 표시할 수 있다. 그래프가 표시하는 지표와 필드 선택을 함께 확인한다.

오늘의 코드 1 - Prometheus 지표 레지스트리 추가

pom.xml (user-service)

		<dependency>
			<groupId>io.micrometer</groupId>
			<artifactId>micrometer-registry-prometheus</artifactId>
		</dependency>

 

Prometheus용 Micrometer 레지스트리 의존성을 추가한 부분이다. 같은 의존성이 사용자·주문·Gateway 서비스의 미커밋 변경에 모두 포함되어 있으며, Actuator에서 Prometheus 형식의 지표를 제공하는 데 사용한다.

오늘의 코드 2 - Actuator 지표 노출과 애너테이션 계측 설정

application.yml (user-service)

management:
  observations:
    annotations:
      enabled: true
  endpoints:
    web:
      exposure:
        include:
          - refresh
          - health
          - beans
          - info
          - httpexchanges
          - busrefresh
          - prometheus
          - metrics

 

사용자 서비스에서 애너테이션 계측 설정을 켜고 HTTP 노출 목록에 prometheus와 metrics를 추가했다. 주문 서비스와 Gateway에도 두 엔드포인트가 추가되어 있으며, 애너테이션 계측 활성화 설정은 현재 사용자 서비스에서 확인된다.

오늘의 코드 3 - @Timed로 환영 메시지 메서드 계측

UserController.java

    @GetMapping("/welcome")
    @Timed(value="users.welcome")
    public String welcome(HttpServletRequest request) {
        log.info("users.welcome ip: {}, {}, {}, {}", request.getRemoteAddr()
                , request.getRemoteHost(), request.getRequestURI(), request.getRequestURL());

//        return env.getProperty("greeting.message");
        return greeting.getMessage();
    }

 

/welcome을 처리하는 메서드에 users.welcome이라는 사용자 지정 Timer 이름을 부여했다. 요청 정보를 로그로 남기고 greeting.getMessage()를 반환하며, 애너테이션 계측이 동작하는 환경에서는 메서드의 실행 횟수와 처리 시간을 기록한다.

오늘의 코드 4 - Gateway에서 서비스별 지표 경로 연결

application.yml (apigateway-service)

            - id: user-service-actuator
              uri: lb://USER-SERVICE
              predicates:
                - Path=/user-service/actuator/**
                - Method=GET,POST
              filters:
                - RemoveRequestHeader=Cookie
                - RewritePath=/user-service/(?<segment>.*), /$\{segment}

 

/user-service/actuator/** 요청을 Eureka에 등록된 USER-SERVICE로 전달하는 전용 라우트다. RewritePath가 /user-service 접두사를 제거하므로 외부 수집 경로는 서비스 내부의 /actuator/prometheus로 연결된다.

application.yml (apigateway-service)

            - id: order-service-actuator
              uri: lb://ORDER-SERVICE
              predicates:
                - Path=/order-service/actuator/**
                - Method=GET,POST
              filters:
                - RewritePath=/order-service/(?<segment>.*), /$\{segment}

 

주문 서비스도 Actuator 전용 라우트를 통해 Gateway에서 접근하도록 설정했다. Prometheus는 고정된 Gateway 주소로 요청하고, Gateway는 ORDER-SERVICE 인스턴스를 찾아 접두사를 제거한 경로로 전달하도록 구성되어 있다.

오늘의 코드 5 - 세 서비스의 Prometheus 수집 작업 등록

prometheus.yml

  - job_name: 'user-service'
    scrape_interval: 15s
    metrics_path: '/user-service/actuator/prometheus'
    static_configs:
      - targets: ['localhost:8000']  # Prometheus를 Docker로 실행했을 경우: 'host.docker.internal:8000'
  - job_name: 'order-service'
    scrape_interval: 15s
    metrics_path: '/order-service/actuator/prometheus'
    static_configs:
      - targets: ['localhost:8000']
  - job_name: 'apigateway-service'
    scrape_interval: 15s
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['localhost:8000']

 

지정한 외부 설정 파일의 34–48줄에 세 서비스의 수집 작업이 정의되어 있다. 각 작업은 localhost:8000의 서로 다른 경로에 15초마다 요청하도록 구성되어 있으며, 현재 파일은 promtool의 설정 문법 검사를 통과했다.

어려웠던 점 / 각종 오류

Windows 명령 프롬프트에서 ./prometheus로 실행했을 때 '.'은(는) 내부 또는 외부 명령, 실행할 수 있는 프로그램, 또는 배치 파일이 아닙니다.라는 메시지가 출력됐다. 이후 같은 디렉터리에서 prometheus --config.file=prometheus.yml로 실행하자 설정 파일을 읽는 단계까지 진행했다. 실행 명령 해석 오류와 설정 파일 해석 오류를 구분할 수 있었다.

이후 로그에는 line 45: field scrape-interval not found in type config.ScrapeConfig가 표시됐다. 파일을 찾은 뒤 설정을 해석하는 과정에서 잘못된 키를 발견한 것이며, 올바른 키는 밑줄을 사용하는 scrape_interval이다. 현재 파일의 45줄은 올바른 키로 수정되어 있고 설정 문법 검사도 통과했으며, 실제 서비스 지표 수집과 Grafana 패널 표시는 이번 TIL 작성 과정에서 재확인하지 않았다.
