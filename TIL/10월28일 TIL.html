[LG CNS AM INSPIRE CAMP 6기] 10/28 TIL - Kubernetes: Pod를 관리하는 컨트롤러와 Service 연결 방식

오늘의 한 줄 요약

  • Kubernetes의 각 컴포넌트는 API 서버를 통해 상태를 공유하고, Pod의 배치와 실행을 나누어 담당한다.
  • ReplicationController와 ReplicaSet은 Pod 수를 유지하고, Deployment는 ReplicaSet을 관리하며 버전 변경을 배포한다.
  • DaemonSet은 노드별 실행을, StatefulSet은 순번이 붙은 Pod의 식별 유지를 담당한다.
  • Service는 라벨로 연결 대상을 찾으며, 접근 위치와 개별 Pod 주소의 필요성에 따라 연결 방식을 선택한다.

오늘 배운 것

네임스페이스와 리소스 조회 범위

네임스페이스는 같은 클러스터의 리소스를 작업 범위별로 구분한다. 네임스페이스를 지정하지 않은 명령은 현재 문맥에 설정된 범위를 사용하며, 별도 설정이 없다면 default를 사용한다.

  • kubectl create namespace로 네임스페이스를 만든다.
  • 리소스를 생성한 범위가 현재 조회 범위와 다르면 -n으로 해당 네임스페이스를 지정한다. 전체 네임스페이스의 조회에는 -A를 사용한다.
  • kubectl get의 출력에 wc -l을 연결하면 출력 줄 수를 센다. 헤더와 실행 대기 중인 리소스도 출력에 포함될 수 있으므로 실행 중인 리소스 수와 구분한다.
  • kubectl edit로 API 서버에 저장된 리소스를 수정할 수 있으며, 수정 후의 반영 방식은 리소스 종류와 변경한 필드에 따라 달라진다.

컨트롤 플레인과 노드 컴포넌트의 역할

컴포넌트 역할
kube-apiserver 리소스 생성·조회·변경 요청을 받고 인증, 권한과 요청 유효성을 확인한다.
etcd API 서버를 통해 클러스터의 설정과 상태 데이터를 키·값 형태로 저장한다.
kube-scheduler 아직 노드가 정해지지 않은 Pod를 보고 실행할 노드를 선택한다.
kube-controller-manager 원하는 상태와 현재 상태를 비교하는 여러 컨트롤러를 실행한다.
kubelet 각 노드에서 자신에게 배정된 Pod의 컨테이너 실행과 상태 보고를 담당한다.
kube-proxy 선택한 프록시 모드에 따라 iptables 등의 규칙으로 Service 통신을 구현한다.
컨테이너 런타임 containerd, CRI-O 등 실제 컨테이너를 실행하는 소프트웨어이다.

Pod 생성 요청은 kubectl에서 API 서버로 전달되고, 검증을 거친 명세가 저장된다. 스케줄러는 API 서버를 통해 미배치 Pod를 확인한 뒤 노드 배정을 기록하고, 해당 노드의 kubelet은 그 명세에 따라 CRI를 통해 런타임에 컨테이너 실행을 요청한다. 이후 kubelet이 보고한 상태도 API 서버를 통해 저장된다.

각 컴포넌트는 API 서버에 기록된 변화를 관찰하며 자신의 작업을 수행한다. ReplicationController 같은 리소스에는 목표 상태가 담기고, 그 목표를 맞추는 제어 로직은 kube-controller-manager에서 실행된다.

단독 Pod와 ReplicationController·ReplicaSet의 관리 방식

대상 Pod를 관리하는 방식 삭제와 템플릿 변경
단독 Pod 상위 컨트롤러 없이 직접 생성한다. Pod 자체를 삭제하면 대체 Pod를 자동 생성하지 않는다.
ReplicationController spec.replicas와 라벨 선택 조건으로 개수를 유지한다. Pod가 부족하면 템플릿으로 생성한다. 템플릿 변경은 이후 생성되는 Pod에 적용된다.
ReplicaSet spec.selector.matchLabels 등으로 대상을 정하고 개수를 유지한다. 기존 Pod의 일괄 교체를 위한 업데이트 관리는 Deployment와 함께 구성한다.

Pod 안의 컨테이너가 종료되었을 때 kubelet이 컨테이너를 다시 실행하는 일과, 삭제된 Pod를 컨트롤러가 새로 생성하는 일은 구분해야 한다. 컨테이너 재시작은 restartPolicy에 따라 동작하며, Pod 수의 유지에는 관리 컨트롤러가 관여한다.

선택 조건은 컨테이너 이미지가 아니라 Pod의 라벨을 기준으로 한다. app: webui를 선택하는 컨트롤러는 그 조건에 맞는 관리자가 없는 Redis Pod도 관리 대상으로 가져올 수 있고, 목표 개수를 넘으면 Pod를 줄인다. RC·RS의 템플릿 라벨은 해당 선택 조건을 만족해야 한다.

RC·RS의 이미지 템플릿을 수정하면 저장된 템플릿은 바뀌지만 기존 Pod를 자동으로 새 이미지로 교체하지는 않는다. 부족한 Pod를 생성하거나 삭제된 Pod를 대체할 때 새 템플릿이 사용된다. ReplicaSet만 삭제하고 Pod를 남기는 삭제 정책에는 --cascade=orphan을 사용한다.

Deployment의 버전 관리와 롤링 업데이트

Deployment는 ReplicaSet을 관리하고, ReplicaSet은 Pod를 관리한다. Pod 템플릿을 바꾸면 그 템플릿에 대응하는 ReplicaSet을 생성하거나 재사용하면서 기존 Pod와 새 Pod의 수를 조절한다. 이전 ReplicaSet은 롤백에 사용할 수 있도록 남길 수 있다.

설정 의미와 실습 값
strategy.type: RollingUpdate 기존 Pod와 새 Pod의 수를 조절하며 점진적으로 교체한다.
maxSurge: 25% 목표 개수보다 추가로 생성할 수 있는 Pod 수이다. 비율 계산 결과는 올림하므로 목표가 3개이면 1개이다.
maxUnavailable: 25% 업데이트 중 사용 불가를 허용하는 Pod 수이다. 비율 계산 결과는 내림하므로 목표가 3개이면 0개이다.
revisionHistoryLimit: 10 롤백을 위해 보존할 이전 ReplicaSet의 개수를 설정한다.
progressDeadlineSeconds: 600 배포 진행이 지연되었다고 판단할 기준 시간을 초 단위로 지정한다.
kubernetes.io/change-cause 변경 사유를 기록하는 Annotation 키이다. 리소스 선택에는 라벨을 사용한다.

이미지 변경에는 kubectl set image를 사용할 수 있고, 변경 이력은 kubectl rollout history로 확인한다. kubectl rollout undo는 이전 템플릿으로 되돌리는 명령이며, --to-revision으로 대상 리비전을 지정할 수 있다.

DaemonSet과 StatefulSet의 실행 기준

리소스 주요 기준 사용 맥락
DaemonSet 실행 대상 노드마다 Pod 한 개를 관리하며 replicas로 전체 수를 지정하지 않는다. 각 노드에 필요한 로그 수집기나 모니터링 에이전트
StatefulSet 순번이 붙은 Pod 이름과 개별 식별을 유지한다. DB처럼 개별 인스턴스를 일정한 이름으로 구분해야 하는 애플리케이션

StatefulSet은 재생성 후에도 같은 순번의 이름을 사용할 수 있지만 새 실행 인스턴스의 IP는 달라질 수 있다. 저장 데이터의 유지는 별도의 영구 스토리지 설정과 연결되며, 제공된 예제에는 볼륨 설정이 없다.

Pod 관리 정책 생성과 축소 동작
OrderedReady 기본 정책이다. 앞선 Pod가 준비될 때까지 기다리며 생성하고, 축소 시 높은 순번부터 종료를 기다리며 삭제한다.
Parallel 앞선 Pod의 준비나 종료 완료를 기다리지 않고 여러 Pod의 생성·삭제를 진행한다. 실습 YAML에서 활성화된 정책이다.

StatefulSet의 serviceName은 Pod의 네트워크 식별에 사용할 Service 이름이다. 개별 Pod 이름을 DNS로 찾는 구성을 위해 같은 이름의 Headless Service를 준비한다.

Service의 접근 범위와 포트 연결

Service는 Pod의 IP가 바뀌어도 일정한 이름과 접근 지점을 사용할 수 있도록 한다. 선택 조건이 있는 Service는 spec.selector에 맞는 Pod를 연결 대상으로 삼으며, 라벨 키는 app 외에도 지정할 수 있다.

방식 접근 지점 주요 용도
ClusterIP 클러스터 내부의 Service IP와 포트 클러스터 안의 애플리케이션 사이 통신
NodePort 노드 IP와 nodePort; 내부 ClusterIP도 제공 노드에 도달할 수 있는 외부 클라이언트의 접근
LoadBalancer 외부 로드 밸런서가 제공하는 접근 주소 외부 로드 밸런서를 통한 서비스 노출
ExternalName Service 이름을 조회했을 때 돌려주는 외부 DNS 이름 내부 이름으로 외부 도메인을 참조
Headless Service DNS에서 얻은 개별 Pod 주소 대표 IP 없이 개별 연결 대상을 발견
포트 역할
port Service가 요청을 받는 포트
targetPort 요청을 전달할 대상 Pod의 포트
nodePort NodePort 방식으로 노드에서 접근할 때 사용하는 포트

NodePort는 클러스터의 노드에서 같은 포트를 통해 Service로 접근하도록 구성하며, 접속하는 쪽에서 노드 IP와 포트에 도달할 수 있어야 한다. LoadBalancer는 클라우드 제공자나 별도의 로드 밸런서 구현과 연동하며, 일반적인 구성에서는 NodePort도 함께 사용한다.

Headless Service와 ExternalName의 DNS 동작

Headless Service는 type: ClusterIP에 clusterIP: None을 지정한 구성이다. 선택 조건이 있는 경우 Service 이름의 DNS 조회가 대상 Pod들의 IP를 돌려주므로, 클라이언트가 얻은 주소로 직접 연결한다. 이 Service에는 대표 ClusterIP를 통한 프록시나 부하 분산이 구성되지 않는다.

StatefulSet과 함께 사용하면 Pod의 일정한 이름을 이용해 연결 대상을 구분할 수 있다. 이때 Pod의 식별 유지는 StatefulSet이 담당하고, DNS를 통한 주소 발견은 Headless Service와 클러스터 DNS가 담당한다.

ExternalName은 externalName에 적힌 외부 DNS 이름을 CNAME으로 알려준다. 제공된 설정의 대상은 google.com이며, DNS 별칭을 제공하는 방식이므로 Service가 외부 서버까지 트래픽을 프록시하는 구조와 구분된다.

오늘의 코드 1 - 단독 Pod와 ReplicationController의 라벨 선택

redis.yaml

metadata:
  labels:
    app: webui
  name: redis
spec:
  containers:
  - image: redis
    name: redis

 

직접 선언한 Redis Pod에는 app: webui 라벨이 붙어 있다. 이 라벨은 아래 ReplicationController의 선택 조건과 일치하므로, 이 Pod도 해당 컨트롤러의 관리 대상이 될 수 있다.

rc-nginx.yaml

spec:
  replicas: 3
  selector:
    app: webui
  template:
    metadata:
      name: nginx-pod
      labels:
        app: webui
    spec:
      containers:
      - name: nginx-container
        image: nginx:1.14

 

목표 개수는 replicas: 3이고, 선택 조건과 새 Pod 템플릿의 라벨이 모두 app: webui이다. 템플릿에는 nginx:1.14가 지정되어 있으며, 컨트롤러는 선택된 Pod 수가 목표 개수에 맞도록 생성과 삭제를 조절한다.

오늘의 코드 2 - ReplicaSet의 선택 조건과 Pod 템플릿

rs-nginx.yaml

spec:
  replicas: 3
  selector:
    matchLabels:
      app: webui
  template:
    metadata:
      name: nginx-pod
      labels:
        app: webui

 

이 파일의 리소스 종류는 apps/v1의 ReplicaSet이며, matchLabels로 관리할 Pod를 선택한다. 목표 개수는 3개이고 템플릿의 app: webui가 선택 조건을 만족한다.

오늘의 코드 3 - Deployment의 Pod 배포와 변경 이력

deploy-nginx.yaml (k8slab1)

spec:
  replicas: 3
  selector:
    matchLabels:
      app: webui
  template:
    metadata:
      name: nginx-pod
      labels:
        app: webui
    spec:
      containers:
      - name: nginx-container
        image: nginx:1.14

 

deploy-nginx Deployment의 초기 템플릿은 nginx:1.14를 사용하며 Pod 목표 개수는 3개이다. Deployment 아래의 ReplicaSet이 이 템플릿으로 Pod를 관리하는 구조를 확인할 수 있다.

deployment-exam2.yaml

metadata:
  name: deploy-nginx
  annotations:
    kubernetes.io/change-cause: version 1.15

 

동일한 deploy-nginx 리소스에 version 1.15라는 변경 사유가 기록되어 있다. kubernetes.io/change-cause는 부가 설명을 저장하는 Annotation이며 Pod 선택 조건과 역할이 다르다.

deployment-exam2.yaml

spec:
  progressDeadlineSeconds: 600
  revisionHistoryLimit: 10
  strategy:
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%
    type: RollingUpdate
  replicas: 3
  selector:
    matchLabels:
      app: webui
  template:
    metadata:
      labels:
        app: webui
    spec:
      containers:
      - name: web
        image: nginx:1.15
        ports:
        - containerPort: 80

 

새 템플릿은 nginx:1.15를 사용하고 롤링 업데이트의 추가 생성과 사용 불가 허용 비율을 각각 25%로 지정한다. 목표 개수가 3개이므로 계산상 추가 생성 허용량은 1개, 사용 불가 허용량은 0개이며 이전 ReplicaSet은 최대 10개 보존하도록 설정되어 있다.

오늘의 코드 4 - DaemonSet의 노드별 Pod 관리

daemonset-exam.yaml

kind: DaemonSet
metadata:
  name: daemonset-nginx
spec:
  selector:
    matchLabels:
      app: webui
  template:
    metadata:
      name: nginx-pod
      labels:
        app: webui

 

리소스 종류가 DaemonSet이고 Pod 템플릿과 라벨 선택 조건이 정의되어 있다. 전체 Pod 수를 replicas로 정하는 대신 실행 대상 노드별로 Pod가 있도록 관리하는 예제이다.

오늘의 코드 5 - StatefulSet의 이름 유지와 병렬 관리 정책

statefulset-exam.yaml

kind: StatefulSet
metadata:
  name: sf-nginx
spec:
  replicas: 3
  serviceName: sf-service
#  podManagementPolicy: OrderedReady
  podManagementPolicy: Parallel

 

sf-nginx는 Pod 3개와 serviceName: sf-service를 선언하며, OrderedReady는 주석이고 Parallel이 활성화되어 있다. 기본 순번 설정에서 생성될 이름은 sf-nginx-0, sf-nginx-1, sf-nginx-2이고, 실제 생성·축소의 대기 방식은 활성화된 정책을 따른다.

오늘의 코드 6 - ClusterIP·NodePort·LoadBalancer의 접근 설정

clusterip-nginx.yaml

spec:
  type: ClusterIP
  clusterIP: 10.100.100.100
  selector:
    app: webui
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80

 

clusterip-service는 내부 IP 10.100.100.100의 80번 포트를 app: webui Pod의 80번 포트로 연결하도록 선언되어 있다. 직접 지정한 ClusterIP는 실제 클러스터의 Service 주소 범위 안에 있어야 하며 다른 Service와 중복되지 않아야 한다.

nodeport-nginx.yaml

spec:
  type: NodePort
  clusterIP: 10.100.100.200
  selector:
    app: webui
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
    nodePort: 30200

 

nodeport-service에는 내부 IP 10.100.100.200과 노드 포트 30200이 함께 지정되어 있다. 노드 IP의 30200번 포트 또는 내부 Service IP의 80번 포트로 접근해 대상 Pod의 80번 포트에 연결하는 설정이다.

loadbalancer-nginx.yaml

spec:
  type: LoadBalancer
  selector:
    app: webui
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80

 

loadbalancer-service는 type: LoadBalancer로 선언되어 있고 같은 라벨의 Pod 80번 포트를 연결 대상으로 삼는다. YAML 자체에 외부 IP가 적혀 있지는 않으며, 실제 외부 접근 주소의 할당은 로드 밸런서 구현과 클러스터 환경에 달려 있다.

오늘의 코드 7 - Headless Service와 외부 DNS 이름 연결

headless-nginx.yaml

spec:
  type: ClusterIP
  clusterIP: None
  selector:
    app: webui
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80

 

headless-service는 clusterIP: None과 라벨 선택 조건을 사용하므로 DNS를 통해 대상 Pod의 IP를 찾는 설정이다. 앞선 StatefulSet의 serviceName은 sf-service로 선언되어 있어, 제공된 두 파일을 그 StatefulSet의 네트워크 식별용으로 연결하려면 Service 이름을 맞춰야 한다.

external-name.yaml

spec:
  type: ExternalName
  externalName: google.com

 

externalname-svc의 외부 DNS 대상은 google.com으로 지정되어 있다. 선택 조건이나 Pod 포트 대신 외부 DNS 이름을 등록하는 구성을 확인할 수 있다.

어려웠던 점 / 각종 오류

ReplicationController와 kube-controller-manager가 같은 것인지 헷갈렸다. ReplicationController는 목표 Pod 수와 템플릿을 담는 리소스이고, 그 내용을 보고 실제 상태를 조절하는 제어 로직은 kube-controller-manager에서 실행된다는 관계로 정리했다.

수업 메모에는 nginx Pod 3개를 관리하던 중 같은 app: webui 라벨의 Redis Pod를 추가하자 Redis가 삭제된 결과가 기록되어 있다. 컨트롤러가 라벨 조건에 맞는 Pod를 관리 대상으로 가져오면서 목표 개수를 초과한 상황으로 이해했다. 이미지가 달라도 선택 조건이 같으면 관리 대상이 겹칠 수 있어 라벨의 역할을 확인하는 것이 중요했다.

RC·RS의 템플릿을 수정했을 때 기존 Pod가 바로 새 버전이 되는지와 Deployment의 업데이트 동작을 구분하기 어려웠다. 새로 생성될 Pod의 명세를 바꾸는 것과 실행 중인 Pod를 교체하는 배포 절차를 나누어 정리했고, Deployment의 maxSurge와 maxUnavailable은 각각 추가 생성과 사용 불가 허용량이라는 기준으로 이해했다.

ClusterIP·NodePort·Headless Service는 쇼핑몰의 연결 상황으로 구분했다. 클러스터 안의 웹 서버가 상품 API를 호출할 때는 ClusterIP, 외부 컴퓨터가 노드 포트로 웹 화면에 들어올 때는 NodePort, DB 클라이언트가 개별 인스턴스의 주소를 찾아 연결할 때는 Headless Service를 사용하는 흐름이다. Headless Service에서 어느 DB 역할에 접속할지는 애플리케이션이나 DB 클라이언트가 결정한다.
