  • 사용자·상품·주문 서비스를 나누고, 요청 객체 → DTO → Entity → 응답 객체의 역할을 구분했다.
  • Eureka에 등록한 서비스 이름과 Gateway의 경로 조건을 연결하고, 실제 Controller 경로까지 맞춰야 한다는 것을 배웠다.

  • H2 메모리 DB는 서비스 프로세스마다 분리되며, 상품 테이블 생성 후 초기 데이터를 넣도록 실행 순서를 설정한다.
  • 주문은 사용자 ID를 경로에서 받고, 주문 ID와 총액을 생성해 저장한 뒤 사용자별로 조회한다.

오늘 배운 것

사용자·상품·주문 서비스의 책임과 데이터 객체

사용자 서비스는 회원 등록과 조회, 상품 서비스는 상품 목록 조회, 주문 서비스는 주문 생성과 사용자별 주문 조회를 담당한다. 각 서비스의 Controller가 HTTP 요청을 받고, Service가 처리 흐름을 구성하며, Repository가 DB 저장과 조회를 맡는다.

객체 역할 실습 예시
요청 객체 클라이언트가 보낸 JSON을 받는다. RequestUser, RequestOrder
DTO 서비스 내부에서 처리할 값을 전달한다. UserDto, OrderDto
Entity DB 테이블과 컬럼에 연결되는 데이터를 표현한다. UserEntity, CatalogEntity, OrderEntity
응답 객체 클라이언트에게 공개할 필드를 선택한다. ResponseUser, ResponseCatalog, ResponseOrder

ModelMapper는 객체 사이의 변환을 돕지만 DB 저장이나 비밀번호 해싱까지 수행하지는 않는다. 비밀번호와 내부 DB 기본 키가 응답에 노출되지 않도록 응답 객체를 별도로 둔다. 현재 상품 목록 조회는 CatalogEntity를 ResponseCatalog로 변환하며, CatalogDto를 거치는 흐름은 사용하지 않는다.

// 요청과 DB 객체를 직접 연결하지 않고 처리용 DTO로 먼저 변환한다.
UserDto dto = mapper.map(request, UserDto.class);
UserEntity entity = mapper.map(dto, UserEntity.class);
// 저장·해싱 등은 별도 처리이며, 응답은 공개할 필드만 가진 객체로 만든다.
ResponseUser response = mapper.map(dto, ResponseUser.class);

서비스 등록, 포트와 설정값 읽기

Spring Boot 애플리케이션은 main 메서드에서 시작되고, 사용자 서비스에는 서비스 발견을 위한 @EnableDiscoveryClient가 선언되어 있다. application.yml의 spring.application.name은 서비스 이름이고, eureka.client.service-url.defaultZone은 등록할 Eureka 서버의 주소다. register-with-eureka는 등록 여부, fetch-registry는 등록 정보 조회 여부를 정한다.

현재 사용자 서비스는 실습 편의를 위해 60000번 포트로 고정되어 있고, 상품·주문 서비스는 server.port가 0이다. server.port는 설정값이고 local.server.port는 웹 서버가 시작된 뒤 결정된 실제 포트이므로, 임의 포트 방식에서는 두 값을 구분해야 한다. 인스턴스 ID에 임의 값을 넣으면 같은 이름으로 실행한 여러 인스턴스를 구분할 수 있다.

// port가 0이면 설정값은 "0", 실제 포트는 실행할 때 배정된 번호다.
String configuredPort = env.getProperty("server.port");
String actualPort = env.getProperty("local.server.port");

// Spring이 관리하는 객체에는 설정값을 직접 주입할 수도 있다.
@Value("${greeting.message}")
private String message;

Gateway 경로와 Controller 경로 연결

Gateway는 Path 조건으로 요청을 받을 서비스를 고르고, lb:// URI의 서비스 이름으로 Eureka에 등록된 인스턴스를 찾는다. 현재 사용자·상품·주문 경로에는 접두사를 제거하는 필터가 없으므로 /user-service 같은 접두사를 포함한 경로가 해당 서비스로 전달된다. Controller의 클래스 경로와 메서드 경로를 합친 값이 전달된 경로와 같아야 한다.

기능 HTTP 메서드 현재 프로젝트의 전체 경로
회원 등록 POST /user-service/users
전체 회원 조회 GET /user-service/users
회원 상세 조회 GET /user-service/users/{userId}
상품 목록 조회 GET /catalog-service/catalogs
주문 생성 POST /order-service/{userId}/orders
사용자별 주문 조회 GET /order-service/{userId}/orders

Gateway를 이용하는 요청은 현재 설정의 8000번 포트로 보내고, 직접 호출할 때는 각 서비스의 실제 포트를 사용한다. PDF의 상태 확인 예시에는 /health_check가 등장하지만, 현재 프로젝트는 /health-check를 사용하므로 실제 매핑에 맞춰 호출해야 한다.

@RequestMapping("/user-service")
class ExampleController {
    // 클래스와 메서드 경로를 합쳐 /user-service/users가 된다.
    @GetMapping("/users")
    public String users() { return "users"; }
}

요청 검증과 JPA의 DB 제약 구분

요청 검증은 입력값이 처리 조건을 만족하는지 확인하는 단계다. @NotNull은 null을 막고, @Size(min = 2)는 길이의 최소 조건을 지정하며, @Email은 이메일 형식을 검사한다. @NotNull만으로 빈 문자열이나 공백 문자열까지 금지되는 것은 아니다.

JPA의 @Column(nullable = false, unique = true)는 DB 컬럼의 제약이고 요청 검증과 적용 위치가 다르다. 실습의 UserEntity는 숫자형 id를 DB 기본 키로 사용하고, userId에는 서비스가 생성한 UUID를 저장한다. Repository의 findByUserId는 DB 기본 키가 아닌 이 userId 프로퍼티를 조건으로 조회한다.

// 개념 예시: @Valid로 요청 객체의 검증 제약을 적용한다.
@PostMapping("/users")
public void register(@Valid @RequestBody ExampleRequest request) { }

class ExampleRequest {
    @NotNull
    @Size(min = 8) // 비밀번호 길이는 최소 8자라는 뜻이다.
    public String pwd;
}

현재 RequestUser에는 검증 제약이 선언되어 있지만 createUser의 요청 매개변수에는 @Valid가 없다. 따라서 제약을 적어 두었다는 이유만으로 이 API에서 자동 검증이 실행된다고 기록할 수 없다. PDF의 비밀번호 안내 문구에 최대 길이가 언급되어도 @Size에 max가 없다면 최대 길이 조건이 설정된 것은 아니다.

회원 등록과 BCrypt 비밀번호 처리

회원 등록은 RequestUser를 UserDto로 변환한 뒤 UUID로 userId를 생성하고, UserEntity로 변환해 저장하는 흐름이다. DB에 저장하기 전에 BCryptPasswordEncoder로 원문 비밀번호를 해싱하여 encryptedPwd에 넣는다. 정상 처리 시 Controller는 ResponseUser와 201 Created를 반환하도록 작성되어 있다.

BCrypt 해시는 복호화해서 원문을 꺼내는 값이 아니다. 솔트가 포함되므로 같은 비밀번호를 다시 encode해도 해시 문자열은 달라질 수 있고, 일치 여부는 matches(원문, 저장된 해시)로 확인한다. 암호화된 비밀번호라는 필드 이름과 달리 실습의 encryptedPwd에는 BCrypt 해시가 들어간다.

BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();
String storedHash = encoder.encode("sample-password");
// 새로 생성한 해시 문자열끼리 비교하지 않고 원문과 저장된 해시를 검사한다.
boolean matched = encoder.matches("sample-password", storedHash);
// 이 예시의 matched는 true다. 해시에서 원문을 복원하는 과정은 없다.

H2 계정, Basic 인증 계정과 가입 회원 구분

H2 콘솔의 로그인은 DB 접속이고, Basic 인증은 HTTP 요청의 사용자 인증이다. 현재 WebSecurity는 /h2-console/**를 허용하고 나머지 사용자 서비스 요청에 인증을 요구한다. 회원 가입 API도 이 나머지 경로에 포함되므로 현재 설정에서는 Basic 인증을 함께 보내야 한다.

구분 설정 또는 저장 위치 현재 코드에서 확인한 값·역할
H2 접속 계정 spring.datasource username은 sa, password는 빈 값이다.
Basic 인증 계정 spring.security.user name은 user이고 password에는 BCrypt 해시가 설정되어 있다.
가입 회원 users 테이블 회원 정보와 해싱한 비밀번호를 저장한다. 현재 Basic 인증과 연결하는 조회 구현은 없다.

Basic 인증 요청에는 해시를 만들기 전의 비밀번호를 입력한다. application.yml의 해시 문자열 자체를 비밀번호로 보내는 방식이 아니다. Utils.java는 예시 원문 password의 해시를 출력하지만, 현재 설정된 해시와 이 원문의 일치 여부는 확인하지 않았으므로 실제 인증 비밀번호라고 단정하지 않는다.

회원 조회와 null·빈 주문 목록의 차이

전체 회원 조회는 Repository의 findAll로 읽은 Entity를 ResponseUser 목록으로 변환한다. 상세 조회는 findByUserId로 회원을 찾고 UserDto에 주문 목록을 넣은 뒤 ResponseUser로 변환한다. 회원이 없으면 서비스 코드에서 UsernameNotFoundException을 던지지만, 이 예외만으로 HTTP 404 응답이 보장되는 것은 아니다.

@JsonInclude(NON_NULL)은 null 필드를 JSON에서 생략한다. 빈 리스트는 null이 아니므로 응답에 빈 배열로 남는다. 현재 회원 상세 조회는 새 빈 리스트를 직접 설정하므로 orders가 빈 배열이며, 주문 서비스에 저장된 주문을 가져오는 연동은 구현되어 있지 않다.

// NON_NULL을 적용한 응답 객체의 개념 예시
response.setOrders(null);              // JSON에서 orders 필드를 생략한다.
response.setOrders(new ArrayList<>()); // JSON에 "orders": []를 포함한다.

서비스별 H2 DB와 상품 초기화 순서

jdbc:h2:mem:testdb는 이름이 testdb인 메모리 DB를 뜻하지만, 이름이 같다고 별도 서비스 프로세스들이 하나의 DB를 공유하지는 않는다. 현재 사용자·상품·주문 서비스는 각각 실행되는 애플리케이션이므로 사용자 DB에는 users, 상품 DB에는 catalog, 주문 DB에는 orders를 각자의 Entity 기준으로 만든다. DB_CLOSE_DELAY=-1은 마지막 연결이 닫혀도 해당 프로세스 안의 메모리 DB를 유지하는 설정이며, 프로세스가 종료된 후까지 데이터를 보존하는 설정은 아니다.

설정 역할 현재 적용 서비스
ddl-auto: update 기존 스키마를 기준으로 필요한 변경을 반영한다. 사용자·주문 서비스
ddl-auto: create-drop 시작 시 스키마를 다시 만들고 정상 종료 시 삭제한다. 상품 서비스
defer-datasource-initialization: true SQL 초기화를 JPA 초기화 이후로 미룬다. 상품 서비스의 data.sql 실행 순서

상품 서비스는 CatalogEntity로 catalog 테이블을 만든 후 data.sql의 세 상품을 넣도록 설정되어 있다. createdAt 컬럼은 CURRENT_TIMESTAMP 기본값을 갖고, insertable = false와 updatable = false로 JPA의 INSERT·UPDATE 대상에서 제외되어 DB가 생성 시각을 채운다. 이 설명은 확인한 설정과 코드의 동작이며, 이번 작성 과정에서 SQL 조회를 실행해 테이블이나 데이터 존재를 확인한 것은 아니다.

-- 개념 예시: 초기 데이터는 대상 테이블 생성 이후에 넣어야 한다.
insert into catalog(product_id, product_name, stock, unit_price)
values('EXAMPLE-001', 'Example', 10, 1000);
-- created_at을 생략하면 DB에 선언된 기본값이 적용된다.

상품 목록 조회와 사용자별 주문 처리

상품 목록은 CatalogRepository의 findAll로 읽고 ResponseCatalog에 상품 ID·이름·단가·재고·생성 시각을 담아 반환한다. 주문 생성은 URL의 userId와 RequestOrder의 productId·qty·unitPrice를 OrderDto에 모아 처리한다. 주문 서비스가 UUID로 orderId를 만들고 qty × unitPrice로 totalPrice를 계산해 orders에 저장한다.

// 주문의 사용자 ID는 경로에서, 수량과 단가는 요청 본문에서 받는다.
orderDto.setUserId(userId);
orderDto.setOrderId(UUID.randomUUID().toString());
orderDto.setTotalPrice(orderDto.getQty() * orderDto.getUnitPrice());
// 예시: qty가 2, unitPrice가 1500이면 totalPrice는 3000이다.

사용자별 주문 조회는 findByUserId로 해당 사용자 ID가 저장된 주문을 찾아 응답 목록으로 변환한다. 현재 주문 생성 코드는 요청 본문의 단가를 사용하며, 상품 서비스의 가격 조회·재고 감소나 사용자 존재 확인을 수행하지 않는다. 또한 주문 생성 응답의 중간 객체인 OrderDto에는 createdAt이 없으므로 Entity를 바로 변환하는 주문 목록 응답과 생성 시각 필드가 다를 수 있다.

오늘의 코드 1 - Gateway: 서비스 이름으로 요청 분기

application.yml

- id: user-service
  uri: lb://USER-SERVICE
  predicates:
    - Path=/user-service/**
- id: catalog-service
  uri: lb://CATALOG-SERVICE
  predicates:
    - Path=/catalog-service/**
- id: order-service
  uri: lb://ORDER-SERVICE
  predicates:
    - Path=/order-service/**

 

Gateway의 routes 설정에 사용자·상품·주문 서비스의 경로 조건을 추가했다. Path로 요청을 구분하고 lb://서비스명으로 Eureka에 등록된 인스턴스를 찾아 전달하도록 구성했다. 세 경로는 접두사를 유지하므로 각 서비스의 Controller 경로도 이에 맞췄다.

오늘의 코드 2 - 사용자 서비스: Eureka에 서비스 등록

application.yml

server:
#  port: 0
  port: 60000 # 실습 편의상 60000번으로 고정

spring:
  application:
    name: user-service

 

서비스 이름을 user-service로 지정하고 실습 편의를 위해 포트를 60000으로 고정했다. 이 서비스 이름이 Gateway의 lb://USER-SERVICE에서 대상을 찾는 기준이 된다.

application.yml

eureka:
  instance:
    instance-id: ${spring.application.name}:${spring.application.instance_id:${random.value}}
    prefer-ip-address: true # 호스트명 대신 IP로 등록
  client:
    service-url:
      defaultZone: http://127.0.0.1:8761/eureka
    fetch-registry: true
    register-with-eureka: true

 

8761번 Eureka 서버에 자신을 등록하고 등록 정보를 조회하도록 설정했다. 인스턴스 ID로 같은 서비스의 실행 인스턴스를 구분하고 IP 주소로 등록하도록 구성했다. 상품·주문 서비스에도 동일한 Eureka 설정을 적용했으므로 공통 설정은 여기에서 한 번만 발췌했다.

오늘의 코드 3 - 상품 서비스: 임의 포트와 Gateway 경로 연결

application.yml

server:
  port: 0

spring:
  application:
    name: catalog-service

 

상품 서비스는 catalog-service라는 이름으로 등록하도록 설정하고, port: 0으로 실행 시 포트를 배정받게 했다. Gateway의 /catalog-service/** 요청은 lb://CATALOG-SERVICE로 연결되므로 라우팅 대상에 상품 서비스의 포트를 직접 적지 않는다.

오늘의 코드 4 - 주문 서비스: 같은 연동 구조 확장

application.yml

server:
  port: 0

spring:
  application:
    name: order-service

 

주문 서비스도 order-service라는 이름과 임의 포트를 사용해 같은 Eureka 등록 구조를 적용했다. Gateway는 /order-service/** 요청을 lb://ORDER-SERVICE로 전달하도록 설정했다. 여러 서비스에 같은 등록·라우팅 방식을 적용하여 하나의 Gateway로 각 서비스에 접근하는 구조를 구성했다.

어려웠던 점 / 각종 오류

60000번 포트의 H2 콘솔에 접속하면서 DB 계정과 Basic 인증 계정을 혼동했다. H2 로그인에는 사용자 서비스의 spring.datasource 설정을 사용하여 JDBC URL에 jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1;, User Name에 sa를 넣고 Password를 비워 둔다. HTTP 요청용 user 계정은 spring.security.user에 설정되어 있어 H2 로그인 계정과 다르다.

application.yml에 들어 있는 BCrypt 해시를 요청 비밀번호로 보내야 하는지도 헷갈렸다. Basic 인증 요청에는 해당 해시를 생성할 때 사용한 원문 비밀번호를 입력하고, 서버가 원문과 저장된 해시의 일치 여부를 확인한다. Utils.java의 예시 원문은 password이지만, 현재 설정된 해시와의 일치는 별도로 확인해야 실제 요청 비밀번호를 확정할 수 있다.

catalog-service를 실행했는데 H2에서 catalog 테이블을 찾을 수 없는 이유를 살펴봤다. 60000번 콘솔로 접속하면 사용자 서비스의 DB에 연결되므로 같은 testdb라는 이름을 사용해도 별도 프로세스인 상품 서비스의 테이블을 조회할 수 없다. 상품 서비스의 실제 포트를 시작 로그나 Eureka 등록 정보에서 확인한 뒤 그 포트의 /h2-console에 접속해야 하며, 임의 포트는 재실행할 때 바뀔 수 있다.
