오늘 배운 것

예외 분류와 처리 위치

Checked exception도 실행 중 발생한다. 컴파일 시점에는 처리 여부를 검사하며, IOException과 이번 CustomException이 예다. RuntimeException 계열은 처리 선언이 강제되지 않으며, 배열 범위를 벗어나거나 문자열을 숫자로 바꾸지 못할 때 발생할 수 있다.

// Java
try {
    int menu = Integer.parseInt("abc"); // 정수로 변환할 수 없음
} catch (NumberFormatException e) {
    System.out.println("숫자를 입력하세요."); // 예외 처리 결과
} finally {
    System.out.println("입력 확인 끝"); // 처리 후 실행
}

여러 catch를 쓰면 구체적인 하위 예외를 먼저 둔다. finally는 정상 완료·예외·return으로 블록을 벗어나는 과정에서 실행되지만, System.exit로 JVM이 종료되면 실행이 보장되지 않는다.

throw와 throws로 사용자 정의 예외 전달하기

throw는 예외 객체를 던져 현재 실행 흐름을 바꾼다. throws는 메서드 밖으로 전달될 수 있는 예외를 선언하며 예외를 처리하는 동작 자체는 아니다. Exception을 상속한 CustomException은 호출자가 처리하거나 다시 선언해야 한다.

// Java
static void validate(int value) throws CustomException {
    if (value < 0) {
        throw new CustomException("0 이상을 입력하세요."); // 음수 거부
    }
} // validate(0)은 통과, validate(-1)은 호출자에게 예외 전달

계층 분리와 생성자 주입

구성 요소 이번 실습의 역할

생성자 주입은 객체가 사용할 의존 객체를 외부에서 받는 방식이다. 팩토리가 DAO → Service → Controller 순서로 만들고 연결하며, 컨트롤러는 서비스 인터페이스 타입을 사용한다.

// Java
BlogReactDao dao = new BlogReactDao();
BlogReactService service = new BlogReactSerciveImpl(dao); // DAO 전달
ListController controller = new ListController(service); // Service 전달
System.out.println(controller.list().size()); // 디버그 로그 다음에 4

싱글톤 팩토리와 콘솔 MVC의 범위

BlogBeanFactory.getInstance()는 단일 스레드의 이 콘솔 실습에서 같은 팩토리를 반환한다. 팩토리는 list.posts 키에 컨트롤러를 저장하고, getBean은 객체를 조회한다. 이 구현에는 동시 초기화를 막는 처리가 없다.

// Java
BlogBeanFactory first = BlogBeanFactory.getInstance();
BlogBeanFactory second = BlogBeanFactory.getInstance();
System.out.println(first == second); // 같은 팩토리이므로 true

DAO와 Service는 팩토리 생성 시 한 번 만들어 공유하지만 각각이 싱글톤 클래스로 구현된 것은 아니다. 현재는 HTTP·서블릿·DB가 없는 콘솔 구조이며 전체 조회만 연결되어 있다. List.of(...)는 수정 불가 목록을 만들고, 이를 감싼 new ArrayList<>(...)는 요소 추가·삭제가 가능한 목록을 만든다.

오늘의 코드 1 - 배열 범위 예외 처리와 finally

ExceptionApp.java

// Java
String[] strArr = {"Oasis", "Maroon 5", "YOASOBI"};
try {
    for (int i = 0; i <= strArr.length; i++) {
        System.out.println(strArr[i]);
    }
} catch(ArrayIndexOutOfBoundsException e) {
    e.printStackTrace();
} finally {
    System.out.println("예외 발생 여부와 상관없이 실행");
}

 

요소 세 개를 출력한 뒤 인덱스 3 접근에서 ArrayIndexOutOfBoundsException을 재현했다. catch에서 예외를 출력하고 finally를 실행한 뒤 다음 입력 코드로 진행했다.

오늘의 코드 2 - 사용자 정의 예외 발생과 전파

CustomException.java

// Java
public class CustomException extends Exception {
    public CustomException() {
    }
    public CustomException(String msg) {
        super(msg);
    }
}

 

기존 Exception을 상속하고 생성자로 받은 메시지를 부모 생성자에 전달했다. 호출자는 catch (CustomException e)로 이 예외를 구분해 처리할 수 있다.

ExceptionDemo.java

// Java
public void sample(int x) throws CustomException {
    System.out.println("sample 시작");
    try {
        if(x < 0) {
            throw new CustomException("양의 정수를 입력하세요.");
        }
    } finally {
        System.out.println("sample 끝");
    }
}

 

sample(-1)은 시작·끝을 출력하고 예외를 호출자인 ExceptionApp으로 전달했다. 실제 조건은 음수만 거부하므로 0도 허용하며, 메시지의 양의 정수라는 표현과 허용 범위가 다르다.

오늘의 코드 3 - 팩토리에서 의존 객체 연결하기

BlogBeanFactory.java

// Java
private BlogBeanFactory() {
    map = new HashMap<>();
    dao = new BlogReactDao();
    service = new BlogReactSerciveImpl(dao);
    map.put("list.posts", new ListController(service));
}

public static BlogBeanFactory getInstance() {
    if(instance == null) {
        instance = new BlogBeanFactory();
    }
    return instance;
}

 

DAO를 서비스에, 서비스를 컨트롤러에 생성자로 전달했다. 전체 조회 실행 시 팩토리에 등록된 컨트롤러에서 서비스와 DAO로 호출이 이어졌다.

오늘의 코드 4 - 요청 키로 조회하고 DTO 목록 출력하기

BlogFrontController.java

// Java
public List<BlogResponseDTO> list(String endPoint) {
    System.out.println("debug >>>> BlogFrontController.list, endPoint = " + endPoint);
    Object controller = factory.getBean(endPoint);
    return ((ListController)controller).list();
}

 

list.posts에 등록된 객체를 ListController로 변환해 조회를 요청했다. 등록되지 않은 키에는 null이 반환되므로 그대로 호출할 수 없다.

BlogReactView.java

// Java
public void list() {
    System.out.println(">>>> 데이터 출력 <<<<");
    String endPoint = "list.posts";
    List<BlogResponseDTO> response = front.list(endPoint);
    response.stream().forEach(System.out::println);
}

 

조회 결과가 List<BlogResponseDTO>로 돌아와 게시글 1~4가 콘솔에 출력됐다. @ToString이 적용되어 각 DTO의 필드 값을 확인할 수 있었다.

어려웠던 점 / 각종 오류

배열 반복 조건을 i <= strArr.length로 쓰면 길이와 같은 인덱스에 접근해 예외가 발생한다. 모든 요소만 순회하려면 i < strArr.length로 수정해야 한다.

콘솔에 숫자가 아닌 값을 입력하면 Integer.parseInt에서 NumberFormatException이 발생한다. View의 catch가 안내 문구를 출력한 뒤 메뉴를 다시 표시하므로 올바른 번호를 다시 입력할 수 있다.
