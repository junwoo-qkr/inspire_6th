키워드 정리

키워드 설명 또는 예시
groupId / artifactId Maven 프로젝트의 소속과 이름. 예: com.example, user-service
clean / compile / package 기존 빌드 산출물 삭제 / 소스 컴파일 / 배포 형식으로 묶기
JAR / WAR Java Archive / Web Application Archive. 오늘은 실행 가능한 JAR 파일을 다뤘다.
Service Discovery 서비스 이름으로 실행 중인 인스턴스의 주소를 찾는 기능
Eureka Registry 서비스의 이름, 주소, 포트 등 인스턴스 정보를 보관하는 등록부
@EnableEurekaServer Eureka 서버 기능을 활성화하는 어노테이션
@EnableDiscoveryClient 서비스 발견 클라이언트를 나타내는 어노테이션. Eureka 클라이언트 starter로 자동 구성도 가능하다.
register-with-eureka / fetch-registry 자신의 정보를 등록할지 / 등록된 서비스 정보를 조회할지 결정
Load Balancer 같은 서비스의 여러 인스턴스 중 요청을 보낼 대상을 선택
API Gateway 외부 요청을 받아 해당 서비스로 전달하는 공통 진입점
server.port: 0 실행할 때 사용 가능한 포트를 자동으로 할당받는 설정
eureka.instance.instance-id Eureka에서 같은 서비스의 실행 인스턴스를 구별하는 식별자
@RestController / @RequestMapping / @GetMapping 응답 본문을 반환하는 컨트롤러 / 공통 경로 지정 / GET 요청 매핑
@RequestHeader 요청 헤더의 값을 메서드 매개변수에 연결. 기본적으로 필수다.
Environment 실행 환경의 설정값을 읽는 객체. 예: env.getProperty("local.server.port")

오늘 배운 것

Maven 프로젝트와 빌드 단계

pom.xml은 프로젝트 정보와 의존성, 빌드 설정을 담는다. groupId는 보통 소유한 도메인을 뒤집은 형태로 정하며, test.com이라면 com.test처럼 쓸 수 있다.

명령 역할 대표 결과
mvn clean 기존 빌드 산출물을 삭제한다. 기본 출력 폴더인 target 정리
mvn compile 메인 소스를 컴파일한다. target/classes에 클래스 파일 생성
mvn package 컴파일·테스트 등 앞선 단계를 거쳐 배포 형식으로 묶는다. JAR 프로젝트에서는 target에 JAR 생성

package는 앞선 컴파일 단계도 수행하므로 JAR 생성 전에 compile을 별도로 실행할 필요는 없다. spring-boot-maven-plugin을 사용하는 프로젝트에서는 실행 가능한 Spring Boot JAR로 패키징할 수 있다.

# PowerShell
# msa/user-service의 pom.xml이 있는 폴더에서 실행한다.
# 기존 산출물을 지운 뒤 컴파일·테스트·패키징을 진행한다.
mvn clean package
# 성공하면 target/user-service-0.0.1-SNAPSHOT.jar가 생성된다.

Java 소스를 어느 버전 기준으로 컴파일할지 정한 설정과 실제 JDK가 서로 맞아야 한다. Spring Boot와 Spring Cloud 역시 서로 호환되는 버전 조합으로 구성해야 한다.

Service Discovery, Load Balancer, API Gateway의 역할

서비스가 다른 서비스를 호출하려면 대상의 주소가 필요하다. 인스턴스가 늘어나거나 주소가 바뀔 때마다 호출 코드에 주소를 직접 적으면 관리하기 어려우므로, Eureka에 등록된 정보를 이용해 필요한 서비스의 위치를 찾는다.

구성 요소 하는 일 요청 흐름에서의 역할
Eureka 서비스 인스턴스 정보를 등록하고 조회할 수 있게 한다. 호출할 서비스의 위치 정보를 제공한다.
Load Balancer 여러 인스턴스 중 요청 대상을 선택한다. 같은 서비스의 인스턴스들에 요청을 분산한다.
API Gateway 공통 진입점에서 요청을 분석하고 라우팅한다. 외부 요청을 해당 서비스로 전달한다.

서비스 등록과 실제 요청 전달은 서로 다른 역할이다. Gateway가 Eureka의 서비스 정보를 활용해 라우팅하는 구성을 배웠으며, 오늘 확인한 new-toy-msa에서는 각 서비스 포트로 직접 접속해 응답을 확인했다.

Eureka 서버와 클라이언트 구성

Eureka 서버는 등록 정보를 보관하고, 클라이언트는 자신의 실행 정보를 등록하거나 다른 서비스 정보를 조회한다. 서버에는 Eureka 서버 starter와 @EnableEurekaServer를 사용하고, 클라이언트에는 Eureka 클라이언트 starter와 서버 주소를 설정한다.

설정 독립 실행하는 실습 서버 실습 클라이언트
register-with-eureka false: 자신을 등록하지 않는다. true: 자신의 정보를 등록한다.
fetch-registry false: 다른 등록 정보를 조회하지 않는다. true: 레지스트리 정보를 조회한다.

이번 서버는 server.port를 8761로 지정했다. 서버 실행 후 http://localhost:8761에서 대시보드에 접근하며, 클라이언트의 eureka.client.service-url.defaultZone에는 등록 API 주소를 지정한다.

# YAML
# 클라이언트가 등록·조회 요청을 보낼 Eureka 서버 주소다.
# 서비스 자체의 HTTP 요청을 받는 포트와는 구분한다.
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/

직접 작성한 클라이언트에는 @EnableDiscoveryClient가 있다. Eureka 클라이언트 starter가 있으면 자동 구성으로 등록할 수 있으므로 준비용 프로젝트의 클라이언트에는 이 어노테이션이 없어도 된다.

같은 서비스를 여러 인스턴스로 실행하기

같은 서비스를 여러 프로세스로 실행하는 것은 인스턴스를 늘리는 것이다. 같은 컴퓨터에서는 각 프로세스가 서로 다른 포트를 사용해야 한다. IntelliJ의 VM 옵션에는 -Dserver.port=60001처럼 지정하고, 터미널에서도 JVM 옵션으로 포트를 바꿀 수 있다.

# PowerShell
# msa/user-service의 pom.xml이 있는 폴더에서 실행한다.
# Maven 실행 목표를 통해 애플리케이션을 60002번 포트로 시작한다.
mvn spring-boot:run "-Dspring-boot.run.jvmArguments=-Dserver.port=60002"

# 다른 터미널에서 msa/user-service/target 폴더로 이동한다.
# 이미 생성된 JAR를 60003번 포트로 시작한다. JVM 옵션은 -jar 앞에 둔다.
java "-Dserver.port=60003" -jar .\user-service-0.0.1-SNAPSHOT.jar
# 각각 정상 시작하면 지정한 서로 다른 포트로 요청을 받을 수 있다.

매번 포트를 지정하는 대신 server.port: 0으로 사용 가능한 포트를 자동 할당받을 수 있다. 이때 실제 서버가 사용하는 포트는 실행 시 결정되며, 여러 프로세스가 모두 0번 포트에서 요청을 받는 것은 아니다.

Eureka에서는 포트뿐 아니라 인스턴스 ID도 구별되어야 한다. ${spring.application.instance_id:${random.value}}는 지정한 인스턴스 ID를 우선 사용하고, 없으면 랜덤 값을 사용한다. 서비스 이름과 이 값을 연결하면 같은 서비스의 실행 인스턴스를 구별할 수 있다.

컨트롤러 경로와 필수 요청 헤더

@RestController에서 반환한 문자열은 응답 본문으로 전달된다. 접속 경로는 클래스의 @RequestMapping과 메서드의 @GetMapping을 합쳐 결정하며, 서버의 포트까지 맞춰 요청해야 한다.

// Java
@RestController
@RequestMapping("/demo")
class DemoController {
    @GetMapping("/echo")
    public String echo(@RequestHeader("X-Example") String value) {
        // GET /demo/echo의 X-Example 헤더 값을 응답 본문으로 돌려준다.
        // 헤더가 hello이면 응답은 hello이고, 헤더가 없으면 기본적으로 400이다.
        return value;
    }
}

브라우저 주소창만으로는 컨트롤러가 요구하는 임의의 요청 헤더를 추가할 수 없다. 필수 헤더를 받는 API는 Postman 등의 요청 도구에서 헤더를 넣어 확인한다. 헤더를 보내지 않으면 컨트롤러 메서드 실행 전에 요청이 거절될 수 있다.

오늘의 코드 1 - Maven 프로젝트 정보와 실행 JAR 빌드 설정

pom.xml

<!-- XML -->
<groupId>com.example</groupId>
<artifactId>helloworld</artifactId>
<version>1.0-SNAPSHOT</version>

<build>
    <plugins>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
        </plugin>
    </plugins>
</build>

 

helloworld 프로젝트에서 Maven 좌표와 Spring Boot 빌드 플러그인을 설정했다. 좌표는 프로젝트를 식별하고, 플러그인은 Spring Boot 실행과 실행 가능한 JAR 패키징에 사용된다.

오늘의 코드 2 - Eureka 서버 시작과 독립 실행 설정

ServiceDiscoveryApplication.java

// Java
@SpringBootApplication
@EnableEurekaServer
public class ServiceDiscoveryApplication {
    public static void main(String[] args) {
        SpringApplication.run(ServiceDiscoveryApplication.class, args);
    }
}

 

직접 작성한 service-discovery의 시작 클래스에서 Eureka 서버 기능을 활성화했다. main에서 Spring Boot 애플리케이션을 시작하면 서버 구성과 함께 실행된다.

application.yaml

# YAML
server:
  port: 8761

spring:
  application:
    name: service-discovery

eureka:
  client:
    register-with-eureka: false
    fetch-registry: false

 

실습 서버를 8761번 포트로 구성하고, 자신을 클라이언트로 등록하거나 다른 레지스트리를 조회하는 동작을 껐다. 독립 실행하는 등록 서버에 맞춘 설정이다.

오늘의 코드 3 - Eureka 클라이언트 활성화와 등록·조회 설정

UserServiceApplication.java

// Java
@SpringBootApplication
@EnableDiscoveryClient
public class UserServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(UserServiceApplication.class, args);
    }
}

 

직접 작성한 user-service에는 서비스 발견 클라이언트를 나타내는 @EnableDiscoveryClient를 적용했다. 프로젝트의 Eureka 클라이언트 의존성과 설정을 함께 사용한다.

application.yml

# YAML
eureka:
  client:
    service-url:
      defaultZone: http://127.0.0.1:8761/eureka
    fetch-registry: true
    register-with-eureka: true

 

준비용 new-toy-msa의 user-service에서는 등록 서버 주소와 등록·조회 설정을 확인했다. 두 값을 true로 지정하여 자신의 정보를 등록하고 레지스트리도 조회하도록 구성한다.

오늘의 코드 4 - 랜덤 포트와 고유 인스턴스 ID

application.yaml

# YAML
server:
  port: 0

spring:
  application:
    name: user-service

eureka:
  instance:
    instance-id: ${spring.application.name}:${spring.application.instance_id:${random.value}}

 

직접 작성한 user-service에서 포트를 자동 할당받고 인스턴스 ID에는 서비스 이름과 구별 가능한 값을 사용하도록 설정했다. 명시적인 인스턴스 ID가 없으면 랜덤 값을 사용하므로 같은 서비스를 여러 개 실행할 때 등록 ID의 충돌을 피하는 데 도움이 된다.

오늘의 코드 5 - 서비스별 GET 엔드포인트

FirstServiceController.java

// Java
@RestController
@RequestMapping("/first-service")
@Slf4j
public class FirstServiceController {
    @GetMapping("/welcome")
    public String welcome() {
        return "Welcome to the First service.";
    }
}

 

준비용 first-service에서 공통 경로와 메서드 경로를 조합한 http://localhost:8081/first-service/welcome으로 요청했다. 실제 요청으로 HTTP 200과 반환 문자열을 확인했다.

SecondServiceController.java

// Java
@RestController
@RequestMapping("/second-service")
@Slf4j
public class SecondServiceController {
    @GetMapping("/welcome")
    public String welcome() {
        return "Welcome to the Second service.";
    }
}

 

준비용 second-service의 접속 주소는 http://localhost:8082/second-service/welcome이다. 해당 요청도 HTTP 200과 반환 문자열을 확인했다.

오늘의 코드 6 - 요청 헤더를 받는 컨트롤러 메서드

FirstServiceController.java

// Java
@GetMapping("/message")
public String message(@RequestHeader("f-request") String header) {
    log.info(header);
    return "Hello World in First Service.";
}

 

first-service의 /message는 f-request 헤더를 받아 로그로 남긴다. 헤더 없이 요청하면 400이고, f-request: test를 넣으면 200과 응답 문자열이 반환되는 것을 확인했다.

SecondServiceController.java

// Java
@GetMapping("/message")
public String message(@RequestHeader("s-request") String header) {
    log.info(header);
    return "Hello World in Second Service.";
}

 

second-service는 같은 역할의 메서드에서 s-request 헤더를 요구한다. 이 서비스도 헤더가 없으면 400, s-request: test를 넣으면 200으로 응답하는 것을 확인했다.

오늘의 코드 7 - 실제로 실행 중인 서버 포트 확인

FirstServiceController.java

// Java
@GetMapping("/check")
public String check(HttpServletRequest request) {
    log.info("Server port={}", request.getServerPort());

    return String.format("Hi, there. This is a message from First Service on PORT %s"
            , env.getProperty("local.server.port"));
}

 

요청 객체의 getServerPort()로 요청을 받은 포트를 로그에 남기고, Environment의 local.server.port를 응답에 넣는다. 실제 요청에서 PORT 8081이 포함된 응답을 확인했다.

어려웠던 점 / 각종 오류

준비용 프로젝트를 실행할 때 IntelliJ의 서비스 모듈 컴파일 대상은 Java 21인데 사용하는 JDK는 17이라 빌드가 중단되었다. 로그의 Target bytecode version 21 is not supported by SDK 17을 확인했고, pom.xml의 Java 17 설정과 IDE의 SDK·언어 수준·바이트코드 대상도 함께 맞춰야 한다는 점을 배웠다.

컨트롤러에 접속할 때는 포트와 공통 경로, 메서드 경로를 모두 확인해야 했다. /welcome과 /check는 정상 응답했으며, /message는 필수 헤더 없이 요청하면 400 Bad Request가 발생했다. 각 서비스가 요구하는 헤더를 넣은 요청에서는 200 응답을 확인했다.

수업 메모에서는 같은 서비스를 랜덤 포트로 여러 개 실행했을 때 Eureka 대시보드에 인스턴스가 하나만 표시된 상황을 기록했다. 실행 포트의 자동 할당과 등록 ID의 고유성은 별개이므로, 포트는 자동 할당받더라도 인스턴스 ID는 각 실행을 구별할 수 있도록 설정해야 한다.

IntelliJ에서 강의 화면처럼 실행 구성을 복사하는 방법을 찾기 어려워 각 실행 구성을 직접 설정했다. 같은 애플리케이션에 서로 다른 -Dserver.port VM 옵션을 지정해 실행하는 흐름을 정리했다.
