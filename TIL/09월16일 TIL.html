오늘의 한 줄 요약

  • ChatClient로 시스템·사용자 프롬프트를 구성하고 문자열 또는 DTO 형태로 AI 응답을 받는 흐름을 정리했다.
  • AI Agent가 @Tool 메서드를 선택해 기존 서비스와 저장소를 호출하도록 역할을 분리했다.
  • 데이터 변경은 AI가 바로 저장하지 않고 초안 생성과 사용자 확정 단계로 나누는 안전한 흐름을 학습했다.
  • RAG·Vector DB·MCP의 관계와 백엔드가 외부 Open API를 대신 호출하는 이유를 연결했다.

오늘 배운 것

ChatClient 요청과 응답 변환

ChatClient는 모델 연결 설정을 재사용하면서 요청마다 시스템 프롬프트와 사용자 프롬프트를 조합한다. 응답을 글로 사용할 때는 .content(), 정해진 필드가 필요한 때는 .entity()를 선택한다.

응답 방식알맞은 상황
.content()블로그 본문처럼 자유로운 텍스트가 필요할 때
.entity(DTO.class)맛집 목록이나 퀴즈처럼 필드 구조가 정해진 결과가 필요할 때
 
// Java: 같은 호출 흐름에서 필요한 반환 형태만 선택한다.
String text = chatClient.prompt()
    .system("짧고 명확하게 답해줘.")
    .user("REST API를 한 문장으로 설명해줘.")
    .call()
    .content(); // 결과: 생성된 일반 문자열

Controller, Agent, Tool, Service의 역할 분리

기존 흐름에서는 Controller가 Service의 정해진 메서드를 직접 호출한다. Agent 흐름에서는 Controller가 Agent에게 목표를 전달하고, Agent가 프롬프트 규칙에 따라 필요한 Tool을 고른다. Tool은 새 비즈니스 로직을 중복 작성하지 않고 기존 Service를 호출한다.

구성 요소역할
ControllerHTTP 요청을 받고 Agent에 입력을 전달한다.
Agent작업 규칙을 모델에 전달하고 도구 사용 여부를 판단하게 한다.
Tool모델이 호출할 수 있는 구체적인 Java 작업을 제공한다.
Service / Repository검증된 비즈니스 로직과 데이터 조회·저장을 담당한다.
 
// Java: Tool은 기존 서비스 호출을 얇게 감싼다.
@Tool(description = "카테고리와 키워드로 기존 글을 검색한다.")
public List<BlogResponseDTO> search(String category, String keyword) {
    return blogService.searchByKeyword(category, keyword);
} // Agent가 필요하다고 판단할 때 이 메서드를 호출한다.

데이터 변경을 위한 Draft와 Confirm 분리

AI가 생성과 저장을 한 요청에서 모두 처리하면 중복 게시나 의도하지 않은 변경이 생길 수 있다. 초안 요청은 검색과 생성만 수행하고, 사용자가 결과를 확인한 뒤 기존 저장 API를 호출하도록 나누면 변경 시점을 명확하게 통제할 수 있다.

// Java: 초안 생성은 문자열만 반환하고 DB 저장 메서드는 호출하지 않는다.
String draft = agent.generate(category, keyword);
// 사용자가 draft를 검토한 뒤 별도의 게시 요청으로 저장을 확정한다.

RAG, Vector DB, MCP의 관계

LLM이 알지 못하는 내부 자료나 최신 자료가 필요하면 먼저 관련 문맥을 검색해 프롬프트에 추가할 수 있다. RAG는 이 전체 생성 방식이고, Vector DB는 의미가 비슷한 자료를 찾는 저장·검색 수단이며, MCP는 애플리케이션이 외부 도구와 데이터 원천을 연결하는 규약이다.

개념핵심 역할
RAG검색한 문맥을 모델 입력에 보강해 답변의 근거를 늘린다.
Vector DB임베딩 사이의 유사도를 이용해 관련 문서를 찾는다.
MCP로컬·원격 도구 및 데이터 서버를 AI 클라이언트와 연결한다.

백엔드 중심 외부 Open API 연동

서비스 키가 필요한 외부 API는 브라우저에서 직접 호출하지 않고 백엔드가 대신 호출한다. 백엔드는 URL을 만들고 상태 코드를 확인한 뒤 UTF-8 문자 스트림으로 응답을 읽으며, 필요한 JSON 노드만 DTO로 변환해 프런트엔드에 반환한다.

// Java: 쿼리 매개변수를 문자열 연결 대신 빌더로 조립한다.
String requestUrl = UriComponentsBuilder.fromUriString(endPoint)
    .queryParam("serviceKey", key)
    .queryParam("base_date", baseDate)
    .queryParam("dataType", "JSON")
    .toUriString(); // 결과: 요청에 사용할 URL 문자열

외부 응답은 먼저 HTTP 상태를 확인하고, InputStreamReader와 BufferedReader로 문자열을 만든다. 이후 ObjectMapper.readTree()로 JSON 트리를 만들고 필요한 배열 노드를 DTO 목록으로 변환한다.

오늘의 코드 1 - ChatClient로 구조화된 응답 받기

OpenAiService.java

RecommandResponseDTO result = chatClient
    .prompt()
    .system("전처리된 json 형태로만 반환해줘.")
    .user("""
        현재 날씨와 지역에 맞는 맛집을 추천해줘.
        날씨: "%s"
        위치: "%s"
        """.formatted(weather, location))
    .call()
    .entity(RecommandResponseDTO.class);

return result;

모델의 역할과 출력 제약은 system, 실제 날씨와 지역은 user 프롬프트로 분리했다. 호출 결과를 문자열로 다시 파싱하지 않고 RecommandResponseDTO로 바로 변환하는 흐름을 확인했다.

오늘의 코드 2 - 로컬 메서드를 AI Tool로 공개

BlogAITool.java

@Tool(description = "주어진 카테고리와 키워드로 이미 작성된 블로그 게시글이 있는지 검색한다.")
public List<BlogResponseDTO> searchBlogKeyword(Map<String, Object> map) {
    List<BlogResponseDTO> list = blogService.searchByKeyword(map);
    return list;
}

@Tool의 설명은 모델이 이 메서드를 언제 사용해야 하는지 판단하는 근거가 된다. Tool 자체는 검색 로직을 다시 만들지 않고 기존 BlogService에 입력을 넘겨 결과를 반환한다.

오늘의 코드 3 - Agent 전용 ChatClient에 Tool 등록

BlogAIAgentConfig.java

@Bean
public ChatClient blogChatClient(ChatClient.Builder builder,
                                 BlogAITool blogAITool,
                                 ObjectProvider<ToolCallbackProvider> objectProvider) {
    builder = builder.defaultTools(blogAITool);
    return builder.build();
}

ChatClient.Builder에 BlogAITool을 기본 도구로 등록한 뒤 블로그 Agent가 사용할 클라이언트를 생성했다. 외부 MCP 도구 연결 객체도 매개변수로 받을 수 있는 구조지만, 확인된 실행 코드에서는 로컬 Tool만 등록했다.

오늘의 코드 4 - 검색 Tool을 사용하는 블로그 초안 Agent

BlogAIAgent.java

public String generate(Map<String, Object> map) {
    String systemPrompt = """
        당신은 SEO를 고려한 블로그 작성 에이전트입니다.
        - searchBlogKeyword로 중복 여부를 확인합니다.
        - 본문은 300자 이내로 작성합니다.
        - 결과만 반환하고 저장하지 않습니다.
        """;
    String userPrompt = "%s와 %s를 기반으로 글을 작성하고 저장하지 말고 반환만 해줘."
        .formatted(map.get("category"), map.get("keyword"));

    return blogChatClient.prompt()
        .system(systemPrompt)
        .user(userPrompt)
        .call()
        .content();
}

카테고리와 키워드를 동적 입력으로 전달하고, 중복 검색과 초안 반환 규칙을 시스템 프롬프트에 넣었다. 이 메서드는 결과를 문자열로 돌려주며 데이터베이스 저장은 수행하지 않는다.

오늘의 코드 5 - 기존 글 검색 결과를 Tool에 전달

BlogRepository.java

@Query("""
    SELECT b
    FROM BlogEntity b
    WHERE LOWER(b.content) LIKE LOWER(CONCAT('%', :content, '%'))
      AND b.category = :category
    """)
List<BlogEntity> findByContentAndCategory(@Param("content") String content,
                                           @Param("category") String category);

본문에는 키워드가 포함되고 카테고리는 일치하는 게시물을 조회한다. 대소문자 차이를 줄이기 위해 본문과 검색어 양쪽에 LOWER()를 적용했다.

BlogService.java

public List<BlogResponseDTO> searchByKeyword(Map<String, Object> map) {
    return blogRepository
        .findByContentAndCategory((String) map.get("keyword"),
                                  (String) map.get("category"))
        .stream()
        .map(BlogResponseDTO::fromEntity)
        .toList();
}

Tool에서 받은 카테고리와 키워드로 저장소를 조회하고 JPA 엔티티 목록을 응답 DTO 목록으로 변환한다. 이 결과가 Agent로 돌아가면 모델은 기존 글의 존재 여부를 반영해 답변을 생성할 수 있다.
