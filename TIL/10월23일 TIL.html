오늘 배운 것

컨테이너 프로세스와 로그 확인

컨테이너의 실행 상태를 살펴볼 때는 프로세스와 로그를 각각 확인한다. 이미지 목록에서는 식별자가 생략되는지도 구분할 수 있다.

명령어확인하는 내용
docker top지정한 컨테이너에서 실행 중인 프로세스
docker logs컨테이너의 표준 출력·표준 오류로 수집된 로그
docker logs -f기존 로그를 표시하고 이후에 추가되는 로그를 계속 확인
docker images --no-trunc이미지 목록의 ID 등을 축약하지 않고 표시

Apache와 Nginx 웹 서버 이미지 구성

웹 서버 이미지는 기본 이미지에 서버 프로그램과 웹 문서를 준비하고, 컨테이너 시작 시 서버를 실행하도록 구성한다. 수업 메모에서는 Ubuntu에 Apache를 설치하는 방식과 Nginx 이미지를 바탕으로 웹 문서를 교체하는 방식을 비교했다.

구분Apache 구성Nginx 구성
기본 이미지ubuntu:22.04nginx:1.14
서버 준비RUN에서 패키지 목록을 갱신하고 apache2 설치기본 이미지에 포함된 Nginx 사용
웹 문서 복사 대상/var/www/html/index.html/usr/share/nginx/html/index.html
서버 실행apache2ctl의 FOREGROUND로 실행nginx의 daemon off; 설정으로 실행
이미지 이름과 태그httpdweb:v1.0nginxweb:v1.0

FROM은 기본 이미지를 선택하고, RUN은 빌드 중 명령을 실행하며, COPY는 준비한 웹 문서를 이미지에 넣는다. CMD는 컨테이너 시작 시 실행할 기본 명령을 지정한다. 두 구성 모두 웹 서버가 포그라운드에서 실행되도록 설정했다.

메모의 빌드 명령인 docker build -t httpdweb:v1.0 .과 docker build -t nginxweb:v1.0 .에서 마지막 .은 현재 디렉터리를 빌드 컨텍스트로 지정한다. 메모에서는 Nginx 기반 이미지가 더 작았다고 기록했으며, 크기 차이는 각 기본 이미지와 추가로 포함한 패키지·파일 구성을 함께 보고 비교한다.

호스트 인터페이스와 Docker 네트워크 방식

수업에서 살펴본 ens5는 EC2 호스트의 네트워크 인터페이스이고, docker0는 Docker 기본 브리지의 인터페이스다. 브리지 네트워크에는 컨테이너의 가상 인터페이스가 연결되므로, 네트워크 자체의 개수와 연결된 컨테이너 인터페이스의 개수는 구분해서 본다.

네트워크 방식동작
bridge컨테이너에 별도 IP를 할당하고 브리지로 연결한다. 같은 브리지의 컨테이너끼리 통신할 수 있다.
host호스트의 네트워크 공간을 공유하며 컨테이너 전용 IP를 할당하지 않는다. 호스트 포트를 직접 사용하므로 포트 매핑 옵션은 적용되지 않는다.
none루프백 인터페이스만 두어 외부 네트워크와 분리한다.

메모의 172.17.0.1은 기본 브리지 주소의 예시이며, 실제 주소 범위는 Docker 설정에 따라 달라진다. 컨테이너 IP는 연결한 네트워크의 주소 범위에서 할당되므로, 실행 순서로 추정하기보다 현재 할당된 값을 확인한다.

docker network ls는 네트워크 목록을, docker network inspect는 지정한 네트워크 이름이나 ID의 상세 정보를 보여준다. ifconfig는 인터페이스를, brctl show는 브리지와 그 브리지에 연결된 인터페이스를 확인하는 데 사용한다.

컨테이너 내부 포트와 호스트 포트 게시

브리지 네트워크에서는 호스트가 컨테이너의 내부 IP로 접근하는 경로와 외부에서 호스트 IP로 접근하는 경로가 다르다. 외부 요청을 컨테이너로 전달하려면 호스트 포트와 서버가 실제로 응답하는 컨테이너 포트를 연결한다.

설정의미
-p 80:80호스트 80번을 컨테이너 80번에 연결
-p에 컨테이너 포트만 지정호스트의 사용 가능한 포트를 자동 할당해 지정한 컨테이너 포트에 연결
-P이미지의 EXPOSE 등으로 노출된 포트들을 호스트의 자동 할당 포트에 연결
EXPOSE 80이미지의 사용 포트를 알리는 설정이며, 호스트 포트 게시는 별도로 지정

수업 메모의 iptables -t nat -L -n -v 결과에는 호스트 80번을 172.17.0.2:80으로, 32768번을 172.17.0.3:80으로 전달하는 규칙이 있었다. 이처럼 호스트에서 받은 요청의 목적지 주소와 포트를 컨테이너의 주소와 포트로 바꾸어 전달한다.

사용자 지정 브리지의 주소 범위와 고정 IP

사용자 지정 브리지는 애플리케이션이 사용할 네트워크와 주소 범위를 직접 정할 때 사용한다. 네트워크를 만든 뒤 컨테이너를 해당 네트워크에 연결하고, 필요하면 그 범위 안의 IP를 지정한다.

메모의 설정역할
mynetbridge 드라이버로 만드는 사용자 지정 네트워크 이름
--subnet 192.168.100.0/24컨테이너에 할당할 네트워크의 주소 범위
--gateway 192.168.100.254해당 네트워크의 게이트웨이 주소
--net mynetappjs 컨테이너를 연결할 네트워크 선택
--ip 192.168.100.100컨테이너에 지정할 내부 IP

네트워크 생성은 docker network create로 수행하고, 목록과 상세 정보에서 설정을 확인한다. 내부 IP 지정과 호스트 포트 게시의 역할은 서로 다르므로, 외부 접속 경로를 확인할 때는 포트 연결도 함께 살펴본다.

컨테이너 변경 저장과 이미지 보관 방식 비교

컨테이너의 변경 상태를 이미지로 남기는 작업, 컨테이너 파일 시스템을 내보내는 작업, 기존 이미지를 보관하는 작업은 저장 대상이 다르다. 무엇을 다시 사용할 것인지에 따라 명령을 선택한다.

방법저장 대상과 결과메모의 명령
commit기존 이미지에 컨테이너의 파일 변경·설정을 반영해 새 이미지 생성. 마운트된 볼륨 데이터는 제외한다.docker commit web nginx1.14
export → import컨테이너 파일 시스템을 tar 파일로 보관하고 새 이미지 생성. 볼륨 데이터와 원래 이미지의 레이어 이력·실행 설정은 함께 보존되지 않는다.docker export -o nginx:1.14.tar nc
docker import nginx:1.14.tar new_nginx
save → load이미지를 레이어·설정·지정한 태그와 함께 tar 파일로 보관하고 복원docker save -o nginx.tar nginx:1.14
docker load -i nginx.tar

export와 save의 기본 결과는 여러 내용을 담는 tar 아카이브다. 파일 크기를 줄이는 압축은 별도로 적용할 수 있다.

import한 이미지에 기본 실행 명령이 없다면 docker run의 이미지 이름 뒤에 실행할 명령과 인자를 지정하거나, 가져올 때 --change로 CMD·ENTRYPOINT 같은 설정을 추가한다. -g는 Nginx 실행 명령의 인자로, 전역 설정을 전달할 때 사용한다.

최종 이미지 구성 줄이기와 빌드 캐시

이미지 경량화는 최종 이미지에 포함되는 파일과 패키지를 줄이는 데 초점을 둔다. 수업에서 살펴본 방법은 필요한 구성만 포함하기, 가벼운 기본 이미지 사용하기, 빌드 단계와 실행 단계를 나누기다.

  • 여러 명령을 &&로 연결하면 하나의 RUN에서 처리할 수 있다. 설치 중 생긴 불필요한 파일을 같은 단계에서 정리하면 해당 파일이 최종 레이어에 남는 것을 줄일 수 있다.
  • alpine처럼 작은 기본 이미지를 선택할 때는 실행에 필요한 구성과 호환되는지도 함께 확인한다.
  • 멀티 스테이지 빌드는 여러 FROM으로 단계를 나누고, 앞 단계의 결과물 중 실행에 필요한 것만 마지막 단계로 가져온다. 빌드 도구와 중간 산출물을 최종 이미지에서 제외할 수 있다.

--no-cache는 기존 빌드 캐시를 재사용하지 않고 명령을 다시 실행하도록 하는 옵션이다. 최종 이미지 크기는 포함된 파일과 패키지에 의해 결정되므로, 캐시 재사용 여부와 이미지 경량화는 역할을 구분해서 이해한다.

어려웠던 점 / 각종 오류

EC2 안에서 curl 192.168.100.100을 실행하면 Marvel 페이지의 HTML을 확인할 수 있었지만, 외부 IP로 접속했을 때는 Nginx 기본 화면이 보였다. 포트를 생략한 HTTP 요청은 80번을 사용하므로, 내부 요청은 192.168.100.100:80에 대한 응답을 확인한 것이다.

sudo ss -lntp 'sport = :80'의 결과에는 80번 수신 소켓이 표시되지 않았다. 이어서 확인한 docker ps 출력에서 appjs의 포트 정보는 다음과 같았다.

실제 표시된 값의미
80/tcp컨테이너의 80번 포트 표시. 호스트 포트와의 연결은 표시되지 않았다.
0.0.0.0:8080->8080/tcp호스트의 IPv4 8080번을 컨테이너 8080번에 연결
[::]:8080->8080/tcp호스트의 IPv6 8080번을 컨테이너 8080번에 연결

확인된 포트 연결은 호스트 8080번에서 컨테이너 8080번으로 향하고 있었다. 내부에서 응답한 80번 서비스로 호스트 8080번의 요청을 전달하려면 -p 8080:80처럼 대상 포트를 맞춰야 한다. 내부 IP에서 응답을 받은 사실과 외부 IP로 원하는 페이지에 도달하는 사실을 구분하고, PORTS의 호스트·컨테이너 포트를 함께 읽는 것이 핵심이었다.

외부에서 보인 Nginx 기본 화면의 응답 출처, 실행 중인 appjs의 내부 IP 일치 여부, 포트 설정을 바꾼 뒤의 접속 결과는 추가로 확인되지 않았다.
