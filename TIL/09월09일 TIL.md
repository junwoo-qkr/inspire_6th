# 제목: JWT 인증 필터와 JPA 게시글·댓글 처리

## 오늘의 한 줄 요약

- 외부 설정에서 JWT 비밀 키를 주입하고, `JwtProvider`에서 Access Token과 Refresh Token을 생성·검증하는 구조를 구성했다.
- `JwtFilter`에서 CORS 사전 요청, 인증 제외 경로, Bearer 토큰 검증을 순서대로 처리하는 흐름을 학습했다.
- `doFilter()`가 현재 필터에서 다음 필터 또는 DispatcherServlet으로 요청을 전달하는 방식을 이해했다.
- 요청 DTO를 연관 Entity와 연결해 저장하고, 조회한 Entity를 응답 DTO로 변환했다.
- JPQL의 `LEFT JOIN FETCH`로 게시글과 댓글을 함께 조회하고, 댓글을 응답 DTO에 담는 변환 메서드를 구성했다.
- 트랜잭션 안에서 관리 중인 Entity의 필드를 변경하면 Dirty Checking을 통해 DB에 수정 내용이 반영되는 원리를 학습했다.

## 키워드 정리

| 키워드               | 설명                                                                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JPA / Hibernate   | JPA는 자바 객체와 관계형 데이터베이스를 매핑하기 위한 표준 명세이고, Hibernate는 JPA를 구현한 ORM 프레임워크다. Entity의 상태를 영속성 컨텍스트에서 관리하며 조회·저장·수정·삭제 작업을 수행한다.                                                              |
| Flyway            | 데이터베이스 스키마 변경을 버전이 있는 마이그레이션 파일로 관리한다. 각 마이그레이션의 적용 여부를 DB에 기록해 여러 환경에서 동일한 스키마 변경 순서를 유지한다.                                                                                            |
| JWT               | Header, Payload, Signature로 구성된 문자열 토큰이다. Payload에는 사용자 식별 정보와 발급·만료 시각 같은 Claim을 담고, Signature는 토큰이 발급 이후 변조되지 않았는지 확인하는 데 사용한다. Payload는 암호화가 아니라 인코딩된 값이므로 비밀번호 같은 민감한 정보를 넣으면 안 된다. |
| `JwtProvider`     | JWT 생성과 검증에 필요한 공통 기능을 담당하는 클래스다. 비밀 키를 준비하고, 사용자 정보를 Claim에 넣어 Access·Refresh Token을 발급하며, 전달받은 토큰의 서명과 만료 여부를 검증한다.                                                                   |
| `JwtFilter`       | HTTP 요청이 Controller에 도달하기 전에 Authorization 헤더를 확인하고 JWT를 검증하는 Servlet Filter다. CORS 사전 요청과 인증 제외 경로를 먼저 처리한 뒤 보호된 경로의 토큰을 검사한다.                                                         |
| `@Value`          | Spring의 외부 설정값을 Bean의 필드나 생성자 매개변수에 주입하는 애노테이션이다. `@Value("${jwt.secret}")`는 `jwt.secret` 설정값을 읽어 필드에 넣는다.                                                                              |
| `@PostConstruct`  | 객체 생성과 의존성 주입이 끝난 직후 한 번 실행되는 초기화 메서드를 지정한다. 문자열 형태의 비밀 키를 JWT 라이브러리가 사용할 `Key` 객체로 변환하는 작업에 적합하다.                                                                                      |
| HMAC 키            | 하나의 비밀 키를 사용해 서명과 검증을 수행하는 대칭 키 방식의 키다. 토큰을 발급하는 서버와 검증하는 서버가 같은 비밀 키를 안전하게 공유해야 한다.                                                                                                    |
| Bearer 인증         | `Authorization` 헤더에 `Bearer ` 접두사와 토큰을 함께 전달하는 인증 방식이다. 필터는 접두사를 확인한 뒤 실제 JWT 문자열만 분리해 검증한다.                                                                                            |
| Preflight         | 브라우저가 실제 교차 출처 요청을 보내기 전에 OPTIONS 메서드로 서버에 허용 여부를 확인하는 요청이다. Authorization 같은 사용자 정의 헤더를 사용할 때 자주 발생한다.                                                                                 |
| FilterChain       | 여러 Servlet Filter와 최종 서블릿을 연결한 실행 구조다. 현재 필터가 `chain.doFilter()`를 호출하면 다음 필터가 실행되고, 더 이상 필터가 없으면 DispatcherServlet 또는 대상 서블릿으로 요청이 전달된다.                                                |
| `doFilter()`      | 현재 필터의 요청 처리 지점이다. 필터가 직접 응답을 종료하지 않고 `chain.doFilter(request, response)`를 호출하면 다음 처리 단계로 넘어간다. 호출하지 않으면 현재 필터에서 요청 흐름이 멈춘다.                                                            |
| 경로 패턴 매칭          | `/user/**`처럼 여러 URL을 하나의 패턴으로 표현하고 실제 요청 경로와 비교하는 방식이다. 인증 제외 경로를 관리할 때 사용한다.                                                                                                           |
| `anyMatch()`      | Stream의 요소 중 조건을 만족하는 값이 하나라도 있으면 `true`를 반환한다. 허용 목록의 패턴 중 현재 요청 경로와 일치하는 패턴이 있는지 확인하는 데 사용한다.                                                                                         |
| `JpaRepository`   | Entity 타입과 기본 키 타입을 지정하면 저장·조회·삭제·수정에 필요한 기본 메서드를 제공하는 Spring Data JPA 인터페이스다.                                                                                                          |
| DTO 변환            | 외부 요청·응답 형식과 DB Entity를 분리하는 과정이다. RequestDTO는 입력값을 Entity로 만들고, ResponseDTO는 Entity에서 외부에 전달할 값만 추출한다.                                                                                 |
| `Optional`        | 조회 결과가 없을 수 있음을 표현하는 컨테이너다. `orElseThrow()`로 결과가 없을 때 예외를 발생시키고, `map()`으로 값이 있을 때만 변환할 수 있다.                                                                                           |
| Stream과 메서드 참조    | 컬렉션을 선언적인 방식으로 처리하는 기능이다. `BlogResponseDTO::fromEntity`는 Entity를 DTO로 변환하는 메서드를 Stream의 `map()`에 전달하는 표현이다.                                                                             |
| JPQL / Fetch Join | JPQL은 테이블이 아니라 Entity와 Entity 필드를 기준으로 작성하는 객체 지향 쿼리다. Fetch Join은 연관 Entity를 조회 시점에 함께 로딩해 별도의 지연 로딩 조회를 줄인다.                                                                          |
| `@Transactional`  | 메서드 실행을 하나의 트랜잭션으로 묶는다. 트랜잭션 안에서 조회한 Entity는 영속성 컨텍스트의 관리 대상이 되며, 커밋 시 변경 사항이 반영될 수 있다.                                                                                                 |
| Dirty Checking    | 영속성 컨텍스트가 처음 조회한 Entity의 상태와 현재 상태를 비교해 변경 여부를 감지하는 기능이다. 관리 중인 Entity의 필드를 변경하면 별도의 `save()` 없이도 flush 시 UPDATE가 실행될 수 있다.                                                             |
| Axios 요청 설정       | Axios에서 GET은 두 번째 인수에 설정 객체를 전달하고, POST는 두 번째 인수에 요청 본문, 세 번째 인수에 설정 객체를 전달한다. 인증 헤더는 반드시 설정 객체의 `headers`에 넣어야 한다.                                                                     |
| Promise 오류 콜백     | 비동기 요청이 실패했을 때 실행할 함수를 `catch()`에 전달하는 방식이다. 오류 객체를 출력하거나 사용자에게 실패 메시지를 보여줄 수 있다.                                                                                                       |

## 오늘 배운 것

### 웹 요청을 처리하는 구성 요소와 데이터 접근 도구

- Tomcat은 서블릿을 실행하는 웹 컨테이너이며, Catalina는 서블릿 컨테이너, Jasper는 JSP 엔진이다. Spring MVC의 DispatcherServlet은 요청을 받아 알맞은 Controller로 연결한다. 데이터 접근에서는 JPA와 Hibernate로 Entity를 관리하고, Flyway는 DB 스키마 변경 이력을 관리한다.

| 구성 요소             | 역할과 적용 위치                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| Servlet Filter    | DispatcherServlet이나 Controller가 실행되기 전에 요청을 가로채 공통 검증과 전처리를 수행한다. JWT 인증 필터는 Authorization 헤더를 검사하는 위치에 해당한다. |
| DispatcherServlet | Spring MVC의 진입점이다. Filter를 통과한 요청을 HandlerMapping으로 적절한 Controller 메서드에 연결한다.                                 |
| Interceptor       | Spring MVC가 Controller를 호출하기 전후에 실행된다. Filter보다 Spring MVC와 Controller에 가까운 위치에서 동작한다.                        |
| AOP               | Spring Bean의 메서드 호출 전후에 로깅, 트랜잭션, 권한 검사 같은 공통 관심사를 적용한다.                                                      |
| JPA / Hibernate   | Entity와 테이블을 매핑하고, 영속성 컨텍스트를 통해 Entity의 상태와 DB 반영을 관리한다.                                                      |
| Flyway            | DB 구조 변경을 순서가 있는 마이그레이션으로 관리하고 적용 이력을 저장한다.                                                                   |

### 외부 설정 주입과 초기화 시점

- `application.yml`에서 `.env` 파일의 값을 읽어 `JWT_SECRET_KEY`를 `jwt.secret`에 연결한다. `@Value`는 설정값을 필드에 주입하고, `@PostConstruct`는 주입이 끝난 뒤 문자열 비밀 키를 JWT 라이브러리가 사용할 `Key` 객체로 변환한다.
- JWT 라이브러리는 단순 문자열보다 알고리즘에 맞는 `Key` 객체를 사용해 서명과 검증을 수행한다. 따라서 Provider와 Filter가 동일한 비밀 키를 사용해야 발급한 토큰을 검증할 수 있다.

```java
@Value("${jwt.secret}")
private String secret;

@PostConstruct
private void init() {
    key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
}
```

- `secret.getBytes(StandardCharsets.UTF_8)`는 문자열을 UTF-8 바이트 배열로 변환한다. `Keys.hmacShaKeyFor()`는 이 바이트 배열을 HMAC 알고리즘에 사용할 키로 만든다. 비밀 키가 너무 짧으면 라이브러리가 안전하지 않은 키로 판단해 예외를 발생시킬 수 있으므로 충분히 긴 값을 사용해야 한다.

### `JwtProvider`의 역할과 JWT 발급·검증 과정

`JwtProvider`는 JWT와 관련된 기능을 한곳에 모아 관리하는 클래스다. 일반적으로 다음과 같은 책임을 가진다.

1. 외부 설정에서 비밀 키를 읽는다.
2. 문자열 비밀 키를 서명용 `Key` 객체로 변환한다.
3. 사용자 식별 정보를 Claim에 넣어 Access Token을 생성한다.
4. 더 긴 만료 시간을 가진 Refresh Token을 생성한다.
5. 전달받은 토큰의 서명과 만료 시간을 검증한다.
6. 검증이 끝난 토큰에서 subject나 다른 Claim을 추출한다.

JWT 생성 시 Header에는 서명 알고리즘과 토큰 타입 같은 정보가 들어가고, Payload에는 `sub`, `iat`, `exp` 같은 Claim이 들어간다. 마지막 Signature는 Header와 Payload, 비밀 키를 이용해 생성된다. 서버는 같은 비밀 키로 Signature를 다시 계산해 토큰이 변조되지 않았는지 확인한다.

| 설정 메서드                    | 의미                                                               |
| ------------------------- | ---------------------------------------------------------------- |
| `setSubject(email)`       | Payload의 `sub` Claim에 사용자 이메일을 저장한다. 이후 인증된 사용자를 식별할 때 사용할 수 있다. |
| `setIssuedAt(new Date())` | 토큰이 발급된 시각을 `iat` Claim에 저장한다.                                   |
| `setExpiration(...)`      | 토큰이 더 이상 유효하지 않은 시각을 `exp` Claim에 저장한다.                          |
| `signWith(key)`           | 비밀 키를 사용해 Header와 Payload에 대한 서명을 생성한다.                          |
| `compact()`               | Header, Payload, Signature를 점으로 연결한 최종 JWT 문자열을 반환한다.            |

```java
long expiry = 1000L * 60 * 30;

String token = Jwts.builder()
    .setSubject(email)
    .setIssuedAt(new Date())
    .setExpiration(new Date(System.currentTimeMillis() + expiry))
    .signWith(key)
    .compact();
```

- Access Token은 API 요청마다 인증을 확인하는 데 사용하므로 비교적 짧은 만료 시간을 설정한다. Refresh Token은 Access Token이 만료되었을 때 새 Access Token을 발급받기 위한 용도이므로 더 긴 만료 시간을 설정한다.
- JWT의 Header와 Payload는 Base64URL 인코딩일 뿐 암호화가 아니다. 따라서 누구나 내용을 디코딩할 수 있으며, 비밀번호나 주민등록번호 같은 민감한 정보를 넣으면 안 된다.
- 서명 검증은 토큰의 무결성과 발급 주체를 확인하지만, 토큰 자체를 폐기하는 기능은 아니다. 로그아웃, 강제 만료, Refresh Token 재사용 방지 등이 필요하면 서버 저장소나 별도의 폐기 전략이 필요하다.

### JWT 검증 메서드의 작동 방식

JWT 검증은 단순히 토큰 문자열이 존재하는지 확인하는 과정이 아니다. 서버는 다음 항목을 확인한다.

1. 토큰 구조가 JWT 형식인지 확인한다.
2. 서버가 가진 비밀 키로 Signature를 검증한다.
3. 토큰의 `exp`가 현재 시각보다 이전인지 확인한다.
4. 검증이 성공하면 Payload의 Claim을 읽을 수 있다.
5. 검증에 실패하면 서명 오류, 만료 오류, 형식 오류 등이 발생한다.

```java
Jwts.parserBuilder()
    .setSigningKey(key)
    .build()
    .parseClaimsJws(token);
```

- `parserBuilder()`는 JWT 파서를 구성한다.
- `setSigningKey(key)`는 서명 검증에 사용할 비밀 키를 지정한다.
- `build()`는 설정이 완료된 파서를 생성한다.
- `parseClaimsJws(token)`은 전달받은 토큰을 파싱하고 서명과 만료 시간을 검증한다.
- 검증이 성공하면 Claims JWS가 반환되고, 실패하면 예외가 발생한다.

검증이 성공한 뒤에는 다음과 같이 subject를 추출할 수 있다.

```java
Claims claims = Jwts.parserBuilder()
    .setSigningKey(key)
    .build()
    .parseClaimsJws(token)
    .getBody();

String email = claims.getSubject();
```

현재 구조에서는 토큰 검증과 요청 사용자 식별을 연결하는 작업이 남아 있다. 단순히 토큰이 유효하다는 사실만 확인하는 것과, 토큰의 이메일을 이용해 실제 사용자 정보를 가져오는 것은 별도의 단계다.

### JWT 필터의 전체 실행 흐름

`JwtFilter`는 요청이 Controller에 도달하기 전에 실행된다. 일반적인 흐름은 다음과 같다.

1. 요청 메서드와 URI를 확인한다.
2. OPTIONS 요청이면 CORS 사전 요청으로 처리한다.
3. 허용 목록에 포함된 경로인지 확인한다.
4. 허용 경로가 아니면 Authorization 헤더를 읽는다.
5. `Bearer ` 접두사가 있는지 확인한다.
6. 접두사를 제거하고 JWT 문자열만 추출한다.
7. `JwtProvider` 또는 JWT 파서로 서명과 만료를 검증한다.
8. 검증이 성공하면 `chain.doFilter()`를 호출한다.
9. 헤더가 없거나 토큰이 잘못되면 401 응답을 설정하고 흐름을 종료한다.

필터는 Controller보다 앞에서 실행되므로 인증 실패 요청을 Controller까지 보내지 않을 수 있다. 반대로 필터에서 `chain.doFilter()`를 호출하지 않으면 다음 필터와 DispatcherServlet이 실행되지 않는다.

### `doFilter()`의 작동 방식

`doFilter()`는 현재 필터가 요청을 다음 처리 단계로 넘길지 결정하는 핵심 메서드다.

```java
chain.doFilter(request, response);
```

이 코드를 호출하면 다음과 같은 흐름이 이어진다.

- 다음 Filter가 등록되어 있으면 다음 Filter의 `doFilter()`가 실행된다.
- 다음 Filter가 없으면 DispatcherServlet 또는 대상 Servlet이 실행된다.
- 이후 Controller의 응답 처리가 끝나면 호출 스택을 따라 이전 필터로 돌아온다.
- 필터는 `chain.doFilter()` 전후에 요청 전처리와 응답 후처리를 작성할 수 있다.

예를 들어 필터가 세 개라면 흐름은 다음과 같다.

```text
Filter A 전처리
  -> Filter B 전처리
    -> Filter C 전처리
      -> DispatcherServlet
    <- Filter C 후처리
  <- Filter B 후처리
<- Filter A 후처리
```

따라서 `chain.doFilter()`는 단순한 메서드 호출이 아니라 필터 체인의 다음 단계로 실행 권한을 넘기는 동작이다.

반대로 다음과 같이 `chain.doFilter()`를 호출하지 않으면 요청은 현재 필터에서 끝난다.

```java
res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
return;
```

이 방식은 인증 실패처럼 Controller를 실행하면 안 되는 경우에 사용한다. 응답 상태만 설정하고 `return`하면 이후 필터와 Controller가 실행되지 않는다.

다만 OPTIONS 요청에서 `chain.doFilter()`를 호출한 뒤 `return`하는 현재 구조는, CORS 헤더를 설정한 상태로 다음 단계까지 요청을 전달한다는 의미다. 애플리케이션의 다른 필터가 OPTIONS 요청을 처리하지 못하거나 인증을 요구한다면, 사전 요청을 즉시 종료하는 방식이 더 적절할 수 있다. 프로젝트의 CORS 설정과 Filter 순서를 함께 확인해야 한다.

### CORS 사전 요청과 JWT 필터의 실행 흐름

- 브라우저는 다른 출처로 Authorization 헤더가 포함된 요청을 보내기 전에 OPTIONS 사전 요청을 보낼 수 있다.
- 이 요청에는 실제 API 데이터가 없고, 어떤 출처·메서드·헤더를 사용할 것인지 확인하는 정보가 포함된다.
- 서버는 허용 출처, 메서드, 헤더를 응답 헤더로 알려준다.
- OPTIONS 요청에 JWT 인증을 요구하면 실제 요청이 전송되기 전에 401이 발생할 수 있으므로, 필터에서 먼저 분기하는 것이 중요하다.

| 요청 조건                             | 현재 필터의 처리                              |
| --------------------------------- | -------------------------------------- |
| OPTIONS 요청                        | CORS 응답 헤더를 설정하고 다음 처리 단계로 전달한다.       |
| 허용 목록에 포함된 경로                     | 토큰 검사 없이 다음 처리 단계로 전달한다.               |
| Authorization 누락 또는 Bearer 형식 불일치 | 401 상태를 설정하고 처리를 종료한다.                 |
| 유효한 JWT                           | 파싱·서명·만료 검증 후 다음 처리 단계로 전달한다.          |
| JWT 검증 예외                         | 예외를 기록하고 종료하지만, 실패 상태 코드 처리가 추가로 필요하다. |

```java
if ("OPTIONS".equalsIgnoreCase(req.getMethod())) {
    res.setStatus(HttpServletResponse.SC_OK);
    res.setHeader("Access-Control-Allow-Origin", "http://localhost:3000");
    res.setHeader("Access-Control-Allow-Methods", "GET, POST, PUT, PATCH, DELETE, OPTIONS");
    res.setHeader("Access-Control-Allow-Headers", "Authorization, Content-Type, Refresh-token");
    res.setHeader("Access-Control-Allow-Credentials", "true");

    chain.doFilter(request, response);
    return;
}
```

- `Access-Control-Allow-Origin`은 요청을 허용할 출처를 지정한다.
- `Access-Control-Allow-Methods`는 허용할 HTTP 메서드를 지정한다.
- `Access-Control-Allow-Headers`는 브라우저가 실제 요청에 포함할 수 있는 요청 헤더를 지정한다.
- `Access-Control-Allow-Credentials`는 쿠키나 인증 정보가 포함된 요청을 허용할지 지정한다.
- 응답 헤더에 Authorization이나 Refresh-Token을 넣었다면 `Access-Control-Expose-Headers`를 설정해야 브라우저의 JavaScript가 해당 응답 헤더를 읽을 수 있다.

### 허용 경로 분기와 JWT 검증

```java
private static final List<String> WHITE_LIST = List.of(
    "/user/**",
    "/swagger-ui/**",
    "/v3/api-docs/**"
);

private final AntPathMatcher matcher = new AntPathMatcher();

public boolean isPath(String path) {
    return WHITE_LIST.stream()
        .anyMatch(pattern -> matcher.match(pattern, path));
}
```

- `WHITE_LIST`는 인증 없이 접근할 수 있는 경로 목록이다.
- `/user/**`는 로그인·회원가입처럼 인증 전에 접근해야 하는 사용자 관련 경로를 포함한다.
- Swagger UI와 API 문서 경로도 개발 편의를 위해 허용 목록에 포함할 수 있다.
- `AntPathMatcher`는 `/**` 같은 패턴을 실제 요청 URI와 비교한다.
- `anyMatch()`는 목록 중 하나라도 일치하면 `true`를 반환한다.

```java
if (isPath(endPoint)) {
    chain.doFilter(request, response);
    return;
}
```

허용 경로라면 Authorization 헤더를 검사하지 않고 다음 단계로 전달한다. 이때도 반드시 `return`해야 이후의 보호 경로 검증 코드가 다시 실행되지 않는다.

```java
if (header == null || !header.startsWith("Bearer ")) {
    res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    return;
}
```

Authorization 헤더가 없거나 `Bearer `로 시작하지 않으면 인증 형식이 잘못된 것으로 판단한다. `Bearer `는 공백까지 포함한 접두사이므로, 이후 실제 토큰을 추출할 때 7글자를 제거한다.

```java
String token = header.substring(7);
```

`Bearer `의 길이가 7이므로 접두사를 제외한 JWT 문자열만 남는다. 이후 이 문자열을 JWT 파서에 전달한다.

```java
try {
    Jwts.parserBuilder()
        .setSigningKey(key)
        .build()
        .parseClaimsJws(token);

    chain.doFilter(request, response);
} catch (Exception e) {
    e.printStackTrace();
    res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    return;
}
```

검증 성공 시에만 `chain.doFilter()`를 호출해야 한다. 검증 실패 시에는 401 응답을 설정하고 `return`해 Controller 실행을 막아야 한다. 현재 코드처럼 예외를 기록하면서도 상태 코드를 설정하지 않으면 클라이언트가 인증 실패를 명확히 알기 어렵다.

또한 `try` 블록 안에 `chain.doFilter()`까지 포함하면 다음 필터나 Controller에서 발생한 예외가 JWT 검증 실패 예외처럼 기록될 수 있다. 토큰 파싱과 다음 단계 실행을 분리하면 원인을 더 정확히 구분할 수 있다.

### Repository와 DTO를 이용한 게시글·댓글 처리

- Controller는 HTTP 요청을 받고 Service를 호출한다.
- Service는 사용자·게시글 존재 여부를 확인하고 Repository를 호출한다.
- Repository는 Entity 조회·저장·삭제와 JPQL 조회를 담당한다.
- RequestDTO는 요청 데이터를 Entity로 변환한다.
- ResponseDTO는 Entity에서 API 응답에 필요한 값만 추출한다.

| 계층·객체       | 이번 실습의 역할                                 |
| ----------- | ----------------------------------------- |
| Controller  | 게시글 목록·작성·상세 조회와 댓글 요청을 받아 Service를 호출한다. |
| Service     | 연관 Entity 조회, 저장, DTO 변환, 트랜잭션 범위를 구성한다.  |
| Repository  | 기본 CRUD와 JPQL 기반 조회를 제공한다.                |
| RequestDTO  | 요청값과 연관 Entity를 이용해 저장할 Entity를 만든다.      |
| ResponseDTO | 게시글 번호, 작성자 이메일, 댓글 목록 등 응답 데이터를 구성한다.    |

게시글 작성 시에는 요청 이메일로 `UserEntity`를 조회한 뒤 게시글의 `writer`에 연결한다. 댓글 작성 시에는 요청 `postId`로 `BlogEntity`를 조회한 뒤 댓글의 `post`에 연결한다.

```java
BlogEntity post = blogRepository.findById(postId)
    .orElseThrow(() -> new RuntimeException("Post not found"));

CommentEntity comment = request.toEntity(post);
commentRepository.save(comment);
```

연관관계를 설정할 때는 단순히 ID 숫자만 넣는 것이 아니라, JPA가 관리할 연관 Entity를 조회해 연결한다. 이렇게 하면 Entity 사이의 관계가 객체 그래프에 반영되고, 저장 시 외래 키 관계도 올바르게 처리된다.

### JPQL Fetch Join과 댓글 포함 응답

- JPQL은 테이블명과 컬럼명이 아니라 Entity 이름과 자바 필드를 기준으로 작성한다.
- `LEFT JOIN FETCH`는 게시글과 댓글을 조회 시점에 함께 로딩한다.
- `LEFT JOIN`을 사용하면 댓글이 없는 게시글도 조회 결과에 포함된다.
- Fetch Join으로 Entity를 함께 가져오는 것과 DTO에 댓글을 넣는 것은 별개의 작업이다. 조회 결과를 DTO로 변환할 때 댓글 컬렉션을 명시적으로 변환해야 한다.

```sql
SELECT b FROM BlogEntity b
LEFT JOIN FETCH b.comments
WHERE b.postId = :postId
```

| 쿼리 구성             | 의미                                                      |
| ----------------- | ------------------------------------------------------- |
| `BlogEntity b`    | `BlogEntity`를 조회 대상으로 지정하고 `b`라는 별칭을 붙인다.               |
| `b.comments`      | Entity에 선언된 댓글 연관관계를 사용한다.                              |
| `LEFT JOIN FETCH` | 게시글과 댓글을 함께 조회하며 댓글이 없어도 게시글을 유지한다.                     |
| `:postId`         | Repository 메서드의 `@Param("postId")` 값과 연결되는 이름 있는 파라미터다. |

```java
public static BlogResponseDTO fromEntityWithComments(BlogEntity entity) {
    return BlogResponseDTO.builder()
        .postId(entity.getPostId())
        .title(entity.getTitle())
        .content(entity.getContent())
        .category(entity.getCategory())
        .email(entity.getWriter().getEmail())
        .comments(entity.getComments().stream()
            .map(CommentResponseDTO::fromEntity)
            .toList())
        .build();
}
```

현재 `BlogService.read()`가 `BlogResponseDTO::fromEntity`를 호출하면 댓글 필드를 채우지 않는 기본 변환 메서드가 사용된다. 댓글을 응답에 포함하려면 `fromEntityWithComments`를 호출해야 한다.

### 트랜잭션과 Dirty Checking

- 트랜잭션 안에서 Repository로 조회한 Entity는 영속성 컨텍스트의 관리 대상이 된다.
- Entity의 필드를 변경하면 Hibernate는 변경 전 상태와 현재 상태를 비교한다.
- 트랜잭션이 커밋되거나 flush가 실행될 때 변경 사항이 감지되면 UPDATE SQL이 실행된다.
- 따라서 관리 중인 Entity를 수정하는 경우에는 일반적으로 수정 후 별도의 `save()`가 필요하지 않다.

```java
@Transactional
public void changeComment(Integer id, String text) {
    CommentEntity entity = commentRepository.findById(id)
        .orElseThrow(() -> new RuntimeException("Comment not found"));
    entity.updateComment(text);
}
```

이 메서드에서는 댓글을 조회하고 `updateComment()`로 필드를 변경한다. 메서드가 정상적으로 끝나 트랜잭션이 커밋되면 Hibernate가 변경 내용을 DB에 반영한다.

단, Dirty Checking은 영속성 컨텍스트가 관리하는 Entity에만 적용된다. 트랜잭션 밖에서 조회했거나, Entity가 분리된 상태라면 변경 감지가 동작하지 않을 수 있다.

| 작업           | 실습에서 사용한 방식                                |
| ------------ | ------------------------------------------ |
| 새 댓글 저장      | `commentRepository.save(entity)`           |
| 기존 댓글 수정     | 트랜잭션 안에서 조회 후 `entity.updateComment(text)` |
| 댓글 삭제        | `commentRepository.deleteById(id)`         |
| 읽기 중심의 상세 조회 | `@Transactional(readOnly = true)`          |

### React 요청에 인증 헤더 전달하기

- Axios GET 요청은 두 번째 인수에 설정 객체를 전달한다.
- Axios POST 요청은 두 번째 인수에 본문, 세 번째 인수에 설정 객체를 전달한다.
- localStorage에 저장한 Authorization 값을 `headers.Authorization`에 넣어야 서버의 JWT 필터가 읽을 수 있다.

```javascript
api.get("/blog/index", {
    headers: { Authorization: at }
});

api.post("/blog/write", data, {
    headers: { Authorization: at }
});
```

POST 요청에서 헤더 설정을 요청 본문 안에 넣으면 서버는 그것을 HTTP 헤더가 아니라 JSON 데이터로 인식한다. 따라서 필터에서 Authorization 헤더를 찾을 수 없다.

### Promise 오류 처리 함수의 실행 시점

- `catch()`에는 Promise가 실패했을 때 실행할 함수를 전달한다.
- 요청이 성공하면 `catch()`의 콜백은 실행되지 않는다.
- 네트워크 오류, 서버 오류 응답, 요청 처리 실패 등이 발생하면 오류 객체가 콜백의 매개변수로 전달된다.

```javascript
api.get("/blog/index", config)
    .catch(err => console.log(err));
```

## 오늘의 코드 1 - 외부 설정과 JWT 발급

application.yml

```yaml
spring:
    profiles:
        default: dev
    config:
        import: file:./.env[.properties]

jwt:
    secret: ${JWT_SECRET_KEY}
```

외부 `.env` 파일의 `JWT_SECRET_KEY` 값을 Spring 설정의 `jwt.secret`으로 연결했다. 애플리케이션 코드에는 실제 비밀 키를 직접 작성하지 않고 외부 설정으로 분리할 수 있다.

JwtProvider.java

```java
@Value("${jwt.secret}")
private String secret;

private final long ACCESS_TOKEN_EXPIRY = 1000L * 60 * 30;
private final long REFRESH_TOKEN_EXPIRY = 1000L * 60 * 60 * 24 * 7;
```

`@Value`로 비밀 키를 주입하고 Access Token은 30분, Refresh Token은 7일 동안 유효하도록 만료 시간을 선언했다.

JwtProvider.java

```java
return Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
```

문자열 비밀 키를 UTF-8 바이트 배열로 변환한 뒤 HMAC 서명과 검증에 사용할 `Key` 객체로 만들었다. 토큰을 생성할 때와 검증할 때 동일한 키를 사용해야 한다.

JwtProvider.java

```java
return Jwts.builder()
    .setSubject(email)
    .setIssuedAt(new Date())
    .setExpiration(new Date(System.currentTimeMillis() + ACCESS_TOKEN_EXPIRY))
    .signWith(getSecretKey())
    .compact();
```

`createAT()`에서 사용자 이메일을 subject에 저장하고, 현재 시각을 기준으로 30분 뒤를 만료 시각으로 설정했다. `signWith()`는 비밀 키로 서명을 만들고, `compact()`는 최종 JWT 문자열을 반환한다.

JwtProvider.java

```java
return Jwts.builder()
    .setSubject(email)
    .setIssuedAt(new Date())
    .setExpiration(new Date(System.currentTimeMillis() + REFRESH_TOKEN_EXPIRY))
    .signWith(getSecretKey())
    .compact();
```

`createRT()`는 Access Token과 같은 구조를 사용하지만 7일의 만료 시간을 적용한다. Refresh Token은 일반 API 인증에 직접 사용하기보다 Access Token 재발급을 위한 용도로 분리하는 것이 일반적이다.

## 오늘의 코드 2 - 로그인 토큰의 응답 헤더 전달과 저장

UserService.java

```java
String at = jwtProvider.createAT(request.getEmail());
String rt = jwtProvider.createRT(request.getEmail());

Map<String, Object> map = new HashMap<>();
map.put("response", UserResponseDTO.fromEntity(entity));
map.put("at", at);
map.put("rt", rt);

return map;
```

## 오늘의 코드 4 - 허용 경로 분기와 JWT 검증

JwtFilter.java

```java
private static final List<String> WHITE_LIST = List.of(
    "/user/**",
    "/swagger-ui/**",
    "/v3/api-docs/**"
);

private final AntPathMatcher matcher = new AntPathMatcher();

public boolean isPath(String path) {
    return WHITE_LIST.stream()
        .anyMatch(pattern -> matcher.match(pattern, path));
}
```

로그인·회원가입과 API 문서 경로를 인증 제외 목록으로 지정했다. `AntPathMatcher`는 `/user/**`처럼 하위 경로를 포함하는 패턴을 실제 요청 URI와 비교한다. `anyMatch()`는 여러 패턴 중 하나라도 일치하면 `true`를 반환한다.

JwtFilter.java

```java
this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
```

`@PostConstruct` 초기화 메서드에서 주입받은 문자열 비밀 키를 JWT 검증에 사용할 `Key` 객체로 변환했다. Provider가 토큰을 생성할 때 사용한 키와 Filter가 검증할 때 사용하는 키가 달라지면 모든 토큰 검증이 실패한다.

JwtFilter.java

```java

    System.out.println("JwtFilter, " + endPoint + "은(는) 토큰 없이 통과");
    chain.doFilter(request, response);
    return;
}
```

허용 목록에 해당하는 요청은 토큰 검증 없이 다음 단계로 전달한다. `return`을 사용해 이후의 Authorization 헤더 검증 코드가 실행되지 않도록 한다.

JwtFilter.java

```java

    System.out.println("JwtFilter UNAUTHORIZED");
    res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    return;
}
```

Authorization 헤더가 없거나 `Bearer ` 접두사가 없으면 인증 실패로 처리한다. `chain.doFilter()`를 호출하지 않으므로 Controller는 실행되지 않는다.

JwtFilter.java

```java
String token = header.substring(7);
```

Authorization 헤더에서 `Bearer ` 접두사 7글자를 제거하고 JWT 문자열만 추출한다. 추출한 토큰을 파서에 전달해 서명과 만료 시간을 검증한다.

JwtFilter.java

```java

    .setSigningKey(key)
    .build()
    .parseClaimsJws(token);
System.out.println("JwtFilter token validation success, move to DispatchServlet");
chain.doFilter(request, response);
```

토큰 파싱과 검증이 성공하면 요청을 다음 필터 또는 DispatcherServlet으로 전달한다. 검증 과정에서 예외가 발생하면 `chain.doFilter()`를 호출하지 않고 401 응답으로 종료해야 한다.

## 어려웠던 점 / 각종 오류

게시글 상세 조회 코드를 점검하며 Fetch Join으로 댓글을 조회하는 단계와 응답 DTO에 댓글을 채우는 단계가 서로 다르다는 점을 확인했다. `BlogService.read()`에서 기본 `fromEntity()`를 호출하면 댓글 컬렉션을 조회했더라도 DTO의 `comments` 필드가 채워지지 않는다. 따라서 `fromEntityWithComments()`를 호출하고, 프런트엔드가 댓글 배열을 정상적으로 받는지 확인해야 한다.

댓글 작성 요청에서는 Authorization 설정이 요청 본문 안에 들어가면 안 된다. Axios POST 요청의 두 번째 인수는 JSON 본문이고 세 번째 인수가 설정 객체이므로, Authorization 헤더는 세 번째 인수의 `headers`에 넣어야 한다. 현재 JPA 프로젝트에는 댓글 Service와 Repository가 작성되어 있으므로, 프런트엔드 요청을 받을 Controller 연결도 후속 작업으로 남아 있다.

JWT 필터는 Authorization 헤더가 누락되거나 Bearer 형식이 잘못된 경우 401을 설정한다. 그러나 토큰 파싱 예외를 처리하는 catch에서도 반드시 401 또는 적절한 인증 실패 응답을 설정해야 한다. 또한 `chain.doFilter()`를 같은 try 블록 안에 넣으면 다음 필터나 Controller에서 발생한 예외까지 JWT 검증 실패로 기록될 수 있으므로, 토큰 검증과 다음 단계 전달을 분리하는 것이 좋다.

`JwtProvider`에서 토큰을 발급하는 기능과 `JwtFilter`에서 토큰을 검증하는 기능은 같은 비밀 키를 사용해야 한다. Provider는 사용자 이메일을 subject에 넣어 토큰을 만들고, Filter 또는 별도의 인증 처리 로직은 검증이 끝난 토큰에서 subject를 추출해 현재 요청 사용자를 식별해야 한다. 현재는 토큰에서 이메일을 꺼내는 메서드와 이를 SecurityContext 또는 요청 사용자 정보에 연결하는 작업이 남아 있다.

현재 게시글 작성자는 요청 본문의 이메일로 조회하고 있다. 인증이 적용된 이후에는 클라이언트가 보낸 이메일을 그대로 신뢰하기보다, 검증된 JWT의 subject에서 사용자 이메일을 가져와 작성자를 결정하는 방식이 더 안전하다. 그래야 사용자가 다른 사람의 이메일을 요청 본문에 넣어 게시글을 작성하는 문제를 줄일 수 있다.

Access Token과 Refresh Token의 용도도 분리해야 한다. Access Token은 보호된 API 요청 인증에 사용하고, Refresh Token은 Access Token 재발급 요청에만 사용하도록 구성하는 것이 일반적이다. Refresh Token을 Redis 등에 저장하면 로그아웃, 강제 만료, 재사용 감지 같은 서버 측 제어가 가능하다.

마지막으로 비밀 키와 토큰 전체를 로그에 출력하지 않도록 주의해야 한다. 개발 중에도 토큰의 앞부분이나 검증 결과 정도만 기록하고, 운영 환경에서는 비밀 키·Access Token·Refresh Token이 로그에 남지 않도록 관리해야 한다.
