오늘의 한 줄 요약

  • Kubernetes는 원하는 상태를 선언하면 컨트롤러가 현재 상태와의 차이를 줄이는 방식으로 동작한다.
  • Deployment는 ReplicaSet을 통해 Pod 복제본 수를 유지하며, 복제본 수를 바꾸는 것이 Pod의 수평 확장·축소이다.
  • Deployment와 Service는 각각의 selector로 Pod 라벨을 선택하므로 라벨의 위치와 선택 조건을 구분해야 한다.
  • Service의 노출 방식과 MetalLB의 주소 풀을 구분하고, 프라이빗 ECR 이미지는 Secret을 참조해 가져오도록 설정한다.
  • 컨테이너의 자원 요청량·제한량을 설정하고, Metrics Server와 kubectl 명령으로 사용량과 리소스 상태를 확인한다.

오늘 배운 것

원하는 상태를 실현하는 컨트롤 플레인

클러스터 관리는 요청을 받는 역할, 상태를 저장하는 역할, Pod를 배치하는 역할, 원하는 상태를 유지하는 역할로 나뉜다. Scheduler와 컨트롤러는 API Server를 통해 상태를 조회하거나 변경한다.

구성 요소 역할
API Server 관리 요청을 받고 인증·권한과 요청 내용을 검증하며, 클러스터 상태를 etcd에 저장한다.
etcd 클러스터의 설정과 상태를 키·값 형태로 저장한다.
Scheduler 아직 노드에 배정되지 않은 Pod를 찾아 자원 요청량과 배치 조건에 맞는 노드를 선택한다.
Controller Manager 여러 컨트롤러를 실행해 현재 상태가 원하는 상태에 가까워지도록 조정한다.

Deployment 생성 요청이 저장되면 관련 컨트롤러가 ReplicaSet과 Pod를 생성하고, Scheduler가 Pod를 배치할 노드를 정한다. 해당 노드의 kubelet은 컨테이너 런타임을 통해 컨테이너 실행을 진행한다.

독립 Pod와 Deployment의 복제본 관리

독립 Pod는 Pod 리소스를 직접 만드는 방식이고, Deployment는 Pod 템플릿을 바탕으로 ReplicaSet을 관리하는 방식이다. 복제본을 유지하는 흐름은 Deployment → ReplicaSet → Pod로 이어진다.

생성 방식 삭제·장애와 복제본 관리
독립 Pod 상위 컨트롤러가 없으면 삭제되거나 유실된 Pod를 대신할 새 Pod를 생성하지 않는다. 살아 있는 노드에서 같은 Pod 안의 컨테이너를 재시작하는 동작은 restartPolicy에 따른다.
Deployment로 관리하는 Pod ReplicaSet이 필요한 Pod를 생성해 지정한 복제본 수를 유지한다. replicas가 1이어도 이 관리 동작은 적용된다.

Deployment가 생성한 Pod 이름에는 보통 Deployment 이름, Pod 템플릿 해시, 생성 시 부여된 구분 문자열이 이어진다. 리소스 이름만 보지 않고 kubectl get deployments.apps,rs,pods로 각 리소스를 함께 확인한다.

Scale Out·In과 Scale Up·Down, 자원 설정

방식 바꾸는 대상과 방향
Scale Out 서버 또는 Pod 같은 실행 단위의 개수를 늘리는 수평 확장
Scale In 실행 단위의 개수를 줄이는 수평 축소
Scale Up 서버의 CPU·메모리 성능 또는 개별 Pod에 할당하는 자원량을 늘리는 수직 확장
Scale Down 개별 실행 단위의 성능이나 자원량을 줄이는 수직 축소

Deployment의 spec.replicas를 바꾸면 Pod의 개수가 달라진다. 이 설정은 Kubernetes 노드의 개수를 바꾸는 설정과 구분된다.

컨테이너의 resources.requests는 스케줄링 시 자원을 계산하는 기준이고, resources.limits는 실행 중 사용할 자원의 제한량이다. CPU의 100m은 0.1 CPU이며, 메모리의 Mi는 MiB 단위이다.

Metrics Server는 kubelet에서 자원 사용량을 수집하며, kubectl top으로 확인하는 실제 사용량과 YAML에 선언한 요청량·제한량은 서로 다른 값이다.

Pod 네트워크와 라벨 기반 Service 연결

실습에서 사용한 CNI 구현인 Weave Net은 Pod 네트워크를 구성한다. Service는 Pod 집합에 접근할 지점을 제공하고, 라벨과 selector로 연결할 Pod를 선택한다.

라벨은 리소스에 붙이는 키·값이고, selector는 조건에 맞는 리소스를 찾는 기준이다. 실습의 app은 라벨 키로 선택한 이름이며, selector에 여러 조건을 지정하면 그 조건을 모두 만족해야 한다.

설정 위치 선택하거나 표시하는 대상
Deployment의 metadata.labels Deployment 자체에 붙는 라벨
Deployment의 spec.selector.matchLabels 관리할 Pod를 선택하는 조건. Pod 템플릿의 라벨이 이 조건을 만족해야 한다.
Deployment의 spec.template.metadata.labels Deployment가 생성하는 Pod에 붙는 실제 라벨
Service의 spec.selector 같은 네임스페이스에서 트래픽을 전달할 Pod를 선택하는 조건
Service 유형 접근 방식
ClusterIP 클러스터 내부 IP로 접근한다. 실습에서는 port-forward로 로컬 포트에 연결한다.
NodePort 노드 IP와 지정된 nodePort로 접근한다.
LoadBalancer 클라우드 연동 또는 MetalLB 같은 구현을 통해 외부 IP를 제공받는다.

Service의 port는 Service가 받는 포트이고, targetPort는 대상 Pod의 포트이다.

Service의 연결 대상은 selector와 Pod 상태에 따라 정해진다. 따라서 표시되는 연결 대상 수는 준비 상태나 라벨 조건 때문에 Deployment의 replicas 값과 다를 수 있다.

MetalLB의 주소 풀과 L2 광고

MetalLB의 IPAddressPool은 LoadBalancer Service에 할당할 IP 범위를 정의하고, L2Advertisement는 그 주소를 L2 네트워크에 광고하도록 지정한다. ipAddressPools로 광고할 풀을 연결하고, interfaces로 사용할 노드 인터페이스를 제한할 수 있다.

이번 L2 실습에서는 노드가 연결된 네트워크 대역에서 사용하지 않는 주소를 확보해야 한다. 노드·게이트웨이·다른 장비의 주소와 DHCP 할당 범위를 피하고, 광고에 참여할 노드의 실제 인터페이스 이름을 확인해 설정한다.

프라이빗 ECR 이미지와 imagePullSecrets

프라이빗 ECR 이미지를 가져오려면 레지스트리 인증 정보가 필요하다. 실습에서는 AWS CLI로 ECR 로그인 비밀번호를 얻고 kubectl create secret docker-registry로 ecr-secret을 준비하는 방식을 사용한다.

Pod는 spec.imagePullSecrets에서 Secret을 참조하며, Deployment는 Pod 템플릿인 spec.template.spec.imagePullSecrets에 설정한다. 참조하는 Secret은 생성할 Pod와 같은 네임스페이스에 있어야 한다.

이미지는 레지스트리 주소, 저장소 이름, 태그를 포함한 전체 이름으로 지정한다. kubectl expose deployment는 해당 Deployment의 Pod에 접근할 Service를 만드는 명령이다.

kubectl로 생성·조회·진단하기

명령 또는 옵션 용도

오늘의 코드 1 - Pod 생성과 컨테이너 자원 요청량·제한량

netflixweb.yaml

apiVersion: v1
kind: Pod
metadata:
  name: netflixweb-pod
  labels:
    app: nginx-app
spec:
  containers:
  - name: nginx-app
    image: powermvp/netflix:v2.0
    ports:
    - containerPort: 80
    resources:
      limits:
        cpu: 200m
        memory: 256Mi
      requests:
        cpu: 100m
        memory: 128Mi

 

메모에 기록된 독립 Pod 정의는 netflixweb-pod에 app: nginx-app 라벨을 붙이고 지정한 이미지를 실행하도록 구성한다. CPU 요청량은 100m, 제한량은 200m이고 메모리 요청량은 128Mi, 제한량은 256Mi로 선언되어 있다.

오늘의 코드 2 - Deployment의 복제본 수와 Pod 선택 조건

nginx-deploy.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-app-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx-app
  template:
    metadata:
      labels:
        app: nginx-app
    spec:
      containers:
      - name: nginx-app
        image: powermvp/marvel-collection:v1.0
        ports:
        - containerPort: 80

 

Deployment 정의에서 복제본 수, selector, Pod 템플릿을 설정하는 부분을 발췌했다. replicas: 3은 유지하려는 복제본 수이고, matchLabels와 Pod 템플릿의 라벨은 모두 app: nginx-app으로 연결된다.

오늘의 코드 3 - Service의 Pod 연결과 노출 방식

nginx-clusterIp.yaml

apiVersion: v1
kind: Service
metadata:
  name: nginx-app-clusterip
spec:
  selector:
    app: nginx-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
  type: ClusterIP

 

app: nginx-app 라벨의 Pod를 선택하고, Service의 80번 포트로 받은 요청을 Pod의 80번 포트로 전달하도록 정의한다. ClusterIP 유형을 사용해 클러스터 내부 접근 지점을 구성한다.

수업메모.txt

kubectl port-forward svc/nginx-app-clusterip 8080:80
curl http://127.0.0.1:8080

 

첫 명령은 Service의 80번 포트를 명령을 실행한 환경의 8080번 포트로 연결한다. 포트 포워딩을 실행한 상태에서 다른 터미널의 curl로 응답을 확인한다. 127.0.0.1은 해당 명령을 실행한 환경을 가리킨다.

nginx-nodePort.yaml

apiVersion: v1
kind: Service
metadata:
  name: nginx-app-nodeport
spec:
  selector:
    app: nginx-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
    nodePort: 30080
  type: NodePort

 

NodePort 유형은 노드의 30080번 포트로 받은 요청을 Service를 통해 대상 Pod로 전달하도록 구성한다. selector와 대상 포트는 앞의 ClusterIP 예제와 같은 값을 사용한다.

nginx-loadbalancer.yaml

apiVersion: v1
kind: Service
metadata:
  name: nginx-app-nodeport
spec:
  selector:
    app: nginx-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
    nodePort: 30090
  type: LoadBalancer

 

LoadBalancer 유형으로 외부 IP 제공을 요청하고 nodePort는 30090으로 지정했다. 앞의 NodePort 정의와 metadata.name이 같으므로 같은 네임스페이스에 적용하면 기존 Service의 구성을 변경하는 예제이다.

오늘의 코드 4 - ECR 이미지 다운로드 인증과 Service 생성

awsecr-pod.yaml

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  imagePullSecrets:
    - name: ecr-secret
  containers:
  - name: nginx
    image: 447839931800.dkr.ecr.us-east-1.amazonaws.com/ecr-nginx:v2.0
    ports:
    - containerPort: 80

 

독립 Pod의 spec.imagePullSecrets에 ecr-secret을 지정하고 ECR 저장소의 v2.0 이미지를 참조한다. 이 설정은 Pod가 속한 네임스페이스의 Secret을 이미지 다운로드 인증에 사용하도록 연결한다.

awsecr-deploy.yaml

    spec:
      imagePullSecrets:
        - name: ecr-secret
      containers:
      - name: nginx
        image: 447839931800.dkr.ecr.us-east-1.amazonaws.com/ecr-nginx:v2.0
        ports:
        - containerPort: 80

 

Deployment의 Pod 템플릿 안에 있는 spec 부분을 발췌했다. 각 Pod가 ecr-secret으로 ECR 이미지 인증을 수행하도록 설정하며, 메모의 전체 Deployment 정의에는 replicas: 5가 선언되어 있다.

수업메모.txt

kubectl expose deployment nginx-deployment --name nginx-svc --port=80 --type=LoadBalancer

 

nginx-deployment를 대상으로 nginx-svc라는 Service를 생성하는 명령이다. Service의 포트는 80, 유형은 LoadBalancer이며, 외부 IP 할당은 MetalLB 같은 구현이 처리한다.

오늘의 코드 5 - Metrics Server 설치 설정과 사용량 조회

수업메모.txt

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl patch deployment metrics-server -n kube-system \
  --type='json' \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

 

첫 명령은 Metrics Server 설치 구성을 적용하고, 이어지는 JSON 패치는 컨테이너 인자에 --kubelet-insecure-tls를 추가한다. 이 옵션은 kubelet 서버 인증서 검증을 생략하는 테스트 환경용 설정이다.

수업메모.txt

kubectl get pods -n kube-system | grep metrics
kubectl top pods -n kube-system

 

첫 명령은 kube-system에서 Metrics Server Pod를 찾고, 두 번째 명령은 같은 네임스페이스의 Pod별 CPU·메모리 사용량을 조회한다. Pod의 실행 상태와 메트릭 조회 결과를 함께 확인하는 절차이다.

어려웠던 점 / 각종 오류

실행 중인 web Pod에 k scale pods web --replicas=5를 실행했을 때 Error from server (NotFound): the server could not find the requested resource 오류가 발생했다. Pod 자체는 복제본 수를 변경하는 scale 대상이 아니므로 Deployment처럼 복제본을 관리하는 리소스를 대상으로 실행해야 한다. 앞서 작성한 Deployment가 존재한다면 k scale deployment nginx-deployment --replicas=5로 지정할 수 있으며, 대화에서는 수정 명령을 실행한 결과까지 확인되지는 않았다.

Deployment YAML에서 어느 라벨을 Pod 라벨과 맞춰야 하는지 확인했다. nginx-deployment 예제는 Deployment selector와 Pod 템플릿에 모두 app: nginx이 있어 조건이 일치했다. Service를 연결할 때도 대상 Pod의 실제 라벨을 기준으로 selector를 작성한다.

MetalLB 주소를 정하기 위해 노드의 ip -br -4 addr와 ip route 출력을 확인했다. 확인된 인터페이스는 ens33, 노드 주소는 10.0.2.10/24, 연결 대역은 10.0.2.0/24, 기본 게이트웨이는 10.0.2.2였다. 이 환경에서 10.0.2.100-10.0.2.120은 DHCP와 다른 장비의 주소에 겹치지 않는지 확인한 뒤 사용할 수 있는 후보 범위이며, 워커 노드의 인터페이스와 실제 할당 결과는 아직 확인되지 않았다.
