오늘 배운 것

Label과 Selector로 리소스를 분류하고 연결하기

Label은 Node, Pod, Deployment 등의 리소스에 붙이는 키·값 정보다. 환경이나 애플리케이션 이름으로 리소스를 묶고, Selector로 필요한 대상을 선택할 수 있다.

Deployment의 spec.selector.matchLabels는 관리할 Pod를 선택하며, 해당 조건은 spec.template.metadata.labels에 포함되어야 한다. Service의 spec.selector도 연결하려는 Pod의 Label을 기준으로 동작한다.

구분 역할
Label 리소스를 분류하고 Selector의 선택 기준으로 사용한다.
Annotation 도구가 사용하는 부가 정보나 변경 이력 등 관리 정보를 기록한다.
명령 또는 옵션 사용 목적
kubectl label key=value로 Label을 추가한다. 기존 값을 바꾸려면 --overwrite를 사용한다.
key- kubectl label에서 해당 키의 Label을 제거한다.
-l / --selector kubectl get에서 Label 조건에 맞는 리소스를 조회한다.
-L 지정한 Label 키의 값을 조회 결과에 별도 열로 표시한다.
--show-labels 조회 결과에 리소스의 Label 정보를 표시한다.

노드 Label과 nodeSelector로 Pod 배치 조건 지정하기

노드의 특성을 Label로 표현하고, Pod의 spec.nodeSelector에 일치해야 할 키와 값을 선언한다. Deployment에서는 생성할 Pod의 설정인 spec.template.spec.nodeSelector에 작성한다.

예를 들어 kubernetes.io/hostname 조건을 지정하면 해당 Label 값을 가진 노드가 배치 대상이 된다. 여러 조건을 선언하면 모두 만족해야 하며, 실제 배치는 노드의 자원 등 다른 스케줄링 조건도 충족해야 한다.

Canary 배포로 기존 버전에서 신규 버전으로 점진적으로 전환하기

Canary 배포는 기존 버전을 유지하면서 신규 버전의 Pod를 일부 운영해 동작을 확인하는 방식이다. 수업에서는 stable과 canary를 별도 Deployment로 관리하고, 복제본 수를 조절해 전환하는 흐름을 정리했다.

단계 기존 버전과 신규 버전의 운영 방식
신규 버전 도입 stable을 유지하고 소수의 canary Pod를 배포한다.
점진적 전환 신규 버전의 동작을 확인하며 canary 복제본을 늘리고 stable 복제본을 줄인다.
전환 완료 stable의 복제본을 0으로 줄여 Pod를 종료해도 Deployment 정의는 남겨 둘 수 있다.

Service로 두 버전을 함께 연결하려면 두 버전의 Pod가 Service의 Selector 조건을 만족해야 한다. Deployment별로 관리하는 Pod는 구분하면서, Service가 선택할 공통 Label을 함께 사용하는 구조를 이해하는 것이 중요하다.

GitOps와 CI/CD에서 GitHub Actions·ECR·Argo CD의 역할

GitOps에서는 배포할 이미지와 복제본 수 같은 원하는 상태를 YAML로 선언하고 Git에서 관리한다. Argo CD는 지정된 저장소의 매니페스트와 클러스터의 실제 상태를 비교하고 동기화하는 배포 역할을 맡는다.

구성 요소 수업에서 정리한 CI/CD 연계 역할
GitHub Actions 애플리케이션을 빌드·검증하고 이미지를 ECR에 올린 뒤, 배포 저장소의 이미지 정보를 갱신하는 CI 작업을 구성할 수 있다.
ECR 배포할 컨테이너 이미지를 저장한다.
GitOps 저장소 Kubernetes에 적용할 YAML과 이미지 버전 등 원하는 상태를 관리한다.
Argo CD GitOps 저장소의 변경을 읽고 대상 Kubernetes 클러스터에 반영한다.

배포 흐름은 소스 변경, CI의 이미지 빌드·업로드, 배포 YAML 갱신, Argo CD 동기화 순서로 연결된다. 이미지 보관과 배포 선언을 연결하면 배포할 이미지 버전을 Git의 변경 이력으로 관리할 수 있다.

Argo CD 저장소 연결과 Application 동기화·롤백

Argo CD에 Git 저장소를 연결한 뒤 Application에서 읽을 저장소·리비전·경로와 배포할 클러스터·네임스페이스를 지정한다. 저장소 접근에 필요한 인증과 컨테이너 이미지 다운로드에 필요한 ECR 인증은 각각의 대상에 맞게 설정한다.

설정 또는 기능 동작
Auto-Sync 자동 동기화를 활성화하면 Git의 원하는 상태와 클러스터 사이의 차이를 감지해 동기화한다.
Prune Resources Git에서 제거된 Argo CD 관리 대상 리소스를 동기화 시 클러스터에서도 삭제한다.
Auto-Create Namespace Application의 대상 네임스페이스가 없으면 동기화 시 생성한다.
History and Rollback 자동 동기화를 끈 상태에서 이전 배포 이력으로 되돌릴 수 있다. 이 작업 자체가 Git 저장소의 내용을 수정하지는 않는다.

Git의 원하는 상태까지 이전 버전으로 되돌리려면 저장소의 매니페스트도 변경해야 한다. 클러스터만 롤백한 뒤 최신 Git 상태를 다시 동기화하면 Git에 선언된 버전이 적용된다.

LoadBalancer와 NodePort의 접속 주소 구분하기

Service 출력의 80:30872/TCP는 서비스 포트가 80, NodePort가 30872라는 뜻이다. 포트 번호를 사용할 때는 접속하는 IP가 외부 IP인지 노드 IP인지 함께 확인해야 한다.

접속 방식 사용할 IP와 포트
LoadBalancer EXTERNAL-IP와 서비스의 port를 사용한다.
NodePort 접근 가능한 노드 IP와 서비스의 nodePort를 사용한다.

기본 Argo CD 서버의 TLS 접속은 https://192.168.198.100처럼 HTTPS를 사용한다. NodePort 번호는 현재 Service 출력으로 확인하고, 프로토콜과 포트도 함께 맞춰야 한다.

오늘의 코드 1 - Label 선언과 Deployment의 Pod 선택

label-demo.yaml

metadata:
  name: label-demo
  labels:
    environment: production
    app: nginx

 

수업 메모의 Pod YAML에서 metadata.labels 부분을 발췌했다. environment와 app Label을 붙여 운영 환경과 애플리케이션 기준으로 Pod를 분류하도록 선언한다.

nginx-deploy.yaml

spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx

 

참고 저장소의 Deployment는 app: nginx인 Pod를 관리하고, 생성할 Pod에도 같은 Label을 선언한다. 현재 파일의 replicas: 2는 유지하려는 복제본 수를 선언한다.

오늘의 코드 2 - nodeSelector로 Argo CD 서버의 배치 노드 지정

수업메모.txt

kubectl patch deployment argocd-server -n argocd -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/hostname":"k8s-worker1"}}}}}'

 

Deployment의 Pod 템플릿에 nodeSelector를 추가하는 명령이다. 적용하면 새로 생성되는 Argo CD 서버 Pod의 배치 대상은 kubernetes.io/hostname: k8s-worker1 Label 조건을 만족하는 노드로 제한된다.

오늘의 코드 3 - ECR 이미지와 imagePullSecrets 연결

nginx-deploy.yaml

    spec:
      imagePullSecrets:
      - name: ecr-secret
      containers:
      - name: eks-nginx
        image: 447839931800.dkr.ecr.us-east-1.amazonaws.com/ecr-nginx:v2.0
        ports:
        - containerPort: 80

 

Pod 설정의 imagePullSecrets에서 ecr-secret을 참조하고 ECR의 ecr-nginx:v2.0 이미지를 지정한다. Secret은 Pod와 같은 네임스페이스에 있어야 하며, 해당 레지스트리에 사용할 인증 정보가 들어 있어야 한다.

오늘의 코드 4 - LoadBalancer로 Argo CD와 Nginx 서비스 노출

수업메모.txt

kubectl patch svc argocd-server -n argocd -p '{"spec": {"type": "LoadBalancer"}}'

 

Argo CD 서버 Service의 타입을 LoadBalancer로 변경하는 명령이다. 외부 IP가 할당되면 해당 IP와 Service에 선언된 서비스 포트로 접근하는 구조다.

nginx-loadbalancer.yaml

spec:
  selector:
    app: nginx
  ports:
  - protocol: TCP
    port: 80
    targetPort: 80
    nodePort: 30080
  type: LoadBalancer

 

Nginx Service는 app: nginx Label을 가진 Pod를 선택하고 서비스 포트 80의 요청을 대상 포트 80으로 전달하도록 선언한다. nodePort: 30080도 지정되어 있어 노드 IP로 접근할 때 사용할 포트를 구분할 수 있다.

어려웠던 점 / 각종 오류

외부 IP와 NodePort를 조합해 접속을 확인한 과정

192.168.198.100에 NodePort인 30872와 31664로 연결을 시도했을 때 TCP 연결 검사는 시간 초과였다. Service 출력에서 외부 IP에 사용하는 서비스 포트와 노드 IP에 사용하는 NodePort를 구분했으며, 당시 검사 결과만으로 네트워크 연결 실패의 원인까지 확정하지는 않았다.

ECR 인증 주소 오류로 발생한 ErrImagePull과 ImagePullBackOff

Nginx Pod가 ecr-nginx:v3.0 이미지를 받지 못했고, Events에서 authorization failed: no basic auth credentials를 확인했다. Pod의 Secret 참조, 네임스페이스, Secret 내부의 auths 주소 순서로 범위를 좁혔다.

확인 항목 확인 결과
Pod의 Secret 참조 imagePullSecrets에 ecr-secret이 연결되어 있었다.
네임스페이스 Pod와 ecr-secret이 모두 default에 있었다.
등록된 인증 주소 447839931800.dkr.ecr.us-east-1.amazonaws.com/ecr-nginx:v3.0으로 이미지 경로와 태그까지 포함되어 있었다.
ECR 인증에 사용할 주소 447839931800.dkr.ecr.us-east-1.amazonaws.com처럼 레지스트리 호스트만 등록해야 한다.

Secret의 존재와 Pod 연결은 확인됐지만, 인증 주소에 이미지 경로와 태그를 넣은 설정 오류가 있었다. ECR 로그인 토큰을 받아 올바른 레지스트리 주소로 Secret을 갱신하고 Deployment를 재시작하는 수정 방법을 정리했다. 수정 후 새 Pod가 1/1 Running으로 전환됐는지는 아직 확인하지 않았다.
