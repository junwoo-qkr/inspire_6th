오늘 배운 것

동기·비동기 통신의 처리 흐름

서비스가 분리되어 있으면 필요한 정보를 다른 서비스에 요청해야 한다. 사용자 상세 정보를 응답하면서 주문 목록도 제공하려면, 사용자 데이터를 관리하는 User Service가 주문 데이터를 관리하는 Order Service와 통신한다.

방식 처리 흐름
동기 HTTP 통신 호출한 흐름이 응답을 기다리고, 받은 결과로 다음 처리를 진행한다. 오늘 실습의 RestTemplate과 Feign 호출이 여기에 해당한다.
비동기 메시지 통신 메시지를 전달하고 작업 완료를 기다리지 않은 채 다른 처리를 이어갈 수 있다. 메시징 프로토콜로 AMQP를 사용할 수 있다.

동기 호출에서는 해당 호출 스레드가 응답을 기다린다. 다른 스레드의 작업까지 모두 멈추는 것은 아니다. 사용자 응답에 주문 정보를 함께 넣는 실습에서는 주문 서비스의 응답을 받아야 조합을 완료할 수 있다.

통신 방식과 데이터 일관성은 구분해야 한다. 동기 호출이 서비스 간 데이터의 강한 일관성을 자동으로 보장하지는 않으며, 비동기 방식에서도 데이터가 최종적으로 같은 상태가 되려면 갱신이 전파되도록 처리해야 한다.

RestTemplate의 요청 정보와 응답 타입

RestTemplate은 코드에서 HTTP 요청을 구성하는 방식이다. exchange()는 호출 주소와 요청 방식, 보낼 정보, 응답을 변환할 타입을 받아 요청을 수행한다.

인자 의미
URL 호출할 주소다. 실습에서는 설정의 order_service.url을 읽고 String.format()으로 %s에 사용자 ID를 넣는다.
HTTP 메서드 HttpMethod.GET으로 주문 목록 조회 요청임을 지정한다.
요청 엔티티 헤더와 본문을 담을 수 있는 요청 정보다. 실습에서는 별도의 요청 엔티티를 전달하지 않아 null을 사용한다.
응답 타입 받은 응답을 변환할 자바 타입이다. 주문 목록처럼 제네릭을 사용하는 경우 ParameterizedTypeReference로 요소 타입까지 전달한다. 
//        ResponseEntity<List<ResponseOrder>> orderListResponse =
//                restTemplate.exchange(orderUrl, HttpMethod.GET, null,
//                        new ParameterizedTypeReference<List<ResponseOrder>>() {});

이 발췌는 주문 객체의 목록을 응답 타입으로 전달하는 부분이다. 현재 실습에서는 RestTemplate 호출 부분이 주석 처리되어 있으며, 응답 객체의 getBody()로 본문을 꺼내는 구조를 확인할 수 있다.

RestTemplate을 빈으로 등록하고 @LoadBalanced를 적용하면 URL의 호스트에 서비스 이름을 사용할 수 있다. Eureka가 인스턴스 정보를 제공하고 로드밸런서가 호출할 대상을 선택하므로, 서비스 이름과 실제 IP·포트를 구분해서 사용할 수 있다. 호스트의 서비스 이름과 그 뒤의 요청 경로는 서로 다른 역할을 한다.

Feign으로 HTTP 요청을 인터페이스에 선언하기

Spring Cloud OpenFeign은 HTTP 호출을 인터페이스로 선언하는 방식이다. 의존성을 추가하고 @EnableFeignClients로 활성화하면 Spring이 인터페이스의 구현 객체를 만들어 준다.

방식 HTTP 호출을 작성하는 위치
RestTemplate 호출 코드에 URL, 메서드, 요청 정보, 응답 타입을 직접 전달한다.
Feign 인터페이스에 서비스 이름과 HTTP 경로, 매개변수, 반환 타입을 선언하고 메서드를 호출한다. 
@GetMapping("/order-service/{userId}/orders_wrongEndpoint")
    List<ResponseOrder> getOrders(@PathVariable String userId);

메서드의 userId가 요청 경로의 같은 이름에 들어가고, 응답은 List<ResponseOrder>로 변환된다. 위 경로는 오류 처리를 확인하기 위해 의도적으로 잘못 지정한 현재 실습 코드다.

@FeignClient(name="order-service")는 서비스 탐색에 사용할 이름을 지정한다. 이를 주입받은 서비스는 사용자 조회 후 주문 목록을 요청하고, 정상 응답을 받으면 사용자 DTO의 orders에 결과를 넣는다.

Feign 로그의 출력 수준과 기록 범위

Feign 로그는 출력 허용 수준과 상세 수준을 함께 설정한다. 클라이언트 인터페이스의 로거를 DEBUG로 설정하고, feign.Logger.Level 빈으로 기록할 범위를 지정한다.

public Logger.Level feignLoggerLevel() {
		return Logger.Level.FULL;
	}
설정 역할
logging.level의 DEBUG 클라이언트의 디버그 로그가 출력되도록 한다.
Logger.Level.FULL HTTP 요청과 응답의 헤더·본문까지 기록할 상세 수준을 지정한다.

자료의 로그 화면에서는 호출 메서드, 요청 URL, 응답 상태와 JSON 본문을 따라갈 수 있다. 사용자 요청과 그 안에서 발생한 주문 조회 요청을 연결해 보면 잘못된 경로를 어느 서비스에 보냈는지 파악할 수 있다.

호출 지점의 예외 처리와 ErrorDecoder

HTTP 오류 응답을 받았을 때 호출 지점에서 예외를 잡을 수도 있고, 공통 Decoder에서 원하는 예외로 변환할 수도 있다. ErrorDecoder는 오류 응답의 HTTP 상태와 호출 메서드를 바탕으로 반환할 예외를 선택한다.

처리 방식 역할
catch (FeignException e) 개별 호출 지점에서 해당 예외 타입을 잡고 후속 처리를 결정한다.
ErrorDecoder.decode() 오류 응답을 자바 예외로 변환한다. Feign은 반환된 예외를 호출자에게 던진다. 
case 404:
                if (methodKey.contains("getOrders")) {
                    return new ResponseStatusException(HttpStatus.valueOf(response.status()),
                            env.getProperty("order-service.exception.order-is-empty"));
                }
                break;

현재 Decoder는 404 응답이면서 호출 메서드에 getOrders가 포함된 경우 설정 메시지를 읽어 ResponseStatusException을 반환한다. methodKey는 호출 메서드를 식별하는 값이며, response.status()는 상대 서비스의 HTTP 응답 상태다.

반환하는 예외 타입을 바꾸면 호출자의 처리 방식도 달라진다. ResponseStatusException은 FeignException의 하위 타입이 아니므로 catch (FeignException e)로 잡히지 않는다. HTTP 응답을 받지 못한 연결 실패도 HTTP 오류 응답을 변환하는 Decoder와 구분해서 보아야 한다.

오류 메시지를 외부 설정으로 분리하기

오류 메시지를 설정 파일에 두면 HTTP 오류를 처리하는 로직과 메시지 내용을 분리할 수 있다. 현재 코드는 Spring이 제공하는 Environment를 생성자로 받아 필요한 설정값을 조회한다.

Environment env;

    public FeignErrorDecoder(Environment env) {
        this.env = env;
    }

getProperty()는 이미 서비스에 로딩된 설정에서 값을 읽는다. Config Server에 원격 요청을 매번 보내는 방식이 아니므로, 원격 설정을 변경했을 때는 서비스의 설정도 갱신되어야 한다. 코드가 조회하는 설정 키와 설정 파일의 이름·계층이 일치해야 한다.

방식 설정값을 사용하는 시점
Environment.getProperty() 메서드를 호출할 때 현재 Environment에 있는 값을 조회한다.
@Value 빈이 만들어질 때 설정값을 필드 등에 주입한다. 새 값으로 빈을 다시 만들도록 @RefreshScope를 함께 사용할 수 있다.

PDF 22페이지는 @Value와 @RefreshScope, busrefresh로 메시지를 갱신하는 방향도 소개한다. 현재 Decoder에는 이 변경을 적용하지 않았으며, Spring Cloud Bus가 구성된 환경에서는 POST /actuator/busrefresh로 설정 갱신 이벤트를 전달할 수 있다.

오늘의 코드 6 - FeignErrorDecoder로 오류 응답 변환하기

FeignErrorDecoder.java

@Component
public class FeignErrorDecoder implements ErrorDecoder {

    Environment env;

    public FeignErrorDecoder(Environment env) {
        this.env = env;
    }

    @Override
    public Exception decode(String methodKey, Response response) {
        switch (response.status()) {
            case 400:
                break;
            case 404:
                if (methodKey.contains("getOrders")) {
                    return new ResponseStatusException(HttpStatus.valueOf(response.status()),
                            env.getProperty("order-service.exception.order-is-empty"));
                }
                break;
            default:
                return new Exception(response.reason());
        }

        return null;
    }
}

 

@Component로 Decoder를 등록하고 getOrders의 404 응답을 설정 메시지를 가진 ResponseStatusException으로 변환한다. 그 외 상태는 default에서 일반 예외를 반환하지만, 400과 조건에 맞지 않는 404는 return null로 끝나는 분기가 남아 있다. 현재 코드의 등록 구성과 예외 전파 흐름을 확인했으며 서비스의 실제 응답과 메시지 갱신 결과를 재검증한 것은 아니다.

어려웠던 점 / 각종 오류

Gateway 요청에서 Environment.getProperty()가 반환한 값에 getBytes()를 호출하면서 예외가 발생했다. 원인은 Gateway가 JWT 검증에 필요한 token.secret을 읽지 못해 null이 반환된 것이었다. 공통 설정에 키를 추가한 뒤 Config Server에서 해당 설정이 제공되는 것은 확인했지만, 인증 헤더 없이 받은 401은 JWT 검증 통과를 확인한 결과는 아니다.

생성자에 의존 객체를 명시하는 것과 필드를 final로 선언하는 것은 역할이 다르다. 생성자 주입은 객체를 전달받는 방법이고 final은 저장된 참조를 다른 객체로 재할당하지 못하게 한다. 현재 실습의 생성자는 전달받은 객체를 다음과 같이 필드에 저장한다.

this.restTemplate = restTemplate;
        this.orderServiceClient = orderServiceClient;

final만 선언하는 것으로 주입이 이루어지는 것은 아니며, 객체 내부의 상태까지 고정되는 것도 아니다. 실습에서는 생성자의 매개변수를 필드에 저장하는 방식으로 의존성을 받았다.

Feign 오류 처리에서는 상대 서비스의 HTTP 상태와 사용자 서비스에서 던지는 예외 타입을 구분해야 했다. 현재는 FeignException을 잡는 블록이 주석 처리되어 있고, Decoder가 반환한 예외가 호출자에게 전달되는 흐름이다.

orders_wrongEndpoint의 404는 주문 데이터가 없다는 뜻으로 해석할 수 없다. 오류 재현을 위해 잘못 지정한 요청 경로이며, 설정 키가 order-is-empty라고 해서 실제 원인이 주문 없음으로 바뀌지는 않는다. 요청 경로와 반환 상태를 먼저 확인해야 한다.

Decoder에서 400 또는 조건에 맞지 않는 404를 처리하면 null을 반환하는 분기가 남아 있다는 점도 확인했다. 오류 응답에 대해 예외를 반환하도록 보완이 필요한 부분이며, TIL에는 현재 작성한 상태를 그대로 기록했다.
