오늘의 한 줄 요약

  • 동기 HTTP 호출과 비동기 메시지 통신은 응답을 기다리는 방식이 다르며, 데이터 일관성은 별도의 처리 설계가 필요하다.
  • RestTemplate.exchange()로 다른 서비스의 데이터를 조회하고, @LoadBalanced로 서비스 이름을 실제 호출 주소에 연결한다.
  • @FeignClient 인터페이스에 HTTP 요청을 선언하면 메서드 호출로 주문 목록을 가져와 사용자 응답에 조합할 수 있다.
  • Feign 로그는 로거의 DEBUG 설정과 Logger.Level 설정을 함께 사용해 요청과 응답을 확인한다.
  • ErrorDecoder로 HTTP 오류 응답을 예외로 변환하고, 오류 메시지는 외부 설정에서 읽도록 분리한다.

오늘 배운 것

동기·비동기 통신과 데이터 일관성

마이크로서비스는 역할별로 나뉘어 있어 다른 서비스가 관리하는 데이터가 필요하면 통신해야 한다. 사용자 정보에 주문 목록을 붙이는 상황에서는 User Service가 Order Service에 조회를 요청한다.

통신 방식 처리 흐름과 특징
동기 HTTP 호출 요청을 보낸 뒤 응답을 받아 후속 처리를 진행한다. 오늘 사용한 RestTemplate과 Feign의 일반적인 호출은 응답을 기다리는 동안 호출 스레드가 대기한다.
비동기 메시지 통신 메시지를 전달한 뒤 작업 완료 응답을 기다리지 않고 다음 처리를 진행할 수 있다. AMQP는 이러한 메시징에 사용할 수 있다.

동기 호출이 기다리게 하는 대상은 호출한 처리 흐름이다. 애플리케이션의 다른 스레드까지 모두 멈추는 것은 아니며, HTTP 자체가 동기 방식만 제공하는 것도 아니다.

강한 일관성은 여러 곳에서 관찰하는 데이터가 같은 최신 상태를 보도록 보장하는 성질이고, 최종적 일관성은 추가 변경이 없고 갱신이 전파되면 데이터가 같은 상태로 수렴하는 성질이다. 동기 통신만으로 강한 일관성이 보장되지는 않으며, 비동기 통신을 사용한다고 최종적 일관성이 자동으로 보장되는 것도 아니다.

RestTemplate의 요청 구성과 서비스 이름으로 호출하기

RestTemplate은 요청을 코드로 구성해 보내는 HTTP 클라이언트다. 빈으로 등록한 객체를 생성자로 주입받고, exchange()에 요청 정보와 응답 타입을 전달한다.

주요 인자 역할
URL 호출 대상 주소와 경로를 지정한다. String.format()을 사용하면 주소의 %s 위치에 사용자 ID를 넣을 수 있다.
HTTP 메서드 HttpMethod.GET처럼 조회·생성 등에 맞는 요청 방식을 지정한다.
요청 엔티티 헤더와 본문을 담는 HttpEntity를 전달한다. 실습에서는 별도로 보낼 요청 정보를 지정하지 않아 null을 사용한다.
응답 타입 응답 본문을 어떤 자바 타입으로 변환할지 지정한다. List<ResponseOrder>처럼 제네릭이 포함되면 ParameterizedTypeReference를 사용할 수 있다. 
// List 내부의 요소 타입까지 표현하는 일반적인 타입 선언 예시다.
ParameterizedTypeReference<List<String>> responseType =
        new ParameterizedTypeReference<List<String>>() {};
// HTTP 클라이언트에 전달하면 문자열 목록 타입으로 응답을 해석하도록 지정할 수 있다.

반환값인 ResponseEntity에는 상태 코드와 헤더, 본문이 포함된다. getBody()로 주문 목록을 꺼내 사용자 DTO에 넣으면 사용자 정보와 주문 정보를 한 응답에 조합할 수 있다.

@LoadBalanced를 적용한 RestTemplate에서는 URL의 호스트 부분에 IP와 포트 대신 서비스 이름을 사용할 수 있다. Eureka는 등록된 인스턴스 정보를 제공하고, 로드밸런서는 호출할 인스턴스를 선택한다. 서비스 이름과 요청 경로는 각각 주소 탐색과 엔드포인트 매핑을 담당한다.

// 첫 번째 order-service는 서비스 이름이고, 그 뒤부터는 요청 경로다.
String url = String.format(
        "http://order-service/order-service/%s/orders", userId);
// userId가 u1이면 경로는 /order-service/u1/orders가 된다.

Feign 인터페이스 선언과 사용자·주문 정보 조합

Spring Cloud OpenFeign은 HTTP 요청을 인터페이스로 선언하는 클라이언트다. spring-cloud-starter-openfeign 의존성을 추가하고 @EnableFeignClients로 활성화한 뒤, 서비스 이름과 HTTP 경로를 인터페이스에 작성한다.

호출 방식 개발자가 작성하는 부분
RestTemplate URL, HTTP 메서드, 요청 정보, 응답 타입을 호출 코드에 직접 전달한다.
Feign 인터페이스의 어노테이션과 메서드 시그니처로 요청을 선언하고, 생성된 클라이언트의 메서드를 호출한다. 
@FeignClient(name = "order-service")
interface OrderClient {
    // 사용자 ID를 경로에 넣어 주문 목록을 조회하는 선언 예시다.
    @GetMapping("/order-service/{userId}/orders")
    List<Order> findOrders(@PathVariable("userId") String userId);
}
// Spring이 구현 객체를 만들어 주므로 HTTP 호출용 구현 클래스를 직접 작성하지 않는다.

@FeignClient의 서비스 이름은 탐색할 서비스를, @GetMapping은 그 서비스에서 호출할 경로를 지정한다. 서비스 탐색과 로드밸런서가 구성된 환경에서는 서비스 이름으로 실제 인스턴스를 찾는다.

생성자로 OrderServiceClient를 주입받은 User Service는 사용자 조회 후 해당 사용자 ID로 주문 목록을 요청한다. 주문 응답을 받은 뒤 DTO의 orders에 넣고 Controller가 이를 ResponseUser로 변환해 반환한다. produces = MediaType.APPLICATION_JSON_VALUE는 사용자 상세 엔드포인트가 제공하는 응답 미디어 타입을 JSON으로 지정한다.

Feign 로그의 출력 조건과 상세 수준

Feign 로그를 보려면 로그 출력 허용 수준과 기록할 상세 수준을 함께 설정해야 한다. 인터페이스가 있는 패키지의 로거를 DEBUG로 설정하고, feign.Logger.Level 빈으로 기록 범위를 지정한다.

설정 역할
로거의 DEBUG Feign이 작성하는 디버그 로그를 실제로 출력할 수 있게 한다. 실습에서는 com.example.userservice.client 패키지에 적용한다.
Logger.Level.FULL HTTP 메서드와 URL, 응답 상태뿐 아니라 헤더와 본문까지 기록한다. 요청 경로 오류와 응답 내용을 추적하는 데 사용한다. 
// Feign이 기록할 상세 범위를 나타내는 열거형 값이다.
Logger.Level detail = Logger.Level.FULL;
// 이 값을 빈으로 제공하고 로거를 DEBUG로 설정하면 전체 요청·응답 로그를 볼 수 있다.

자료의 로그 예시는 호출 메서드 이름, GET 요청 URL, 응답 상태, 헤더와 JSON 본문을 보여준다. 이러한 항목을 따라가면 사용자 상세 요청이 어떤 주문 조회 경로를 호출했는지 확인할 수 있다.

FeignException과 ErrorDecoder의 역할 차이

주문 서비스가 HTTP 오류를 응답하면 이를 사용자 서비스 안에서 어떻게 처리할지 결정해야 한다. 기본 오류 처리에서는 FeignException을 잡을 수 있고, 공통 변환 규칙이 필요하면 ErrorDecoder를 구현한다.

처리 방식 역할과 후속 동작
catch (FeignException e) 개별 호출 지점에서 해당 타입의 예외를 잡는다. 실습의 코드처럼 로그만 남기면 주문 목록이 할당되지 않은 상태로 후속 처리를 이어갈 수 있다.
ErrorDecoder.decode() HTTP 오류 응답의 상태와 호출 메서드를 확인하고 반환할 예외를 선택한다. Feign은 반환된 예외를 호출자에게 던지므로 호출 지점마다 변환 규칙을 반복하지 않아도 된다.

methodKey는 호출한 인터페이스와 메서드를 구분하는 값이고, response.status()는 상대 서비스가 반환한 HTTP 상태다. 상대 서비스의 404가 사용자 서비스의 응답에서도 같은 상태가 되는지는 어떤 예외로 바꾸고 어떻게 처리하는지에 따라 달라진다.

@Override
public Exception decode(String methodKey, Response response) {
    // HTTP 404를 Spring이 상태 코드로 처리할 수 있는 예외로 변환하는 예시다.
    if (response.status() == 404) {
        return new ResponseStatusException(
                HttpStatus.NOT_FOUND, "요청한 경로를 찾을 수 없습니다.");
    }
    // 직접 처리하지 않은 HTTP 오류도 반드시 예외로 변환해 반환한다.
    return new ErrorDecoder.Default().decode(methodKey, response);
}

위 코드는 처리하지 않은 응답을 기본 Decoder에 맡기는 일반적인 예시다. ResponseStatusException은 FeignException의 하위 타입이 아니므로 기존 catch (FeignException e)로 잡히지 않는다. 또한 연결 실패처럼 HTTP 응답 자체가 없는 오류는 오류 응답을 변환하는 ErrorDecoder의 처리 대상과 구분해야 한다.

빈 등록은 @Bean으로 객체를 반환하거나 @Component로 클래스를 스캔하는 방식으로 할 수 있다. 현재 실습은 @Component를 사용해 등록하며, 같은 Decoder를 중복 등록할 필요는 없다.

오류 메시지를 외부 설정에서 읽고 갱신하기

오류 메시지를 코드에 고정하지 않고 외부 설정으로 옮기면 처리 로직과 메시지를 분리할 수 있다. PDF 22페이지는 설정 파일에서 메시지를 관리하고 Environment로 읽는 방식과 @Value, @RefreshScope를 이용한 갱신 방향을 다룬다.

설정값 사용 방식 값을 읽는 시점과 갱신 관계
Environment.getProperty() 호출할 때 현재 Environment에서 값을 조회한다. 원격 파일을 매번 요청하는 방식은 아니므로 Config Server의 변경 내용은 서비스의 Environment에도 반영되어야 한다.
@Value 빈 생성 시 설정값을 필드 등에 주입한다. 갱신된 값으로 빈을 다시 만들도록 @RefreshScope를 함께 사용할 수 있다. 
@Component
@RefreshScope
class OrderErrorMessage {
    // 빈을 만들 때 외부 설정의 오류 메시지를 읽는다.
    @Value("${order-service.exception.order-is-empty}")
    private String message;

    public String getMessage() {
        return message; // 갱신 후 다시 생성된 빈에서는 새 메시지를 반환한다.
    }
}

위 코드는 자료의 갱신 방향을 설명하는 예시이며, 현재 FeignErrorDecoder는 생성자로 주입받은 Environment를 사용한다. @Value와 @RefreshScope로 변경한 상태나 busrefresh 실행 결과를 실습 완료로 기록하지 않는다.

Spring Cloud Bus가 구성된 환경에서는 POST /actuator/busrefresh로 설정 갱신 이벤트를 전달할 수 있다. 코드가 읽는 order-service.exception.order-is-empty와 설정 파일의 키가 같은지 확인해야 하며, 키를 찾지 못한 getProperty()는 기본값을 지정하지 않으면 null을 반환한다.

pom.xml (user-service)

			<groupId>org.springframework.cloud</groupId>
			<artifactId>spring-cloud-starter-openfeign</artifactId>

HTTP 호출 인터페이스를 만들기 위해 spring-cloud-starter-openfeign 의존성을 추가했다. 의존성만 추가하는 것으로 끝나지 않고 Feign 클라이언트 활성화와 인터페이스 선언을 함께 구성한다.

UserServiceApplication.java

@SpringBootApplication
@EnableDiscoveryClient
@EnableFeignClients

 

@EnableFeignClients를 추가해 Feign 인터페이스를 찾아 구현 객체를 생성하도록 구성했다. 현재 인터페이스는 애플리케이션 클래스 아래의 client 패키지에 있다.

OrderServiceClient.java

@FeignClient(name="order-service")  // service-discovery에 등록된 서비스 이름
public interface OrderServiceClient {

//    @GetMapping("/order-service/{userId}/orders")
    @GetMapping("/order-service/{userId}/orders_wrongEndpoint")
    List<ResponseOrder> getOrders(@PathVariable String userId);

서비스 이름과 HTTP 요청 경로를 인터페이스에 선언한 부분이다. 정상 경로는 주석으로 남아 있고, 현재 활성 경로인 orders_wrongEndpoint는 404 오류 처리를 살펴보기 위한 잘못된 엔드포인트다.

오늘의 코드 6 - ErrorDecoder 등록과 상태별 예외 변환

FeignErrorDecoder.java

@Component
public class FeignErrorDecoder implements ErrorDecoder {

    Environment env;

    public FeignErrorDecoder(Environment env) {
        this.env = env;
    }

    @Override
    public Exception decode(String methodKey, Response response) {
        switch (response.status()) {
            case 400:
                break;
            case 404:
                if (methodKey.contains("getOrders")) {
                    return new ResponseStatusException(HttpStatus.valueOf(response.status()),
                            env.getProperty("order-service.exception.order-is-empty"));
                }
                break;
            default:
                return new Exception(response.reason());
        }

        return null;
    }
}

 

@Component로 Decoder를 등록하고, getOrders 호출의 404 응답을 설정 메시지를 담은 ResponseStatusException으로 변환하도록 구성했다. 현재 400과 조건에 맞지 않는 404는 return null로 끝나는 분기가 남아 있으므로, 처리하지 않은 오류도 예외를 반환하도록 보완해야 한다. 빈 구성과 코드 분기는 확인했지만 실행 중인 서비스의 Decoder 호출과 메시지 반영은 별도로 검증하지 않았다.

어려웠던 점 / 각종 오류

Gateway를 통해 사용자 목록을 요청했을 때 Environment.getProperty()의 반환값에 getBytes()를 호출하다가 예외가 발생했다. JWT 검증에 필요한 token.secret이 Gateway의 Environment에 없어 null이 반환된 것이 원인이었다. application.yml (공통 설정)에 설정한 뒤 Config Server가 해당 키를 제공하는 것은 확인했지만, 인증 헤더 없이 받은 401만으로 JWT 검증까지 성공했다고 판단할 수는 없다.

의존성을 생성자로 받는 방식과 필드에 final을 붙이는 방식의 차이가 헷갈렸다. 생성자 주입은 객체를 전달받는 방법이고, final은 저장한 참조를 나중에 다른 객체로 바꾸지 못하게 하는 선언이다. 둘은 함께 사용할 수 있으며, final만 선언한다고 Spring이 의존성을 주입하는 것은 아니다.

class ClientHolder {
    private final OrderServiceClient client;

    ClientHolder(OrderServiceClient client) {
        this.client = client; // 생성자로 전달받은 참조를 한 번 저장한다.
    }
    // final은 참조의 재할당을 막으며, 객체 내부 상태까지 고정하지 않는다.
}

Feign 오류 처리 확인에서는 Decoder가 반환하는 예외 타입과 서비스의 catch 타입을 구분해야 했다. 404를 ResponseStatusException으로 변환하면 catch (FeignException e)로는 잡히지 않는다. 현재 소스에서는 해당 try-catch 블록이 주석 처리되고 Feign을 직접 호출하는 코드가 활성화되어 있다.

지금 호출하는 orders_wrongEndpoint의 404는 주문 데이터가 없어서 생긴 결과로 해석하면 안 된다. 잘못된 엔드포인트를 사용한 실습이며, 메시지 설정의 이름이 order-is-empty라는 이유만으로 실제 오류 원인이 주문 없음이라고 판단할 수는 없다. 요청 경로, 상대 서비스의 HTTP 상태, 변환한 예외를 순서대로 확인해야 한다.

Decoder의 case 400과 일부 404 분기가 return null로 끝나는 부분도 확인했다. decode()는 오류 응답에 대해 예외를 반환해야 하므로, 직접 처리하지 않은 오류는 new ErrorDecoder.Default().decode(methodKey, response)에 맡기는 방식으로 보완할 수 있다. 이 개선 예시는 개념 설명에만 포함했으며 현재 실습 원본 코드는 수정하지 않았다.
