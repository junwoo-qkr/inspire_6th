[LG CNS AM INSPIRE CAMP 6기] 10/13 TIL - MSA: Config Server 연동과 Cloud Bus 설정 갱신, 암호화

오늘의 한 줄 요약

  • API Gateway도 Config Server와 연결해 JWT 검증에 필요한 설정을 중앙에서 가져오도록 구성했다.
  • RabbitMQ와 Spring Cloud Bus를 연결해 서비스마다 따로 보내던 설정 갱신 요청을 이벤트로 전달했다.
  • 대칭키와 RSA 공개키·개인키를 이용한 암호화를 배우고, DB 비밀번호와 JWT 서명 키를 암호문으로 저장했다.

키워드 정리

키워드 설명 또는 예시
Config Server 설정 저장소에서 값을 읽어 여러 서비스에 제공하는 중앙 설정 서버.
bootstrap.yml Config Server 주소와 가져올 설정 이름을 지정하는 초기 설정 파일.
Actuator 상태 확인, 설정 갱신, 요청 기록 등의 관리 엔드포인트를 제공한다.
HttpExchangeRepository HTTP 요청·응답 기록을 저장하며 httpexchanges 조회의 근거가 된다.
Spring Cloud Bus 메시지 브로커를 통해 여러 서비스에 설정 갱신 이벤트를 전달한다.
RabbitMQ / AMQP RabbitMQ는 메시지 브로커이며, AMQP는 메시지 통신에 사용하는 프로토콜이다.
Publish / Subscribe 발행자가 이벤트를 보내고, 구독자가 이를 받아 처리하는 흐름.
refresh / busrefresh refresh는 요청받은 서비스, busrefresh는 연결된 Bus 참여 서비스의 갱신을 유도한다.
대칭키 / 비대칭키 대칭키는 같은 키를 사용하고, 비대칭키는 공개키·개인키 쌍을 사용한다.
{cipher} Config Server가 복호화할 암호문 앞에 붙이는 표시.
keytool / KeyStore JDK의 키 관리 도구와 키·인증서를 보관하는 저장소.
alias / storepass / keypass 키 식별 이름 / 저장소 비밀번호 / 개인키 비밀번호.

오늘 배운 것

공통 설정과 서비스별 설정을 Config Server에서 읽기

Config Server는 설정 파일을 보관한 Git 저장소를 읽고, Config Client에 필요한 값을 제공한다. 서비스는 bootstrap.yml의 spring.cloud.config.uri로 서버에 연결하고, spring.cloud.config.name으로 가져올 설정 이름을 정한다.

application.yml은 공통 설정, 이름이 지정된 파일은 해당 서비스 설정으로 사용한다. 설정 이름을 바꿀 때는 기존 파일에 있던 필수값이 공통 파일이나 새 파일에도 있는지 확인해야 한다.

설정 파일 현재 실습에서의 역할
application.yml 공통 JWT 설정을 보관한다.
ecommerce.yml Gateway가 선택하며, Gateway IP 설정을 보관한다.
user-service.yml user-service가 선택하며, DB 접속 정보와 JWT 설정을 보관한다. 
# example-service.yml의 설정을 요청하는 일반적인 구성
spring:
  cloud:
    config:
      uri: http://localhost:8888
      name: example-service  # 설정 파일 이름에서 확장자를 제외한다.

설정 확인용 GET /user-service/default는 Config Server에 보내는 요청이다. 여기서 user-service는 설정 이름, default는 프로필 이름이다.

Actuator로 개별 설정을 갱신하고 요청 기록 확인하기

Actuator는 애플리케이션의 상태와 관리 기능을 HTTP 엔드포인트로 제공한다. 필요한 기능을 사용하려면 의존성을 추가하고, 최상위 management.endpoints.web.exposure.include에 엔드포인트를 노출해야 한다.

Gateway와 user-service는 서로 다른 프로세스이므로, 한쪽의 refresh 요청이 다른 쪽의 설정까지 자동으로 갱신하지는 않는다. JWT를 발급하는 서비스와 검증하는 Gateway가 동일한 token.secret을 읽는지 확인해야 한다.

엔드포인트 역할
health 서비스의 상태를 확인한다.
refresh 해당 서비스의 외부 설정을 다시 읽는다.
httpexchanges 저장된 HTTP 요청·응답 기록을 조회한다. 
# 각각의 서비스에 POST 요청을 보내 설정을 갱신한다.
Invoke-RestMethod -Method Post -Uri 'http://localhost:8000/actuator/refresh'
Invoke-RestMethod -Method Post -Uri 'http://localhost:8083/actuator/refresh'

httpexchanges는 HttpExchangeRepository 빈이 있어야 기록을 조회할 수 있다. InMemoryHttpExchangeRepository는 기록을 메모리에 보관하므로 재시작 후 기록이 유지되지는 않는다.

원격 Git 저장소에 변경 내용을 반영하는 순서

Config Server의 git.uri를 GitHub 주소로 지정하면 서버는 그 원격 저장소의 브랜치에서 설정을 읽는다. 따라서 로컬 파일 수정만으로는 원격 설정이 바뀌지 않으며, 커밋과 push가 필요하다.

설정의 저장 위치와 실행 중인 서비스에 반영하는 시점은 구분해야 한다. 원격 저장소에 변경을 올린 다음 클라이언트 설정을 갱신한다.

# F:\remoteSettings에서 변경 파일을 원격 main 브랜치에 반영하는 예시
# 실제로 변경한 파일만 스테이징한다.
git add application.yml user-service.yml
git commit -m 'Update service configuration'
git push origin main
# push 후 refresh 또는 busrefresh를 요청하면 원격 설정을 다시 읽는다.

RabbitMQ와 Spring Cloud Bus로 설정 갱신 이벤트 전달하기

Spring Cloud Bus는 서비스들을 메시지 브로커로 연결하고, 상태나 설정의 변경 이벤트를 전달한다. 이번 실습에서는 spring-cloud-starter-bus-amqp와 RabbitMQ를 사용했다.

publish는 이벤트를 보내는 동작이고, subscribe는 이벤트를 받아 처리하는 동작이다. 한 Bus 참여 서비스에 POST /actuator/busrefresh를 보내면 브로커를 통해 갱신 이벤트가 전달되고, 이를 받은 Config Client들이 Config Server에서 설정을 다시 읽는다.

브로커가 이벤트의 전달을 중개해 서비스들이 서로 직접 요청할 필요를 줄인다. 정상적인 갱신에는 서비스들의 브로커 연결과 이벤트 수신이 필요하다.

포트 또는 구성 역할
5672 애플리케이션이 RabbitMQ와 AMQP로 통신하는 포트.
15672 RabbitMQ 관리 화면에 접근하는 포트.
Bus 메시지 destination 여러 참여 서비스에 이벤트를 배포하는 논리적인 목적지. 이번 파일에는 별도 값이 지정되지 않았다. 
# 수업에서 사용한 RabbitMQ 이미지와 두 포트를 연결한다.
docker run -it -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:4.1.0-management

# 노출된 user-service 엔드포인트에서 갱신 이벤트를 발행하는 요청 예시
Invoke-RestMethod -Method Post -Uri 'http://localhost:8083/actuator/busrefresh'

수업에서는 원격 설정을 수정한 후 user-service에서 busrefresh를 요청해 변경값을 다시 가져오는 흐름을 실습했다. 개별 refresh를 여러 서비스에 반복하던 작업을 이벤트 전달로 묶는 것이 핵심이다.

설정값을 암호문으로 저장하고 Config Server에서 복호화하기

대칭키 암호화는 암호화와 복호화에 같은 키를 사용한다. 비대칭키 암호화는 서로 짝을 이루는 공개키와 개인키를 사용하며, 이번 RSA 설정 암호화에서는 공개키로 암호화하고 개인키로 복호화한다.

Config Server의 POST /encrypt에 평문을 보내면 암호문이 반환되고, POST /decrypt에 암호문을 보내면 평문이 반환된다. YAML에 저장할 때는 암호문 앞에 {cipher}를 붙여 복호화 대상임을 표시한다.

방식 설정과 키의 역할
대칭키 encrypt.key로 같은 키를 지정한다.
RSA 비대칭키 encrypt.key-store로 키 저장소를 지정한다. 
# 요청 형식을 설명하기 위한 예시이며, 실제 비밀번호를 사용하지 않는다.
$cipherText = Invoke-RestMethod -Method Post -Uri 'http://localhost:8888/encrypt' -ContentType 'text/plain' -Body 'study-password'
Invoke-RestMethod -Method Post -Uri 'http://localhost:8888/decrypt' -ContentType 'text/plain' -Body $cipherText
# 같은 키 설정이라면 복호화 응답은 study-password이다.

기본적으로 Config Server는 {cipher} 값을 복호화해서 클라이언트에 전달한다. Git 저장소에는 암호문이 남지만 설정 조회 응답에는 평문이 나타날 수 있으므로, 설정 조회와 암호화·복호화 API의 접근을 보호해야 한다.

keytool 옵션과 Config Server의 키 저장소 설정 연결하기

keytool은 JDK에 포함된 키·인증서 관리 도구이다. -genkeypair로 생성한 공개키·개인키 쌍은 자체 서명 인증서와 함께 KeyStore에 보관한다.

alias는 저장소 내부의 키 이름이고, keystore는 저장소 파일이다. 저장소 비밀번호와 개인키 비밀번호는 각각 다른 대상을 보호한다.

keytool 옵션 뜻 Config Server 설정
-genkeypair 공개키·개인키 쌍 생성 키 생성 작업
-alias 저장소 안에서 키를 식별하는 이름 encrypt.key-store.alias
-keyalg RSA RSA 알고리즘으로 키 생성 공개키·개인키 암호화에 사용
-dname 인증서의 소유자 정보 인증서에 기록되는 이름
-keystore 키 저장소 파일 경로 encrypt.key-store.location
-storepass 저장소를 여는 비밀번호 encrypt.key-store.password
-keypass 개인키를 보호하는 비밀번호 encrypt.key-store.secret 
# 키 저장소 폴더에서 실행하는 일반적인 RSA 키 생성 예시
# 생략한 소유자 정보와 저장소 비밀번호는 입력 프롬프트에서 지정한다.
keytool -genkeypair -alias studyKey -keyalg RSA -keystore study.jks -storetype JKS
# 파일 확장자와 별개로 -storetype JKS가 실제 저장 형식을 지정한다.

-dname의 CN은 대표 이름, OU는 부서·조직 단위, O는 기관 이름, L은 지역, C는 국가 코드이다. 각 항목은 쉼표로 구분한다.

수업에서는 -storepass와 -keypass에 같은 값을 사용했다. 개인키 비밀번호가 다르면 encrypt.key-store.secret을 별도로 지정한다. .jks라는 파일 이름만으로 저장 형식이 JKS라고 단정할 수는 없다.

오늘의 코드 1 - Gateway를 Config Client로 연결하기

pom.xml

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-config</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

 

Gateway에 Config Client, bootstrap, Actuator 의존성을 추가했다. 중앙 설정 로딩과 설정 갱신 엔드포인트를 사용할 구성을 갖춘 부분이다.

bootstrap.yml

spring:
  cloud:
    config:
      uri: http://127.0.0.1:8888
      name: ecommerce  # 가져올 설정 파일의 이름

 

Gateway는 8888번 Config Server에서 ecommerce 설정을 가져오도록 지정했다. Gateway의 로컬 JWT 설정은 주석 처리되어 외부 설정을 사용하도록 바뀐 것을 확인했다.

오늘의 코드 2 - Actuator 노출과 HTTP 요청 기록 저장하기

application.yml

management:
  endpoints:
    web:
      exposure:
        include:
          - refresh
          - health
          - beans
          - info
          - httpexchanges
          - busrefresh

 

Gateway의 최상위 management 아래에 사용할 엔드포인트를 열었다. refresh와 busrefresh를 각각 노출하는 목록이며, 이름을 적는 것과 실제 요청 성공 여부는 구분해서 확인한다.

ApigatewayServiceApplication.java

@Bean
public HttpExchangeRepository httpExchangeRepository() {
    return new InMemoryHttpExchangeRepository();
}

 

HttpExchangeRepository 빈을 만들어 HTTP 요청·응답 기록을 메모리에 보관하도록 구성했다. httpexchanges 조회를 위한 저장소이며, 서비스가 재시작되면 기록은 초기화된다.

오늘의 코드 3 - 원격 Git 저장소와 서비스별 설정 이름 선택하기

application.yaml

server:
  port: 8888

spring:
  application:
    name: config-service
  cloud:
    config:
      server:
        git:
          uri: https://github.com/junwoo-qkr/remoteSettings
          default-label: main

 

Config Server의 설정 저장소를 로컬 파일 URI에서 GitHub 주소로 바꾸고 main 브랜치를 지정했다. 현재 구성에서는 원격 브랜치에 변경이 올라가야 서버가 새 값을 읽을 수 있다.

bootstrap.yml

spring:
  cloud:
    config:
      uri: http://127.0.0.1:8888
      name: user-service

 

user-service의 설정 이름을 ecommerce에서 user-service로 변경했다. Gateway와 연결 주소는 같지만 선택하는 서비스별 설정 파일은 다르다.

ecommerce.yml

gateway:
    ip: 192.168.0.28

 

F:\remoteSettings의 ecommerce.yml에는 Gateway IP가 저장되어 있다. 공통 JWT 설정과 Gateway 관련 값을 서로 다른 파일로 분리한 구성이다.

오늘의 코드 4 - RabbitMQ 연결과 Bus 참여 설정하기

pom.xml

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bus-amqp</artifactId>
</dependency>

 

Gateway, user-service, config-service에 같은 Bus AMQP 의존성이 선언된 것을 확인했다. 서비스마다 RabbitMQ에 연결해 갱신 이벤트를 보내고 받도록 구성하는 의존성이다.

application.yml

  rabbitmq:
    host: 127.0.0.1
    port: 5672
    username: guest
    password: '[비밀번호 생략]'

 

Gateway의 spring 아래에 있는 RabbitMQ 연결 설정을 발췌했다. AMQP 통신 포트는 5672이며, 관리 화면의 15672와 역할이 다르다.

오늘의 코드 5 - 공통 설정과 서비스 설정에 암호문 저장하기

application.yml

token:
    expiration_time: 864000000
    secret: '[서명 키 생략]'

 

F:\remoteSettings의 공통 파일에 JWT 만료 시간과 서명 키가 있다. Config Client가 이름으로 선택한 설정 파일과 함께 읽는 공통값이며, 실제 서명 키는 생략했다.

user-service.yml

spring:
  datasource:
    driver-class-name: org.h2.Driver
    url: jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1;
    username: sa
    password: '{cipher}[암호문 생략]'

token:
    expiration_time: 864000000
    # secret: '[서명 키 생략]'
    secret: '{cipher}[암호문 생략]'

 

user-service의 DB 비밀번호와 JWT 서명 키를 {cipher}가 붙은 값으로 저장한 것을 확인했다. 로컬 datasource 설정은 주석 처리되어 있으며, 여기서는 실제 비밀번호·서명 키와 긴 암호문을 생략했다.

오늘의 코드 6 - RSA 키 저장소를 Config Server에 연결하기

bootstrap.yml

encrypt:
#  key: '[대칭키 생략]'
  key-store:
    location: file:///F:/keystore/apiEncryptionKey.jks
    password: '[비밀번호 생략]'
    alias: apiEncryptionKey

 

Config Server의 bootstrap.yml에 키 저장소 경로, 저장소 비밀번호, 키 별칭을 지정했다. 대칭키 설정은 주석 처리되어 있으며, 현재 파일은 apiEncryptionKey라는 별칭의 키를 사용하도록 구성되어 있다.

어려웠던 점 / 각종 오류

처음에는 로컬 설정 파일을 커밋한 뒤 refresh를 요청했는데 브랜치가 이전 상태로 돌아가는 현상을 겪었다. 당시 Config Server가 직접 사용하던 F:\remoteSettings에는 origin이 연결되어 있었고, Git 이력에서도 로컬 커밋 이후 origin/main으로 이동한 기록을 확인했다. 현재처럼 GitHub URI를 사용하는 구성에서는 변경을 커밋·push한 다음 서비스 설정을 갱신하는 순서가 필요하다.

Gateway의 사용자 조회와 user-service의 로그인 처리에서 Environment.getProperty("token.secret")가 null인 상태로 getBytes()를 호출하는 오류를 확인했다. 이는 JWT에 사용할 설정값을 읽지 못한 단계의 문제이므로, 서버 주소·설정 이름·공통 파일의 필수값·각 서비스의 갱신 여부를 먼저 확인해야 한다. 설정 이름을 바꿀 때는 서비스별 파일뿐 아니라 공통 application.yml에서 제공하는 값도 함께 확인한다.

http://localhost:8000/user-service/default에 토큰을 넣었어도 404가 발생했다. Gateway는 이 요청을 user-service의 /default로 전달하지만 해당 API가 없으며, 설정 조회 주소는 Config Server의 http://localhost:8888/user-service/default이다. 사용자 목록 조회는 Gateway의 /user-service/users를 사용한다.

상위 POM에 Bus 의존성을 추가했을 때 dependencies.dependency.version 누락으로 Maven이 프로젝트를 읽지 못하는 오류가 확인됐다. 해당 상위 프로젝트에는 Spring Cloud BOM이 없었고, 자식 모듈들은 Spring Boot를 직접 부모로 사용하므로 그 의존성을 상속받지 않았다. 현재는 필요한 모듈에 Bus 의존성을 선언하고 각 모듈의 Spring Cloud BOM으로 버전을 관리하는 구성을 확인했다.
