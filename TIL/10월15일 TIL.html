오늘 배운 것

여러 서비스 인스턴스의 데이터와 메시지 기반 연동

동일한 서비스를 여러 인스턴스로 실행하면서 각 인스턴스가 별도의 메모리 DB를 사용하면, 요청을 처리한 인스턴스에 따라 저장된 데이터가 달라질 수 있다. 동일 서비스의 인스턴스들이 외부의 공통 DB를 사용하거나, 데이터 변경 이벤트를 전달해 필요한 데이터를 반영하는 방식을 생각할 수 있다.

 

서비스마다 상대 서비스에 직접 연결하는 방식은 연동 대상이 늘어날수록 연결과 데이터 흐름 관리가 복잡해진다. Kafka를 사용하면 생산자는 토픽에 이벤트를 남기고 소비자는 자신에게 필요한 이벤트를 읽으므로, 메시지를 보내는 서비스와 처리하는 서비스의 연결을 분리할 수 있다.

연동 방식 데이터를 처리하는 흐름
동일 서비스의 외부 공통 DB 여러 인스턴스가 같은 DB에 접근해 해당 서비스의 데이터를 조회하고 변경한다.
애플리케이션의 Kafka 연동 서비스가 메시지를 발행하고 다른 서비스의 Consumer가 메시지를 읽어 자신의 DB에 반영한다.
Kafka Connect Source·Sink 커넥터의 설정과 플러그인으로 외부 시스템과 Kafka 사이의 데이터를 이동시킨다.

Broker, Controller와 토픽의 역할

Broker는 토픽의 메시지를 저장하고 Producer와 Consumer의 요청을 처리한다. 토픽은 여러 파티션으로 나눌 수 있고, 메시지 순서는 같은 파티션 안에서 보장된다. 브로커 확장과 파티션 분산은 많은 메시지를 나누어 처리하는 기반이 된다.

 

KRaft에서는 서버에 Broker 역할, Controller 역할 또는 두 역할을 함께 지정할 수 있다. Controller는 클러스터 메타데이터와 리더 선출 등을 관리하며, 고가용성을 위해 여러 Controller를 구성한다. 실습용 단일 서버 구성과 운영 환경의 다중 서버 구성은 구분해야 한다.

Consumer Group과 메시지를 읽는 시작 위치

같은 Consumer Group의 Consumer들은 파티션을 나누어 맡는다. 서로 다른 그룹은 각자의 offset을 기준으로 같은 토픽의 메시지를 독립적으로 읽을 수 있다. 따라서 여러 인스턴스에 Kafka를 연결했다고 해서 각 인스턴스의 독립 DB에 모든 메시지가 반영되는 것은 아니다.

설정 또는 상태 메시지 읽기 기준
저장된 유효한 그룹 offset이 있음 기존에 커밋한 offset을 기준으로 이어서 읽는다.
auto-offset-reset: earliest 저장된 offset이 없거나 유효하지 않으면 현재 보관된 가장 오래된 메시지부터 읽는다.
콘솔의 --from-beginning 시작 offset이 없는 경우 처음부터 읽도록 한다.

Docker와 콘솔 도구로 Kafka 흐름 확인하기

수업에서는 Docker로 broker 컨테이너를 만들고 9092 포트를 공개하는 흐름을 다뤘다. docker exec -it broker bash로 컨테이너에 들어간 뒤 Kafka 콘솔 도구를 사용해 토픽과 메시지를 확인한다.

사용 도구 실습에서 확인하는 내용
kafka-topics.sh --create로 quickstart-events 토픽을 만들고, --list와 --describe로 목록과 상세 정보를 조회한다.
kafka-console-producer.sh 대상 토픽에 입력한 내용을 이벤트로 발행한다.
kafka-console-consumer.sh 대상 토픽의 이벤트를 읽고 실행 중 새로 들어오는 메시지도 계속 확인한다.

Java 설정과 Spring Boot 자동 설정의 관계

Java 설정 방식은 연결 주소와 직렬화 정보를 직접 구성해 ConsumerFactory, ProducerFactory 등의 Bean을 등록한다. Consumer는 컨테이너가 실행하고, 애플리케이션은 KafkaTemplate으로 메시지 발행을 요청한다.

@Bean
public ConsumerFactory<String, String> consumerFactory() {
    Map<String, Object> properties = new HashMap<>();
    properties.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    properties.put(ConsumerConfig.GROUP_ID_CONFIG, "consumer-group-id");
    properties.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
    properties.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
    properties.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
    return new DefaultKafkaConsumerFactory<>(properties);
}
@Bean
public ProducerFactory<String, String> producerFactory() {
    Map<String, Object> configProperties = new HashMap<>();
    configProperties.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    configProperties.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
    configProperties.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
    return new DefaultKafkaProducerFactory<>(configProperties);
}

 

Spring Boot에서는 spring-kafka 의존성과 spring.kafka.* 설정을 사용해 필요한 기본 객체를 자동 구성할 수 있다. 직접 등록한 Bean이 없으면 기본 ConsumerFactory, ProducerFactory, KafkaTemplate과 kafkaListenerContainerFactory를 자동 구성하며, @KafkaListener 처리도 지원한다.

Kafka 설정을 Java 클래스에서 설정 파일로 옮기기

Java 설정 방식은 연결 주소와 직렬화 정보를 직접 구성해 ConsumerFactory, ProducerFactory 등의 Bean을 등록한다. Consumer는 컨테이너가 실행하고, 애플리케이션은 KafkaTemplate으로 메시지 발행을 요청한다.

 

연결 주소, 그룹 ID, 직렬화·역직렬화 클래스처럼 실행 환경에 속하는 값을 application.yml의 spring.kafka 아래로 옮겼다. 이렇게 하면 같은 설정을 Java 코드의 Map과 YAML에 중복해서 적지 않고 설정 파일에서 관리할 수 있다.

옮긴 설정 설정 파일의 위치와 역할
공통 연결 주소 spring.kafka.bootstrap-servers에 localhost:9092를 지정해 Kafka에 처음 연결할 주소를 설정한다.
Consumer 그룹 spring.kafka.consumer.group-id에 consumer-group-id를 지정해 상품 서비스 Consumer가 속할 그룹을 설정한다.
Consumer 시작 위치 정책 spring.kafka.consumer.auto-offset-reset에 earliest를 지정한다. 저장된 유효한 offset이 없을 때 적용한다.
Consumer 역직렬화 spring.kafka.consumer.key-deserializer와 spring.kafka.consumer.value-deserializer에 org.apache.kafka.common.serialization.StringDeserializer를 지정해 수신한 키와 본문을 문자열로 복원한다.
Producer 직렬화 spring.kafka.producer.key-serializer와 spring.kafka.producer.value-serializer에 org.apache.kafka.common.serialization.StringSerializer를 지정해 전송할 키와 본문을 바이트로 변환한다.

주문 객체가 재고 변경으로 이어지는 데이터 변환

주문 서비스는 주문 정보를 JSON 문자열로 만들고, 문자열 직렬화기를 통해 Kafka에 전달한다. 상품 서비스는 받은 바이트를 문자열로 복원한 뒤 JSON을 Map으로 읽어 productId와 qty를 사용한다.

처리 단계 담당 기능
주문 객체 → JSON 문자열 ObjectMapper.writeValueAsString()
문자열 → 전송할 바이트 StringSerializer
수신한 바이트 → 문자열 StringDeserializer
JSON 문자열 → Map ObjectMapper.readValue()

 

주문 생성 후 quickstart-events에 발행한 메시지를 상품 서비스가 수신하고, 해당 상품의 현재 재고에서 주문 수량을 뺀 값을 저장한다. 주문 요청 후 상품 목록을 조회해 재고 변경을 실행 확인했다. 다만 발행 요청 직후의 로그나 주문 HTTP 응답만으로 Consumer의 DB 처리 완료까지 보장되는 것은 아니므로, 상품 조회 결과까지 확인하는 것이 중요하다.

Kafka Connect를 통한 외부 데이터 연계

Kafka Connect는 커넥터 설정으로 외부 시스템과 Kafka 사이의 데이터를 옮긴다. Source 커넥터는 외부 데이터를 Kafka로 가져오고, Sink 커넥터는 Kafka의 데이터를 외부 시스템으로 보낸다. REST API로 커넥터를 등록하고 관리할 수 있으며, 대상 시스템에 맞는 플러그인을 사용한다.

Saga와 보상 트랜잭션

Saga는 여러 서비스의 로컬 트랜잭션을 순서대로 연결하고, 중간 단계가 실패하면 앞서 완료한 작업에 대응하는 보상 트랜잭션을 실행하는 패턴이다. 주문 취소나 재고 복구처럼 업무에 맞는 후속 작업을 정의해야 한다. 오늘의 코드에서 구현한 범위는 주문 이벤트 발행과 재고 차감이며, Kafka Connect와 보상 트랜잭션은 개념으로 정리했다.

오늘의 코드 1 - Spring Kafka 의존성 추가

pom.xml (catalog-service)

<dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
</dependency>

 

상품 서비스와 주문 서비스에 spring-kafka 의존성을 추가했으며, 같은 의존성 선언은 상품 서비스의 코드로 대표해 발췌했다. 이 의존성이 KafkaTemplate과 리스너 기능을 사용할 기반이 되고, 이후 Java 설정 또는 Spring Boot 자동 설정으로 클라이언트를 구성한다.

오늘의 코드 2 - Java 코드로 Consumer 생성 조건 구성

KafkaConsumerConfig.java

// 메시지를 받을 consumer를 만드는 factory
@Bean
public ConsumerFactory<String, String> consumerFactory() {
    Map<String, Object> properties = new HashMap<>();
    properties.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    properties.put(ConsumerConfig.GROUP_ID_CONFIG, "consumer-group-id");
    properties.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
    properties.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
    properties.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class);
    return new DefaultKafkaConsumerFactory<>(properties);
}

 

연결 주소, 그룹 ID, 시작 offset 정책과 역직렬화 클래스를 묶어 문자열 키와 본문을 사용하는 ConsumerFactory를 만드는 코드다. earliest는 저장된 유효한 offset이 없는 경우의 시작 위치를 정하며, 현재는 클래스와 메서드의 등록 어노테이션을 주석 처리하고 YAML 자동 설정으로 전환했다.

오늘의 코드 3 - Consumer를 실행할 리스너 컨테이너 연결

KafkaConsumerConfig.java

// consumer를 실행할 container를 만드는 factory
// container: Kafka에서 메시지를 반복해서 가져오고 받은 메시지를 @KafkaListener 메서드에 전달
@Bean
public ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory() {
    ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory = new ConcurrentKafkaListenerContainerFactory<>();
    kafkaListenerContainerFactory.setConsumerFactory(consumerFactory());
    return kafkaListenerContainerFactory;
}

 

ConsumerFactory를 컨테이너 팩토리에 연결해, 수신한 메시지를 리스너 메서드로 전달하는 실행 환경을 구성한다. 현재 메서드의 @Bean은 주석 처리되어 있으며, Spring Boot의 기본 kafkaListenerContainerFactory를 사용하도록 설정을 옮겼다.

오늘의 코드 4 - Java 코드로 Producer와 KafkaTemplate 구성

KafkaProducerConfig.java

@Configuration
public class KafkaProducerConfig {

    @Bean
    public ProducerFactory<String, String> producerFactory() {
        Map<String, Object> configProperties = new HashMap<>();
        configProperties.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        configProperties.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        configProperties.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        return new DefaultKafkaProducerFactory<>(configProperties);
    }

    @Bean
    public KafkaTemplate<String, String> kafkaTemplate() {
        return new KafkaTemplate<>(producerFactory());
    }
}

 

문자열 직렬화기를 사용하는 ProducerFactory를 만들고 이를 KafkaTemplate에 연결하는 Java 설정 코드다. ProducerFactory는 실제 Kafka Producer 생성에 필요한 설정을 제공하고, KafkaTemplate은 애플리케이션에서 메시지를 보내는 창구가 된다. 현재 등록 어노테이션은 주석 상태로 유지되어 있다.

오늘의 코드 5 - YAML을 이용한 Consumer와 Producer 자동 설정

application.yml (catalog-service)

spring:
  application:
    name: catalog-service
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: consumer-group-id
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      auto-offset-reset: earliest

 

상품 서비스는 consumer-group-id 그룹과 문자열 역직렬화기를 사용하도록 설정했다. Java 코드에서 지정했던 Consumer 설정을 spring.kafka.consumer 아래로 옮겼으며, 현재 파일에는 올바른 bootstrap-servers 키와 역직렬화 클래스 경로가 반영되어 있다.

application.yml (order-service)

spring:
  application:
    name: order-service
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      group-id: consumer-group-id
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer

 

주문 서비스는 같은 Broker 주소와 문자열 직렬화기를 사용해 메시지를 발행한다. 원문에 남아 있는 spring.kafka.producer.group-id는 Spring Boot의 Producer 설정 항목이 아니며, Consumer의 그룹을 지정하거나 발행 대상을 선택하는 데 사용되지 않는다.

오늘의 코드 6 - 주문 객체를 JSON 메시지로 발행

KafkaProducer.java

public void send(String kafkaTopic, OrderDto orderDto) {
    ObjectMapper mapper = new ObjectMapper();
    String jsonInString = "";
    try {
        jsonInString = mapper.writeValueAsString(orderDto);
    } catch (JsonProcessingException e) {
        e.printStackTrace();
    }

    kafkaTemplate.send(kafkaTopic, jsonInString);
    log.info("Kafka Producer send data from Order microservice: " + orderDto);
}

 

주입받은 KafkaTemplate을 사용하기 전에 OrderDto를 JSON 문자열로 변환하고, 전달받은 토픽 이름으로 메시지 발행을 요청한다. 현재 send()의 반환형은 void이며 비동기 전송 완료 결과는 확인하지 않는다. JSON 변환 예외가 나도 이후 로직을 계속 실행하는 구조이므로, 정상 JSON이 만들어진 경로와 예외 경로를 구분해서 이해해야 한다.

오늘의 코드 7 - 주문 생성 흐름에 이벤트 발행 연결

OrderController.java

@PostMapping("/{userId}/orders")
public ResponseEntity<ResponseOrder> createOrder(@PathVariable("userId") String userId,
                                                 @RequestBody RequestOrder orderDetails) {
    log.info("Before add orders data");
    ModelMapper mapper = new ModelMapper();
    mapper.getConfiguration().setMatchingStrategy(MatchingStrategies.STRICT);

    OrderDto orderDto = mapper.map(orderDetails, OrderDto.class);
    orderDto.setUserId(userId);
    /* jpa */
    OrderDto createdOrder = orderService.createOrder(orderDto);
    ResponseOrder responseOrder = mapper.map(createdOrder, ResponseOrder.class);

    kafkaProducer.send("quickstart-events", createdOrder);

    log.info("After added orders data");
    return ResponseEntity.status(HttpStatus.CREATED).body(responseOrder);
}

 

요청의 주문 정보와 사용자 ID로 주문을 생성한 뒤, 생성 결과를 quickstart-events에 전달하도록 연결했다. 주문 요청 후 상품 목록을 조회해 메시지 전달과 재고 변경이 이어지는 것을 실행 확인했다. 주문 저장과 메시지 발행·소비는 하나의 DB 트랜잭션으로 묶여 있지 않으므로 각각의 완료 시점을 구분한다.

오늘의 코드 8 - 주문 이벤트 수신과 상품 재고 차감

CatalogConsumer.java

@KafkaListener(topics="quickstart-events")
public void processMessage(String kafkaMessage) {
    log.info("Received kafka message: {}", kafkaMessage);

    Map<Object, Object> map = new HashMap<>();
    ObjectMapper mapper = new ObjectMapper();
    try {
        map = mapper.readValue(kafkaMessage, new TypeReference<Map<Object, Object>>() {});
    } catch (JsonProcessingException e) {
        e.printStackTrace();
    }

    CatalogEntity catalogEntity = catalogRepository.findByProductId((String) map.get("productId"));
    if (catalogEntity != null) {
        catalogEntity.setStock(catalogEntity.getStock() - (Integer) map.get("qty"));
        catalogRepository.save(catalogEntity);
    }
}

 

@KafkaListener가 같은 토픽의 JSON 메시지를 받아 Map으로 변환하고, 상품 ID로 조회한 상품이 있을 때 주문 수량만큼 재고를 차감해 저장한다. 이 흐름을 통해 주문 서비스가 상품 DB를 직접 수정하지 않고 메시지로 재고 변경을 전달했다. 현재 상품 존재 여부는 검사하지만 수량 검증과 중복 메시지에 따른 재차감 방지는 별도로 구현되어 있지 않다.

어려웠던 점 / 각종 오류

Kafka 설정을 YAML로 옮긴 뒤에도 kafkaListenerContainerFactory()를 직접 등록해야 하는지 헷갈렸다. Consumer 생성 조건과 Consumer를 실행하는 컨테이너의 역할은 서로 다르지만, Spring Boot가 기본 팩토리를 자동 구성할 수 있으므로 현재처럼 별도 기능이 없는 Java 설정은 등록하지 않아도 된다는 점을 이해했다.

 

설정을 옮기는 과정에서 bootstrap-servers을 잘못 작성해 bootstrap-server라고 쓰거나, 직렬화/역직렬화 클래스 경로에 kafka 패키지를 빼먹는 등 오타로 인한 오류가 있었다.
