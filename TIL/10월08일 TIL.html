오늘의 한 줄 요약

  • 로그인 정보는 Spring Security가 검증하고, 인증에 성공하면 User Service가 JWT를 발급한다.
  • Gateway는 회원가입·로그인과 사용자 조회 경로를 나누고, 조회 요청의 JWT를 검사한다.
  • 비밀번호는 BCrypt 해시로 저장하고, 입력값을 저장된 salt와 비용 설정으로 검증한다.
  • Spring Cloud Config로 설정을 외부 Git 저장소에서 관리하고, 실행 중인 서비스에는 재시작이나 refresh로 반영한다.

오늘 배운 것

BCrypt로 비밀번호를 저장하고 비교하는 방법

회원가입 시 원문 비밀번호를 그대로 저장하지 않고 BCrypt 해시로 바꿔 저장한다. BCrypt 해시 문자열에는 salt와 비용 설정이 포함되며, 로그인 시에는 이를 이용해 입력 비밀번호가 저장된 해시와 일치하는지 확인한다.

// encode()는 새로운 salt로 저장용 해시를 만든다.
BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();
String savedHash = encoder.encode("study-password");

// 저장된 해시를 복호화하지 않고 입력값이 일치하는지 검증한다.
boolean correct = encoder.matches("study-password", savedHash); // true
boolean wrong = encoder.matches("different-password", savedHash); // false

같은 비밀번호에 encode()를 다시 호출해 문자열끼리 비교하면 salt가 달라질 수 있다. 비밀번호 확인에는 matches()를 사용하며, 현재 로그인 흐름에서는 Spring Security가 등록된 인코더를 통해 이 비교를 수행한다.

보안 설정, 로그인 처리와 토큰 검사의 역할 구분

세 클래스는 실행되는 위치와 시점이 다르다. 서버 시작 시 보안 설정을 연결하고, 로그인 시 계정을 확인하며, 로그인 이후 조회 요청에서는 토큰을 검사한다.

클래스 위치·실행 시점 담당하는 일
WebSecurity User Service의 보안 설정 구성 시 사용자 조회 서비스와 비밀번호 인코더를 연결하고 로그인 필터·접근 규칙을 등록한다.
AuthenticationFilter User Service의 POST /login 처리 시 JSON에서 이메일·비밀번호를 읽어 인증을 요청하고, 성공하면 JWT를 발급한다.
AuthorizationHeaderFilter Gateway의 보호된 조회 요청 처리 시 요청 헤더의 JWT를 검증하고 통과 또는 거절을 결정한다.

AuthenticationFilter는 UsernamePasswordAuthenticationFilter를 상속하므로 기본적으로 POST /login을 처리한다. 현재 코드는 폼 로그인 화면을 설정한 것이 아니라 JSON 로그인 필터를 등록한 구조이며, 별도의 로그인 Controller 매핑이 필요하지 않다.

UserDetailsService.loadUserByUsername()은 DB에서 인증에 필요한 정보를 가져오는 역할이다. 현재 username에는 이메일을 사용하고, 비밀번호 비교는 AuthenticationManager가 위임한 인증 처리자가 담당한다. UsernamePasswordAuthenticationToken은 이 과정에서 쓰는 내부 인증 객체이며 JWT와 다르다.

세션 인증과 JWT 인증의 차이

로그인 이후 요청에서 사용자를 확인하는 방법은 로그인 상태를 어디에 두는지에 따라 달라진다. 토큰 기반 인증에는 여러 방식이 있으며, 오늘 실습은 JWT를 발급하고 검증하는 방식이다.

구분 세션 기반 인증 JWT 기반 인증
로그인 결과 서버의 세션을 식별할 세션 ID를 전달한다. 보통 쿠키를 사용한다. 사용자 정보와 만료 시각 등을 담아 서명한 JWT를 전달한다.
다음 요청 쿠키의 세션 ID로 서버 측 상태를 조회한다. 클라이언트가 Authorization 헤더에 토큰을 넣고 서버가 검증한다.
여러 서버에서 처리 동일한 세션을 찾도록 저장소 공유나 요청 배치 전략이 필요하다. 검증에 필요한 키를 가진 서버가 토큰을 검증할 수 있다.
모바일 사용 네이티브 앱에서도 쿠키·세션 ID를 직접 관리하면 사용할 수 있다. 앱이 토큰을 보관하고 요청 헤더에 넣어 사용할 수 있다.

JWT는 서버 측 세션 조회 없이 인증할 수 있는 stateless 구조에 사용할 수 있다. 다만 JWT 사용만으로 서비스 전체가 자동으로 stateless가 되거나, CDN 캐싱·영구 로그인·CSRF 방어가 보장되는 것은 아니다. 클라이언트가 토큰을 저장해도 만료 시각은 그대로 적용된다.

// 개념 예시: 사용자 식별자를 담고 키로 서명한 JWT를 만든다.
// key는 미리 준비한 서명 키이며, 서명은 본문 암호화와 다르다.
String jwt = Jwts.builder().subject("member-1").signWith(key).compact();

실습 JWT의 sub에는 사용자 ID, iat에는 발급 시각, exp에는 만료 시각이 들어간다. User Service는 발급한 토큰을 응답의 token 헤더로 전달하고, 이후 클라이언트는 Authorization: Bearer 토큰으로 보낸다.

Gateway 경로 변환과 로그인 이후의 JWT 검증

Gateway의 외부 경로와 User Service가 처리하는 내부 경로를 구분해야 한다. RewritePath는 /user-service 접두사를 제거해 Controller와 로그인 필터가 기대하는 경로로 전달한다.

Gateway 요청 User Service 내부 경로 Gateway JWT 검사
POST /user-service/users POST /users 없음: 회원가입
POST /user-service/login POST /login 없음: 로그인
GET /user-service/users GET /users 있음: 사용자 목록 조회
GET /user-service/users/{userId} GET /users/{userId} 있음: 사용자 상세 조회
GET /user-service/health-check GET /health-check 있음: 현재 GET 라우트에 포함됨 
# 로그인 이후 요청에서 발급받은 토큰을 Bearer 형식으로 전달한다.
GET /user-service/users HTTP/1.1
Authorization: Bearer 발급받은_JWT

필터는 Authorization 헤더 존재 여부를 확인하고 토큰을 파싱해 서명·만료와 비어 있지 않은 subject를 검사한다. 실패하면 401 Unauthorized를 반환하고, 성공하면 chain.filter(exchange)로 다음 처리에 전달한다.

User Service의 일반 접근 규칙은 현재 지정 IP 허용이며, 앞의 /** 규칙이 모든 경로를 잡아 뒤의 anyRequest().authenticated()에 도달하지 않는다. 따라서 8083으로 직접 접근하는 요청과 Gateway를 거친 요청은 JWT 검사 경로가 다르다. 현재 토큰 검사에는 경로의 사용자 ID와 토큰의 사용자 ID를 비교하는 로직도 없다.

CSR과 SSR은 화면을 만드는 위치의 차이

인증 방식과 화면 렌더링 방식은 구분해서 이해해야 한다. 세션 인증이 반드시 서버 렌더링 HTML을 반환해야 하는 것은 아니며, 세션·JWT 어느 방식에서도 JSON 응답을 사용할 수 있다.

구분 화면을 만드는 위치와 흐름
CSR 브라우저 등 클라이언트가 JavaScript와 전달받은 데이터를 이용해 화면을 구성한다.
SSR 서버가 데이터를 반영한 HTML을 구성해 클라이언트에 전달한다.

Spring Cloud Config로 설정을 외부 Git 저장소에서 관리

각 서비스에 흩어진 설정을 외부 저장소에서 관리하고, Config Server가 이를 읽어 서비스에 제공한다. User Service는 Config Client로 동작하며, 현재 bootstrap.yml에서 Config Server 주소와 설정 이름 ecommerce를 지정한다.

현재 Config Server는 8888 포트에서 실행하도록 설정되어 있으며 F:/remoteSettings Git 저장소의 main 브랜치를 읽는다. /ecommerce/default는 ecommerce 설정의 기본 프로필을 조회하는 경로이고, 응답의 propertySources에서 설정 출처, version에서 Git 버전을 확인할 수 있다.

# 외부 설정 저장소에서 실행: 변경한 설정을 Git 버전으로 기록한다.
Set-Location F:\remoteSettings
git add ecommerce.yml
git commit -m "Update configuration"

설정만 바꾸는 경우 각 서비스의 코드를 다시 빌드할 필요는 없다. 그러나 Config Server에서 변경된 값이 조회되는 것과 이미 실행 중인 User Service의 Environment가 갱신되는 것은 별도 단계이다.

환경별 프로필 설정과 설정 우선순위

수업메모에서는 개발용 DEV, 사용자 인수 테스트용 UAT, 운영용 PROD처럼 환경에 맞는 설정을 구분했다. 프로필을 선택하면 해당 환경의 설정과 공통 설정을 함께 읽으며, 같은 키는 더 구체적인 설정이 우선한다.

설정 파일 적용 범위와 우선순위
원격 application.yml 여러 애플리케이션이 공유하는 공통 설정
원격 ecommerce.yml ecommerce 설정에 공통으로 적용하며 원격 공통 설정보다 우선
원격 ecommerce-dev.yml dev 프로필일 때 적용하며 같은 키의 ecommerce 기본 설정보다 우선
서비스의 로컬 application.yml 현재 bootstrap 방식에서는 원격 설정이 기본적으로 우선하며, override 정책에 따라 달라질 수 있음 
# 개념 예시: dev 환경의 설정을 선택한다.
# Config Server는 /ecommerce/dev에서 프로필별 설정과 공통 설정을 제공한다.
spring:
  profiles:
    active: dev

원격 저장소 안의 같은 키는 ecommerce-dev.yml → ecommerce.yml → application.yml 순으로 우선한다. /ecommerce/default를 조회하면서 dev 또는 prod 파일을 수정해도 그 프로필의 값은 적용되지 않는다.

Actuator로 상태를 확인하고 변경된 설정을 다시 읽기

Spring Boot Actuator는 애플리케이션 상태 확인과 관리·모니터링용 HTTP 엔드포인트를 제공한다. 라이브러리 추가, HTTP 노출 설정, Spring Security 접근 규칙은 서로 다른 조건이며 모두 확인해야 한다.

요청 역할
GET /actuator/health 애플리케이션 상태 확인
POST /actuator/refresh Config Client가 설정을 다시 읽고 refresh 대상에 변경을 반영
GET /actuator/beans 등록된 Bean 정보 확인
GET /actuator/info 구성된 애플리케이션 정보 확인 
# 설정 저장·커밋 후 실행할 갱신 요청 예시이다.
# 브라우저 주소창의 GET 요청과 달리 refresh에는 POST를 사용한다.
Invoke-RestMethod -Method Post -Uri http://localhost:8083/actuator/refresh
변경 반영 방법 동작과 범위
서비스 재시작 시작 과정에서 설정을 다시 읽는다. 설정만 바꾼 경우 코드 재빌드는 필요하지 않다.
Actuator refresh 대상 서비스에 갱신을 요청한다. 변경값을 필드에 고정한 모든 객체가 자동으로 다시 만들어지는 것은 아니다.
Spring Cloud Bus 여러 인스턴스에 갱신을 전달하는 방법으로 소개되었으며, 오늘 자료 범위에서는 구성 실습까지 다루지 않았다.

관리 엔드포인트의 라이브러리는 pom.xml의 일반 dependencies에 넣어야 한다. dependencyManagement는 버전과 설정을 관리하며, 여기에만 선언하면 실제 실행 의존성으로 추가되지 않는다.

오늘의 코드 1 - BCrypt 저장과 이메일 기반 사용자 정보 조회

UserServiceImpl.java

        userEntity.setEncryptedPwd(passwordEncoder.encode(userDto.getPwd()));

        userRepository.save(userEntity);

 

회원가입 시 비밀번호를 BCrypt 해시로 바꿔 Entity에 넣고 DB에 저장한다. 저장된 해시는 로그인 검증에 사용하며, 원문 비밀번호로 복호화하지 않는다.

UserRepository.java

    UserEntity findByEmail(String email);

 

findByEmail()은 이메일로 사용자 정보를 조회하는 Repository 메서드이다. 현재 로그인 식별자로 이메일을 사용하므로 로그인 정보 조회가 이 메서드로 연결된다.

UserServiceImpl.java

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        UserEntity userEntity = userRepository.findByEmail(username);

        if (userEntity == null)
            throw new UsernameNotFoundException(username + ": not found");

        return new User(userEntity.getEmail(), userEntity.getEncryptedPwd(),
                true, true, true, true,
                new ArrayList<>());
    }

 

이메일로 조회한 계정과 저장된 비밀번호 해시를 Spring Security의 User 객체로 반환한다. 사용자가 없으면 예외를 발생시키며, 반환된 정보로 비밀번호를 비교하는 작업은 등록된 인증 처리자가 맡는다.

오늘의 코드 2 - 인증 관리자 구성과 로그인 필터 등록

WebSecurity.java

        AuthenticationManagerBuilder authenticationManagerBuilder =
                http.getSharedObject(AuthenticationManagerBuilder.class);
        authenticationManagerBuilder.userDetailsService(userService).passwordEncoder(bCryptPasswordEncoder);

        AuthenticationManager authenticationManager = authenticationManagerBuilder.build();

 

사용자 조회 구현과 BCrypt 인코더를 연결해 인증 관리자를 만든다. 이 설정을 통해 로그인 필터가 전달한 이메일·비밀번호를 DB의 사용자 정보와 비교할 수 있다.

WebSecurity.java

            .authenticationManager(authenticationManager)
            .addFilter(getAuthenticationFilter(authenticationManager))

 

직접 만든 로그인 필터를 보안 필터 체인에 등록하고 같은 인증 관리자를 사용하게 한다. WebSecurity는 JWT를 직접 발급하는 클래스가 아니라 인증 처리에 필요한 구성과 접근 규칙을 연결하는 클래스이다.

오늘의 코드 3 - JSON 로그인 요청을 읽고 인증을 위임

RequestLogin.java

@Data
public class RequestLogin {
    @NotNull(message = "Email cannot be null")
    @Size(min = 2, message = "Email not be less than two characters")
    @Email
    private String email;

    @NotNull(message = "Password cannot be null")
    @Size(min = 8, message = "Password must be equals or grater than 8 characters")
    private String password;
}

 

로그인 요청의 이메일과 비밀번호를 담는 모델이다. 검증 애너테이션은 선언되어 있지만, 필터에서 ObjectMapper로 읽는 것만으로 제약 검증이 자동 실행되는 것은 아니다.

AuthenticationFilter.java

    @Override
    public Authentication attemptAuthentication(HttpServletRequest req,
                                                HttpServletResponse res) throws AuthenticationException {
        try {
            // 로그인 요청의 본문(JSON)을 읽어서 RequestLogin 객체로 변환하는 코드
            RequestLogin creds = new ObjectMapper().readValue(req.getInputStream(), RequestLogin.class);

            // 사용자 이메일과 패스워드를 가지고 인증 처리를 요청
            return getAuthenticationManager().authenticate(
                    new UsernamePasswordAuthenticationToken(
                            creds.getEmail(),
                            creds.getPassword(),
                            new ArrayList<>()
                    )
            );

        } catch (IOException e) {
            throw new RuntimeException(e);
        }
    }

 

POST /login의 JSON 본문을 읽어 이메일과 비밀번호를 인증 관리자에게 전달한다. UsernamePasswordAuthenticationToken은 Spring Security 내부 인증 정보이며, 이후 발급할 JWT와는 별개이다.

오늘의 코드 4 - 인증 성공 후 JWT 발급과 응답 헤더 전달

AuthenticationFilter.java

    @Override
    protected void successfulAuthentication(HttpServletRequest req, HttpServletResponse res,
                                            FilterChain chain, Authentication authResult)
            throws IOException, ServletException {
        // JWT 발행을 위한 준비
        String userName = ((User) authResult.getPrincipal()).getUsername(); // email
        UserDto userDetails = userService.getUserDetailsByEmail(userName); // JWT에 담을 정보를 가져오기 위해

        // JWT 발행
        byte[] secretKeyBytes = environment.getProperty("token.secret").getBytes(StandardCharsets.UTF_8);

        SecretKey secretKey = Keys.hmacShaKeyFor(secretKeyBytes);

        Instant now = Instant.now();

        String token = Jwts.builder()
                .subject(userDetails.getUserId())
                .expiration(Date.from(now.plusMillis(Long.parseLong(environment.getProperty("token.expiration-time")))))
                .issuedAt(Date.from(now))
                .signWith(secretKey)
                .compact();

        res.addHeader("token", token);
        res.addHeader("userId", userDetails.getUserId());
    }

 

인증된 이메일로 사용자 ID를 조회하고 발급·만료 시각을 담아 JWT에 서명한다. 토큰과 사용자 ID는 응답 헤더의 token, userId로 전달하며, 현재 메서드는 응답 본문에 토큰을 쓰지 않는다.

AuthorizationHeaderFilter.java

            // 1. Authorization 헤더가 존재하는지 존재하지 않는지를 먼저 검증
            if (!request.getHeaders().containsKey(HttpHeaders.AUTHORIZATION)) {
                return onError(exchange, "No authorization header", HttpStatus.UNAUTHORIZED);
            }

            // 2. 헤더가 존재한다면, JWT 토큰이 실제로 존재하는지를 검증
            String authorizationHeader = request.getHeaders().get(HttpHeaders.AUTHORIZATION).get(0);
            String jwt = authorizationHeader.replace("Bearer ", "");

            // 3. 토큰이 존재한다면, JWT라는 토큰이 우리가 발했했던 토큰이 맞는지, 유효시간 안에 사용할 수 있는 정상적인 토큰인지 검증
            if (!isJwtValid(jwt)) {
                return onError(exchange, "JWT token is not valid", HttpStatus.UNAUTHORIZED);
            }

            return chain.filter(exchange);

 

헤더가 없거나 토큰 검증에 실패하면 401 응답으로 요청 처리를 끝낸다. 검증에 성공했을 때만 chain.filter(exchange)를 실행해 다음 필터와 대상 서비스로 전달한다.

AuthorizationHeaderFilter.java

    private boolean isJwtValid(String jwt) {
        byte[] secretKeyBytes = env.getProperty("token.secret").getBytes();
        SecretKey signingKey = new SecretKeySpec(secretKeyBytes, SignatureAlgorithm.HS512.getJcaName());

        boolean returnValue = true;
        String subject = null;

        try {
            JwtParser jwtParser = Jwts.parser()
                    .setSigningKey(signingKey)
                    .build();

            subject = jwtParser.parseClaimsJws(jwt).getBody().getSubject(); // userId
        } catch (Exception ex) {
            returnValue = false;
        }

        if (subject == null || subject.isEmpty()) {
            returnValue = false;
        }

        return returnValue;
    }

 

설정에서 읽은 키를 이용해 JWT를 파싱하고 사용자 식별자인 subject를 확인한다. 파싱 예외나 빈 subject는 검증 실패로 처리하며, 경로의 사용자 ID와 subject를 비교하는 로직은 현재 없다.

어려웠던 점 / 각종 오류

로그인 Controller가 없는데 /login이 동작하는 이유와 세 보안 클래스의 역할이 처음에는 혼동되었다. 기본 로그인 경로를 가진 필터를 WebSecurity가 등록하고, 계정 확인은 AuthenticationFilter, 이후 토큰 검사는 Gateway의 AuthorizationHeaderFilter가 담당한다는 흐름으로 구분했다. 메모에 기록된 로그인 404는 외부 경로와 내부 필터 경로를 맞추는 RewritePath로 해결하는 경로 문제이다.

8083 서비스에서 중단점이 동작하지 않는 것처럼 보였지만, 당시 실행 프로세스에는 디버그 옵션이 있는 것을 확인했다. attemptAuthentication()은 POST /login 요청에서 실행되므로 브라우저 주소창의 GET 요청이나 사용자 조회 요청과 구분해야 한다. 실제 요청 방식과 IntelliJ의 중단점 설정을 모두 확인하지 못했으므로 원인을 특정 설정으로 단정하지 않았다.

Config Server에서 비밀 키 변경이 보이지 않는 문제를 확인할 때는 수정한 파일, 조회 프로필, Git 버전을 먼저 구분해야 했다. 당시 /ecommerce/default의 응답은 저장소의 ecommerce.yml과 일치했고, dev·prod 파일의 값은 달랐다. Git 방식에서는 변경을 저장·커밋한 뒤 조회 출처를 확인하고, 실행 중인 서비스의 설정 갱신은 별도로 재시작 또는 refresh로 처리한다.

/actuator/health에서 404와 No static resource actuator/health가 반환되었다. 당시 Actuator가 실행 의존성에 없었고, 원인은 의존성을 일반 dependencies가 아닌 dependencyManagement에만 넣은 것이었다. 현재 파일에서는 위치가 수정되어 있으며, Maven 프로젝트 새로고침과 서비스 재시작이 필요하다. 수정 후 health 성공 응답이나 refresh 실행 결과는 아직 확인하지 않았다.
