오늘의 한 줄 요약

  • 소프트웨어 아키텍처는 구성 요소와 관계를 정의하고, UML은 그 구조를 이해관계자에게 전달하는 공통 언어다.
  • 클라우드 네이티브는 확장성, 변화 대응, 장애 격리를 고려하며 DevOps, CI/CD, 컨테이너 등의 방식으로 개발과 운영을 연결한다.
  • 마이크로서비스는 비즈니스 기능별 독립적인 개발·배포·확장을 가능하게 하지만, 통신과 데이터 일관성 관리의 복잡성이 커진다.
  • REST API는 자원 중심의 URI, HTTP 메서드와 상태 코드, 일관된 규칙을 통해 사용자가 이해하기 쉽게 설계한다.

오늘 배운 것

소프트웨어 아키텍처와 UML의 역할

  • 소프트웨어 아키텍처는 모듈, 서비스, 함수 등 시스템을 이루는 요소와 이들이 연결되는 관계를 정의한다. 각 요소의 역할과 협력 방식을 파악하는 기준이 된다.
  • 개발자와 운영자 등 이해관계자는 시스템을 이해하는 수준과 관심사가 다르다. UML(Unified Modeling Language)은 구조와 동작을 공통된 표기법으로 표현해 의사소통을 돕는다.
  • 아키텍트는 시스템의 전체 구조를 고려하고, 팀이 어떤 방향으로 설계하고 구현할지 제시하는 역할을 한다.

IT 시스템의 변화와 회복 탄력성

수업에서는 IT 시스템의 변화를 하드웨어 중심에서 분산 시스템으로, 다시 클라우드 네이티브와 지속적인 가치 개선으로 이어지는 큰 흐름으로 정리했다.

시기 수업에서 정리한 중심 흐름
1960~1980년대 메인프레임과 하드웨어 중심의 시스템
1990~2000년대 분산화와 견고한 시스템에 대한 관심 확대
2010년대 이후 클라우드 네이티브, 회복 탄력성, 사용자에게 전달하는 가치의 지속적인 개선
  • 회복 탄력성(Resilience)은 장애나 변화가 발생해도 서비스를 유지하거나 정상 상태로 회복하는 능력이다.
  • 안티프래질(Anti-fragile)은 충격과 변화에서 학습해 더 나아지는 성질을 뜻한다. 장애를 견디거나 회복하는 것에서 한 단계 더 나아가 개선을 강조한다.
  • Chaos Engineering은 장애 상황을 통제된 범위에서 실험해 취약점을 찾는 활동이다. 실험으로 얻은 결과를 개선에 반영하며 회복 능력을 높인다.

클라우드 네이티브 아키텍처의 확장성과 장애 격리

클라우드 네이티브 아키텍처는 부하와 환경 변화에 대응하고, 일부 장애의 영향이 시스템 전체로 퍼지는 것을 줄이도록 설계한다.

  • 확장 가능한 구조: 실행 인스턴스를 늘려 부하를 분산하고, 모니터링으로 확장이 필요한 시점을 파악한다.
  • 탄력적인 구조: 서비스 분리와 배포 자동화로 변경을 빠르게 반영한다. 서비스 인스턴스의 추가·삭제를 감지해 통신 대상을 갱신하는 구조도 필요하다.
  • 무상태 처리: 특정 인스턴스에만 필요한 요청 처리 상태가 묶이지 않도록 설계하면 여러 인스턴스에 요청을 분산하기 쉬워진다.
  • 장애 격리: 한 서비스의 장애가 다른 서비스로 전파되지 않도록 통신과 의존 관계를 설계한다. 서비스를 분리했다는 사실만으로 장애 격리가 보장되지는 않는다.
확장 방식 변경하는 대상
Scale Out / Scale In 서버·인스턴스 수를 늘리거나 줄이는 수평 확장·축소
Scale Up / Scale Down 개별 서버의 CPU·메모리 등 자원 크기를 높이거나 낮추는 수직 확장·축소

Auto Scaling은 부하와 정책에 따라 자원을 자동으로 조절하는 방식이다. 수평·수직이라는 구분은 무엇을 확장하는지에 대한 구분이고, 자동 확장은 그 조절을 자동화하는지에 대한 구분이다.

DevOps, CI/CD, 컨테이너로 개발과 운영 연결하기

DevOps는 개발과 운영을 끊임없이 협력시키는 문화다. CI/CD는 변경 사항을 검증하고 전달하는 흐름을 자동화하며, 컨테이너는 애플리케이션과 필요한 실행 환경을 묶는 역할을 한다.

구분 역할과 배포 시점
Continuous Integration 변경 코드를 자주 통합하고 빌드와 테스트로 문제를 빠르게 확인한다.
Continuous Delivery 검증된 변경을 언제든 배포할 수 있는 상태로 유지한다. 운영 배포에는 사람의 승인이나 실행 단계를 둘 수 있다.
Continuous Deployment 검증을 통과한 변경을 운영 환경에 배포하는 단계까지 자동화한다.

CD는 문맥에 따라 Continuous Delivery 또는 Continuous Deployment를 가리킨다. 두 방식은 빌드 결과물 생성뿐 아니라 검증과 배포 준비를 포함하며, 운영 배포를 자동으로 수행하는지에서 차이가 난다.

배포 전략 트래픽을 전환하는 방법
카나리 배포 일부 사용자나 요청에 새 버전을 제공하고, 상태를 확인하면서 적용 비율을 늘린다.
블루그린 배포 기존 버전과 새 버전의 환경을 준비하고, 새 환경이 준비되면 트래픽을 전환한다.

컨테이너는 애플리케이션과 실행에 필요한 라이브러리·설정을 패키징해 격리된 환경에서 실행한다. 실행 환경을 일관되게 구성하는 데 도움이 되며, 배포 자동화와 함께 활용할 수 있다.

12-Factor App과 추가로 고려할 세 가지 관점

12-Factor App은 서비스형 애플리케이션을 개발하고 운영하기 위한 원칙이다. 오늘 수업에서는 설정, 의존성, 실행 상태, 환경 일관성, 로그와 관리 작업을 중심으로 살펴봤다.

  • 설정과 코드 분리: 환경마다 달라지는 설정을 코드와 분리해 관리한다.
  • 의존성 선언과 격리: 필요한 외부 라이브러리를 명시하고, 실행 환경에 우연히 설치된 항목에 기대지 않는다.
  • 무상태 프로세스: 특정 실행 프로세스에만 상태를 저장하지 않도록 구성한다.
  • 빠른 시작과 안전한 종료: 프로세스를 빠르게 시작하고 정상적으로 종료할 수 있게 해 교체와 확장에 대응한다.
  • 환경 차이 최소화: 개발과 운영 환경을 가능한 한 비슷하게 유지한다. 빌드·릴리스·실행 단계도 구분한다.
  • 로그와 관리 작업: 로그는 외부에서 수집·처리할 수 있는 이벤트 흐름으로 내보내고, 관리 작업은 일회성 프로세스로 실행한다.

수업에서는 여기에 API First, Telemetry, Authentication and Authorization을 더한 관점도 다뤘다.

추가 관점 고려할 내용
API First 서비스 간 약속인 API를 먼저 설계해 각 서비스의 개발 기준을 맞춘다.
Telemetry 로그와 지표 등으로 서비스의 상태와 동작을 파악한다.
Authentication and Authorization 요청자의 신원을 확인하는 인증과 허용된 작업을 확인하는 인가를 설계에 포함한다.

모놀리스와 마이크로서비스의 차이

모놀리스는 여러 기능을 하나의 애플리케이션으로 배포하고, 마이크로서비스는 비즈니스 기능을 중심으로 서비스를 나누어 독립적으로 운영한다. 서비스의 크기보다 독립적으로 변경하고 배포할 수 있는 경계가 중요하다.

비교 기준 모놀리스 마이크로서비스
변경과 배포 일부 기능을 바꿔도 애플리케이션 단위로 빌드·테스트·배포한다. 변경한 서비스를 독립적으로 빌드·테스트·배포할 수 있다.
통신 주로 같은 애플리케이션 안에서 호출한다. 서비스 간 네트워크 통신과 그에 따른 지연·실패를 고려한다.
확장 애플리케이션 전체를 확장하는 방식이 기본이다. 부하가 큰 서비스를 선택해 독립적으로 확장할 수 있다.
데이터 관리 여러 기능이 데이터 저장소를 공유하기 쉽다. DB 개수는 설계에 따라 달라진다. 서비스별 데이터 소유권을 분리하며, 여러 서비스에 걸친 일관성을 관리해야 한다.
기술 선택 하나의 애플리케이션 안에서 기술 스택을 함께 맞추는 경우가 많다. 서비스별로 적합한 언어와 데이터 저장 기술을 선택할 수 있다.
이해와 운영 초기에는 흐름 추적과 배포가 단순하지만, 규모가 커지면 결합 관계가 복잡해질 수 있다. 개별 서비스의 범위는 작아지지만, 전체 시스템의 통신·배포·운영은 복잡해진다.

모놀리스도 애플리케이션 전체를 수평 확장할 수 있다. 마이크로서비스의 장점은 필요한 부분만 독립적으로 확장하는 데 있으며, 어느 구조의 성능이 항상 더 좋다고 단정할 수는 없다.

마이크로서비스에서는 서비스마다 변경 주기, 배포 생명주기, 필요한 자원량이 다를 수 있다. 서로 다른 언어와 DB를 선택하는 Polyglot Technology도 가능하지만, 서비스 간 약속은 일관되게 유지해야 한다.

마이크로서비스 설계와 Saga의 보상 처리

마이크로서비스 설계에서는 기능을 나누는 것에 그치지 않고, 나눈 서비스가 어떻게 통신하고 데이터를 변경하며 운영되는지 함께 결정해야 한다.

  • Decomposition: 비즈니스 기능을 기준으로 서비스의 책임과 경계를 나눈다.
  • Communications: 서비스 간에 어떤 요청과 응답을 주고받을지 정한다.
  • Data Management: 서비스가 소유하는 데이터와 다른 서비스에서 접근하는 방식을 정한다.
  • Transaction Management: 여러 서비스에 걸친 작업의 성공·실패와 데이터 일관성을 관리한다.
  • Deployment: 서비스별로 독립적인 변경과 배포가 가능하도록 구성한다.
  • Resilience: 일부 서비스의 장애가 발생했을 때 영향 범위와 회복 방식을 정한다.

Saga는 여러 서비스의 로컬 트랜잭션을 순서대로 연결해 하나의 업무 흐름을 처리하는 방식이다. 각 서비스에서 이미 완료된 작업은 하나의 DB 트랜잭션처럼 함께 롤백하기 어려우므로, 실패 시 완료된 작업의 효과를 되돌리는 보상 트랜잭션을 수행한다.

서비스마다 변경 속도와 운영 주기가 다르므로, 팀도 담당 서비스의 개발과 운영을 책임질 수 있게 구성한다. 수업에서는 약 6~8명 규모의 팀을 예로 들었으며, 외부 의존성과의 상호작용을 단순하게 유지하는 점도 강조했다.

MSA의 Inner Architecture와 Outer Architecture

수업에서는 개별 서비스 내부의 구조를 Inner Architecture, 여러 서비스가 함께 동작하도록 지원하는 공통 기반을 Outer Architecture로 나누어 살펴봤다. 하나의 서비스는 여러 실행 인스턴스로 운영될 수 있다.

공통 기반 요소 역할
External Gateway 외부 요청의 진입점으로서 요청을 내부 서비스에 연결한다.
Service Mesh 서비스 간 통신을 관리하는 기반이다.
Runtime Platform 서비스 인스턴스를 실행하고 관리하는 환경이다.
Backing Services 애플리케이션이 의존하는 DB 등 외부 자원이다.
Telemetry 서비스의 상태와 동작을 파악할 운영 데이터를 수집한다.
CI/CD Automation 서비스의 통합·검증·배포 흐름을 자동화한다.

RESTful 웹 서비스의 성숙도 Level 0~3

Richardson 성숙도 모델은 웹 API가 자원, HTTP의 의미, 하이퍼미디어를 어느 수준까지 활용하는지 설명한다.

단계 핵심 특징
Level 0 HTTP를 메시지 전달 수단으로 사용하고, 자원과 메서드의 의미를 충분히 활용하지 않는다.
Level 1 각 자원을 구분하는 URI를 사용한다.
Level 2 자원별 URI에 더해 HTTP 메서드와 상태 코드의 의미를 활용한다.
Level 3 응답에 다음으로 가능한 동작을 안내하는 링크를 포함한다.

Level 3에서 다루는 HATEOAS는 데이터만 반환하는 데서 더 나아가 클라이언트가 이어서 할 수 있는 동작도 안내하는 방식이다.

사용자 중심의 REST API 설계

REST API를 설계할 때는 사용하는 사람이 어떤 자원을 다루고 무엇을 할 수 있는지 쉽게 이해할 수 있어야 한다. 자원 이름과 작업의 의미를 일관되게 표현하는 것이 중요하다.

  • URI는 자원을 나타내는 명사를 중심으로 구성한다. 목록 자원에는 /users처럼 복수형 이름을 일관되게 사용한다.
  • 작업은 HTTP 메서드의 의미로 구분하고, 결과는 적절한 응답 상태 코드로 전달한다.
  • URI에 비밀번호나 토큰 등 보안에 민감한 정보를 넣지 않는다.
  • 같은 자원을 다루는 API는 경로 구조와 메서드 사용 규칙을 일관되게 유지한다.
# HTTP 요청 설계 예시: 실제 서버에서 실행한 코드가 아니다.
# 목록 자원을 복수형 명사로 표현하고, GET으로 조회한다.
GET /users HTTP/1.1

# 같은 star 자원에 PUT을 사용해 별표 상태를 설정한다.
PUT /gists/42/star HTTP/1.1

# 같은 경로에 DELETE를 사용해 별표 상태를 해제한다.
DELETE /gists/42/star HTTP/1.1

위 예시에서 자원은 URI로 표현하고, 수행할 작업은 HTTP 메서드로 구분한다. PUT /gists/{id}/star와 DELETE /gists/{id}/star처럼 경로를 맞추면 관련 동작의 관계를 파악하기 쉽다.
