#### Path Variable 방식 사용 시 데이터 인코딩하기

Path Variable 방식 사용 시 데이터를 그대로 URL에 포함해 보낸다면 데이터가 사용자에게 노출될 수 있다. React에서 가리고 싶은 데이터에 대해 `encodeURIComponent()`를 적용하면 알아볼 수 없는 문자열로 변환된다.

```
api.patch(
    `/comments/update/${id}/${encodeURIComponent(mention)}`,
    null,
    { headers: { Authorization: at || "" } }
);
```

#### 전역 예외 처리

`HandlerExceptionResolver`는 Spring 프레임워크 내부에서 예외를 처리하는 전역 Resolver가 등록되어 있는 인터페이스다. Controller가 처리하지 않은 예외가 `DispatcherServlet`까지 올라오면 등록된 Resolver 중 해당 예외를 처리할 수 있는 것을 찾는다.

이때 `@RestControllerAdvice`와 `@ExceptionHandler`를 이용해 사용자 정의 예외를 `HandlerExceptionResolver`에 등록할 수 있다.

`@RestControllerAdvice`  
여러 Controller에서 발생하는 예외를 한 곳에서 처리할 클래스를 지정한다.

```
@RestControllerAdvice
public class GlobalExceptionHandler {
}
```

위 코드는 GlobalExceptionHandler에 사용자 지정 예외를 등록하라는 의미이다.

`@ExceptionHandler`  
어떤 예외를 어떤 메서드가 처리할지 지정한다.

```
@ExceptionHandler(LoginFailException.class)
```

위 코드는 LoginFailException 또는 그 하위 예외가 발생했을 때 해당 메서드를 실행하라는 의미이다.

Service에서 로그인 사용자를 찾지 못하면 일반 `RuntimeException` 대신 사용자 정의 예외인 `LoginFailException`을 발생시켰다. Controller에서 직접 처리하지 않은 예외는 Spring MVC의 예외 처리 흐름으로 전달되며, `@RestControllerAdvice`로 등록한 `GlobalExceptionHandler`의 `@ExceptionHandler` 메서드가 해당 예외를 처리한다. 처리할 수 없는 예외는 최종적으로 500 응답이 될 수 있으므로, 예상 가능한 로그인 실패를 `401 Unauthorized`와 오류 응답 객체로 변환했다.

```
@ExceptionHandler(LoginFailException.class)
public ResponseEntity<?> handlerLoginFail(LoginFailException e) {
    ErrorResponse error = new ErrorResponse(e.getMessage());
    return ResponseEntity.status(HttpStatus.UNAUTHORIZED).body(error);
}
```

#### 요청 유효성 검사와 React 오류 표시

메서드 실행 시 특정 매개변수에 대해서 자동으로 유효성 검사를 수행하도록 할 수 있다. 클래스 정의 시 검증하고 싶은 필드에 유효성 관련 어노테이션을 선언하고, 메서드 선언 시 `@Valid` 어노테이션을 매개변수 앞에 붙인다.

또한 검사 결과와 오류 내용을 담는 인터페이스인 `BindingResult`를 함께 매개변수로 주면 검사 결과나 오류 내용을 활용할 수 있다.

| 유효성 관련 어노테이션 예시 | 검사 대상 |
| --- | --- |
| `@NotBlank` | `null`, 빈 문자열, 공백 문자열 |
| `@Pattern` | 영문 대·소문자와 숫자를 포함하는 비밀번호 정책 |
| `@Email` | 이메일 형식 |

`UserRequestDTO` 필드에 제약 조건을 선언하고 Controller의 `@RequestBody` 앞에 `@Valid`를 붙이면 Spring이 요청 객체를 검증한다. `BindingResult`는 검증 대상 매개변수 바로 뒤에 선언하며, `hasErrors()`가 참일 때 필드 이름과 기본 메시지를 Map으로 만들어 `400 Bad Request` 본문으로 반환했다.

```
if (bindingResult.hasErrors()) {
    Map<String, String> errors = new HashMap<>();
    bindingResult.getFieldErrors().forEach(error ->
        errors.put(error.getField(), error.getDefaultMessage()));
    return ResponseEntity.badRequest().body(errors);
}
```

Axios는 400 응답을 성공 콜백이 아니라 `catch`로 전달한다. 서버 응답 본문은 `err.response.data`에서 꺼내 상태로 저장하고, 필드별 메시지가 있을 때 입력창 아래에 렌더링한다.

```
.catch(err => {
    setErrors(err.response?.data ?? {});
});
```

## 어려웠던 점 / 각종 오류

React가 댓글 삭제 요청을 `/comments/delete/${id}`로 보냈지만 Spring은 처음에 `/comments/delete`와 `@RequestParam("id")` 조합으로 선언되어 있어 Controller 메서드가 실행되지 않았다. URL 경로에 ID를 포함하는 현재 요청 방식에 맞춰 Spring을 다음과 같이 수정했다.

```java
@DeleteMapping("/delete/{id}")
public ResponseEntity<?> delete(@PathVariable("id") int id, ...) {
    // 삭제 처리
}
```

`@PathVariable int id`만 작성했을 때 컴파일 결과에서 매개변수 이름을 확인할 수 없어 `Name for argument of type [int] not specified` 오류가 발생했다. URL의 변수 이름을 `@PathVariable("id")`에 명시해 해결했다.

`CommentMapper.update()` 호출 시 `Invalid bound statement` 오류가 발생했다. Mapper 인터페이스에는 `update()`가 있지만 원본 `src/main/resources/mappers/CommentMapper.xml`에 같은 `id`의 SQL이 없었고, 빌드 결과물인 `build` 폴더의 XML을 수정한 것이 원인이었다. 원본 Mapper XML에 `<update id="update">`를 작성해 Java 메서드와 SQL을 연결했다.

회원가입 요청에 빈 문자열을 보냈는데 `bindingResult.hasErrors()`가 `false`였던 원인을 확인하는 과정에서, Gradle의 `runtimeClasspath`에는 `hibernate-validator`가 존재하지만 VS Code에서 실행 중인 서버의 클래스패스에는 포함되지 않은 것을 확인했다. Java Language Server와 Gradle 프로젝트를 새로고침한 뒤 서버를 다시 실행하여 해결했다.

Spring이 검증 실패를 `400 Bad Request`로 반환하면 Axios는 `.then()`이 아니라 `.catch()`를 실행한다. 오류 메시지 Map을 꺼내기 위해 오류가 발생한 상황에서도 HttpStatus를 2XX번으로 설정하려고 했지만, `catch()`에서 `err.response.data`와 같이 데이터를 꺼낼 수 있다는 사실을 발견하여 400번으로 설정했다.
