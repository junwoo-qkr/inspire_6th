오늘 배운 것

EC2와 Docker 실습 환경 준비

EC2에서 aws-docker-ec2라는 이름으로 Ubuntu 24.04 인스턴스를 준비하는 과정을 살펴봤다. 서브넷은 CIDR이 172.31.16.0/20인 항목을 선택하고, 인바운드 규칙을 편집한 뒤 Xshell에서 SSH 연결을 확인하는 순서로 진행한다.

수업에서 다룬 인바운드 규칙은 SSH, HTTP, HTTPS, ICMP IPv4, 사용자 지정 TCP였다. 보안 그룹은 인스턴스로 들어오는 통신의 허용 범위를 정하며, 컨테이너 포트 연결은 Docker 실행 단계에서 따로 설정한다.

Docker의 구성 요소와 이미지·컨테이너 레이어

구성 요소 역할
Client build, pull, run 등의 명령으로 작업을 요청한다.
Docker host 이미지를 관리하고 이를 바탕으로 컨테이너를 생성·실행한다.
Registry 호스트가 내려받거나 업로드할 이미지를 보관한다.

이미지는 여러 읽기 전용 레이어로 구성된다. 컨테이너를 생성하면 그 위에 쓰기 가능한 컨테이너 레이어가 추가되어 파일 생성·수정·삭제가 반영된다. 같은 이미지로 만든 컨테이너도 각자의 변경 내용을 따로 관리한다.

새 이미지를 가져올 때는 이미 가지고 있는 레이어를 재사용하고 필요한 레이어를 추가로 내려받는다. 컨테이너 안에서 수정한 파일은 해당 컨테이너에 반영되며 기반 이미지 자체를 바꾸지는 않는다.

메인 프로세스와 컨테이너 실행·접속 분리

컨테이너는 메인 프로세스가 실행되는 동안 유지된다. docker run은 이미지로 새 컨테이너를 생성하고 실행하며, 이미지가 로컬에 없으면 내려받는다. 기존 컨테이너를 다시 실행할 때는 docker start를 사용한다.

옵션 동작
-d 터미널에서 분리해 백그라운드로 실행한다.
-i 연결되어 있지 않아도 표준 입력을 열린 상태로 유지한다.
-t 가상 터미널을 할당한다.
--name 컨테이너 이름을 지정한다.
--rm 컨테이너가 종료되면 자동으로 삭제한다.

docker run -d --name app1 ubuntu:focal에서는 기본 명령인 Bash가 입력을 기다릴 조건이 없어 종료되고 컨테이너도 함께 종료된다. 백그라운드 실행 옵션 자체가 프로세스를 계속 실행시키는 것은 아니다.

docker run -it --name app2 ubuntu:focal /bin/bash는 셸에 연결된 상태로 실행된다. Ctrl + P 다음에 Ctrl + Q를 누르면 컨테이너를 유지하면서 접속만 분리할 수 있다. 메인 셸에서 exit를 실행하면 해당 셸과 컨테이너가 종료된다.

docker run -d -it --name app3 ubuntu:focal처럼 -d와 -it를 함께 사용하면 Bash를 유지하면서 처음부터 백그라운드로 실행할 수 있다. 웹 서버처럼 계속 실행되는 프로세스가 있는 컨테이너는 그 서버 프로세스로 실행 상태를 유지한다.

MySQL 실행과 컨테이너 내부 명령 실행

MySQL 이미지를 실행할 때 -e로 MYSQL_ROOT_PASSWORD 환경 변수를 전달해 초기 관리자 비밀번호를 설정하는 방법을 다뤘다. docker exec는 실행 중인 컨테이너 안에서 별도의 명령을 실행한다.

mysql -u root와 비밀번호 옵션을 사용하면 MySQL 클라이언트로 데이터베이스에 연결하고, /bin/bash를 실행하면 컨테이너의 셸로 들어간다. 수업에서는 /etc/hosts와 MySQL 데이터 디렉터리인 /var/lib/mysql도 확인 대상으로 다뤘다.

컨테이너와 이미지 관리 명령

컨테이너 상태와 이미지 정보를 확인하고, 실행 중인 컨테이너 안에서 명령을 실행하거나 파일을 관리하는 명령을 정리했다.

명령 용도
docker -v Docker CLI 버전을 확인한다.
docker ps -a / docker images 전체 컨테이너 상태 / 로컬 이미지 목록을 확인한다.
docker inspect 이미지나 컨테이너의 설정과 네트워크 등 상세 정보를 확인한다.
docker exec -it <컨테이너ID> /bin/bash 실행 중인 컨테이너 안에서 Bash 셸을 새로 실행해 명령을 입력한다.
docker rename 기존 컨테이너의 이름을 변경한다.
docker cp 호스트와 컨테이너 사이에 파일을 복사한다. 컨테이너 쪽 경로에는 이름 또는 ID와 콜론을 사용한다.
docker stats 실행 중인 컨테이너의 자원 사용량을 확인한다.
docker system df / docker ps --size Docker 디스크 사용 현황 / 컨테이너별 파일 시스템 크기를 확인한다.
docker rm / docker rmi 컨테이너 / 이미지를 삭제한다.
docker container prune 중지된 컨테이너를 일괄 삭제한다.

docker exec -it <컨테이너ID> /bin/bash에서 -i는 표준 입력을 유지하고 -t는 가상 터미널을 할당한다. 컨테이너 ID 대신 이름도 사용할 수 있다. 이 명령으로 새로 실행한 셸에서 exit를 입력하면 해당 셸이 종료되고, 기존 메인 프로세스가 실행 중이면 컨테이너는 유지된다.

컨테이너를 삭제하면 해당 컨테이너의 쓰기 가능 레이어에만 저장한 변경도 함께 사라진다. 파일을 남겨야 한다면 삭제 전에 docker cp 등으로 필요한 파일을 복사한다.

Nginx 실습에서는 컨테이너에 접속해 cat > /usr/share/nginx/html/index.html로 웹 파일 내용을 입력하고 Ctrl + D로 입력을 마치는 방법을 다뤘다. 이 수정은 실행 중인 컨테이너의 파일에 적용된다.

Dockerfile의 빌드 명령과 실행 설정

Dockerfile은 기반 이미지에 필요한 파일과 프로그램을 더해 이미지를 만드는 명세다. 파일에 적힌 순서대로 빌드가 진행되며, 빌드 단계에서 실행하는 명령과 컨테이너가 시작할 때 사용하는 명령을 구분해야 한다.

명령 실습에서의 역할
FROM ubuntu:18.04를 기반 이미지로 지정한다.
LABEL 이미지에 작성자 등의 메타데이터를 붙인다.
ENV Tomcat 버전과 Java·Tomcat 경로 등의 환경 변수를 설정한다.
RUN 빌드 중 패키지를 설치하거나 웹 파일을 생성한다.
COPY 빌드 컨텍스트의 index.html을 이미지 내부에 포함한다.
EXPOSE 이미지에서 사용하려는 컨테이너 포트를 기록한다.
CMD 컨테이너 시작 시 실행할 기본 명령을 지정한다.

Tomcat 실습 설정은 버전 9.0.100과 Java 17 경로를 지정하고 catalina.sh run으로 실행하도록 작성되어 있다. 웹 이미지 실습은 패키지를 설치한 뒤 웹 파일을 직접 생성하거나 외부 파일에서 복사하고, FOREGROUND 옵션으로 서버 프로세스를 유지하도록 구성했다.

RUN echo는 빌드 중 문자열로 파일을 만들고, COPY는 미리 작성한 파일을 가져온다. 두 방식의 차이는 웹 파일을 이미지에 포함하는 방법이며, 서버의 수신 포트는 별도 설정으로 결정된다.

Apache HTTP Server는 브라우저의 HTTP 요청을 받아 HTML 같은 웹 파일을 제공하는 웹 서버다. 이번 실습에서는 apt-get update로 패키지 목록을 갱신하고 apt-get install -y apache2로 이미지 안에 Apache를 설치했다. /var/www/html/index.html은 이번 구성에서 기본 페이지로 제공할 파일이며, 빌드 중 직접 생성하거나 COPY로 포함한다.

CMD의 /usr/sbin/apache2ctl은 Apache를 실행·제어하는 명령이다. -D FOREGROUND로 서버를 포그라운드에서 실행해 컨테이너의 주된 실행 작업으로 유지한다. Bash만 실행하는 Ubuntu 컨테이너와 달리, 이 구성은 Apache가 HTTP 요청을 기다리며 실행되는 동안 컨테이너가 유지된다.

이번 Apache 기본 구성은 컨테이너 내부 80번 포트를 사용한다. EXPOSE 80으로 사용 예정 포트를 기록하고, 호스트의 8080번에서 접속하려면 컨테이너 생성 시 -p 8080:80으로 연결한다.

빌드 컨텍스트와 이미지 태그·업로드

docker build -t tomcat:v1.0 .에서 -t는 이미지 이름과 태그를 지정하고 마지막의 .은 현재 디렉터리를 빌드 컨텍스트로 지정한다. COPY ./index.html의 원본은 이 컨텍스트를 기준으로 찾으므로, Dockerfile이 있는 위치만 보고 판단하면 안 된다.

수업에서는 docker images로 이미지를 확인하고, docker tag tomcat:v1.0 junwooqkr5302/tomcat:v1.0으로 저장소 이름을 포함한 태그를 붙인 뒤 docker push junwooqkr5302/tomcat:v1.0으로 업로드하는 흐름을 다뤘다. 태그 추가는 이미지의 프로그램이나 파일을 새로 만드는 작업과 구분된다.

호스트 포트와 컨테이너 포트, 재활용한 이미지 구분

-p 8080:80은 Docker 호스트의 8080번 포트로 들어온 요청을 컨테이너의 80번 포트로 전달한다. EXPOSE 80은 포트에 대한 정보이며, 호스트 포트를 연결하거나 서버의 수신 포트를 변경하지 않는다.

브라우저에서 사용하는 localhost는 그 브라우저가 실행되는 컴퓨터를 가리킨다. 이번 화면은 Ubuntu 가상 머신 안의 Firefox였으므로, 그 Ubuntu에서 공개한 호스트 포트에 접속하는 상황이었다.

컨테이너 이름, 이미지 태그, 이미지 안에서 실행되는 프로그램은 구분해서 확인해야 한다. tomcat2 이미지는 httpweb 이미지를 재활용한 것이 확인되었으므로 실제 웹 서버 구성과 수신 포트를 기준으로 연결한다. Dockerfile을 수정하거나 이미지 태그를 바꿔도 이미 생성한 컨테이너의 실행 설정이 자동으로 바뀌지는 않는다.

오늘의 코드 1 - Tomcat 환경 변수와 실행 명령

dockerfile (Tomcat 실습)

ENV TOMCAT_VERSION 9.0.100
ENV CATALINA_HOME /usr/local/tomcat
ENV JAVA_HOME /usr/lib/jvm/java-17-openjdk-amd64
ENV PATH $CATALINA_HOME/bin:$PATH

 

TOMCAT_VERSION은 설치할 버전을, CATALINA_HOME과 JAVA_HOME은 프로그램 경로를 지정한다. PATH에 Tomcat의 실행 파일 디렉터리를 추가한 설정이며, 실제로 작성된 Java 경로는 17을 가리킨다.

dockerfile (Tomcat 실습)

CMD ["/usr/local/tomcat/bin/catalina.sh", "run"]

 

컨테이너가 시작할 때 Tomcat의 catalina.sh를 run으로 실행하도록 지정한다. 서버 프로세스가 계속 실행되는 동안 컨테이너도 유지되는 실행 구조를 확인할 수 있다.

오늘의 코드 2 - RUN으로 웹 페이지 파일 생성

dockerfile (웹 파일 직접 생성 실습)

RUN apt-get update \
    && apt-get install -y apache2
RUN echo "TEST WEB" > /var/www/html/index.html

 

빌드 중 패키지 목록을 갱신하고 웹 서버를 설치한 뒤, echo의 출력을 웹 루트의 index.html에 기록한다. 이 방식은 외부 HTML 파일을 복사하지 않고 이미지 안에 TEST WEB이라는 내용을 만드는 실습이다.

오늘의 코드 3 - COPY로 웹 파일 포함 및 서버 실행

dockerfile (외부 웹 파일 복사 실습)

COPY ./index.html /var/www/html/index.html
EXPOSE 80
CMD ["/usr/sbin/apache2ctl","-D","FOREGROUND"]

 

빌드 컨텍스트의 index.html을 이미지의 웹 루트로 복사하고 80번 포트 정보를 기록한다. 컨테이너 시작 시 FOREGROUND로 서버를 실행하며, 호스트에서 접근할 포트는 실행 단계의 -p로 연결해야 한다.

어려웠던 점 / 각종 오류

COPY ./index.html /var/www/html/index.html에서 failed to calculate checksum과 "/index.html": not found가 발생했다. 이는 빌드 컨텍스트에서 복사할 파일을 찾지 못한 오류다. 빌드 명령 마지막에 지정한 디렉터리에 index.html이 있는지, 파일명과 대소문자가 맞는지, .dockerignore에서 제외되는지 확인해야 하며 실제 파일 위치에 맞춰 컨텍스트나 복사 원본 경로를 정해야 한다.

tomcat을 실행하면 접속되던 localhost:8080이 tomcat2 실행 시에는 접속되지 않았다. 확인 결과 tomcat2 이미지는 httpweb 이미지를 재활용한 것이었고, 제공한 웹 서버 구성은 컨테이너 내부 80번을 사용하는데 화면에는 8080->8080/tcp로 연결되어 있었다. 이 구성에서는 호스트 8080번이 컨테이너 80번을 가리키도록 -p 8080:80으로 컨테이너를 생성해야 한다. 포트를 변경한 뒤의 접속 성공 결과는 이번 기록에서 확인되지 않았다.

로그의 AH00558은 서버의 정규 도메인 이름을 정하지 못했다는 경고였다. 이어 실행한 수신 포트 확인 명령은 컨테이너에 ss와 netstat이 없어 각각 not found로 끝났으므로, 해당 명령으로 내부 수신 포트를 확인하지는 못했다.
