마스터 컴포넌트(controller plane) 구성 요소
- etcd: key-value 타입의 노드의 정보를 저장하는 저장소
- kube-apiserver: 요청의 유효성 등을 검색
- kube-scheduler: 포드를 실행할 노드 선택
- kube-controller-manager: 포드의 개수 보장

워커 노드 컴포넌트(data plane) 구성 요소
- kubelet: 모든 노드에서 실행되는 k8s -> daemon 형태로 동작함
- kubu-proxy: k8s의 network 동작을 관리, iptable rule을 구성
- 컨테이너 런타임: 컨테이너를 실행하는 엔진(docker, containerd, CRI-O 등)

k8s 동작 순서
1. kubectl로 create pod api에 호출
2. api server가 요청의 유효성 검사 후 etcd에 저장
3. etcd가 결과 반환
4. api server가 scheduler 호출
5. scheduler가 pod를 실행할 위치를 결정하고 반환
6. api server가 pod 실행 결과를 etcd에 기록
7. etcd가 결과 반환
8. api server가 해당 노드의 kubelet 호출
9. kubelet은 docker api로 컨테이너를 생성
10. kubelet은 api를 호출해서 pod 상태를 업데이트
11. api server가 etcd의 상태 유지

replication controller: 실행중인 pod의 갯수를 설정대로 유지
- spec.selector.app과 spec.template.metadata.labels.app이 같아야 함

kubectl edit <자원 타입> <자원 이름>: 실행중인 자원의 설정을 수정하고 바로 반영

yaml 파일을 수정(image 버전 등)하고 apply하면 실행중인 pod에 변경사항이 적용되지 않음
delete 후 재실행되는 pod는 변경사항이 적용됨

label이 webui인 ngnix(replicas=3) pod를 3개 실행중일때, label이 똑같이 webui인 redis를 실행
-> nginx와 redis의 label이 같기 때문에 같은 pod라고 생각하고 rc가 바로 redis를 꺼버림

replicaset
- replication controller와 동일한 역할

replication controller와 replicaset의 차이
replication controller:
- apiVersion: v1
- kind: ReplicationController
- selector.app: webui
replicaset:
- apiVersion: apps/v1
- kind: ReplicaSet
- selector.matchLabels.app: webui

replicaset도 이미지 버전등에 대해서는 실행 중 수정이 안됨 -> replicaset, replication controller 둘 다 pod의 갯수만 유지해줌

rs 삭제 시 --cascade=false 옵션이 있으면 pod는 rs 삭제 후에도 남아있음

rs 실행 시 label이 같은 pod가 이미 실행중이면 같은 rs라고 생각함

deployment
- pod의 버전관리 담당
- deployment 하위에 replicaset
- yaml 파일에 kind: Deployment로 정의되어 있음
- rolling update(변경 사항이 있으면 pod 인스턴스를 점진적으로 업데이트) 지원

실행 중인 deployment의 yaml에서 이미지 버전을 변경하고 apply -> 바뀐 버전으로 pod가 재실행

한 deployment에 여러 rs: 버전을 바꿀때마다 새 rs가 생김
이전에 사용하던 rs는 rollback 등을 위해 실행하지 않고 남겨놓음
deployment의 rollingupdate.maxSurge, maxUnavailable에 대한 설명?

kubectl rollout history deployment <deployment이름>

daemonset
- 노드 당 pod가 하나씩 실행되도록 보장
- 로그 수집기, 모니터링등에 적용
yaml 파일에 kind:DaemonSet으로 정의되어 있음(replicas 설정은 없음)

statefulset
- pod의 상태(이름) 유지
- 생성되는 pod의 이름이 일정(xxx-0, 1, 2, ...)
- 삭제하면 다시 생성되는 pod는 원본과 동일
- scale in하면 제일 마지막에 생성된 것부터 삭제

service
- 동일한 서비스(동일 라벨) pod 그룹에 단일 진입점을 제공
- kind: Service로 정의됨
- 종류:
  - ClusterIP
    - selector의 label이 동일한 pod를 묶어 단일 진입점 생성
    - 클러스터 내부에서만 사용 가능
  - NodePort
    - 모든 워커 노드를 대상으로 외부에서 접속 가능한 포트 예약
    - ClusterIP와 NodePort를 예약
  - LoadBalancer
    - public cloud(aws, gcp 등)에서 사용 가능
    - nodeport를 예약 후 해당 nodeport로 외부 접근 허용
  - ExternalName
    - 클러스터 안에서 외부에 접속 시 사용할 도메인을 yaml 파일에 등록
  - headless service
    - clusterIP가 없는 서비스 -> 단일 진입점이 필요 없을 때 사용
    - 일반적으로 DB에 statefulset과 함께 사용
  - kube-proxy
    - iptable rule을 기반으로 서비스를 pod와 연결
