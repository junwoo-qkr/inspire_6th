### 8월 12일 강의: 자바 백엔드 아키텍처 및 핵심 문법 심화 정리

본 보고서는 8월 12일 진행된 'AI 서비스 개발을 위한 백엔드' 강의의 핵심을 집대성한 결과물입니다. 단순한 문법 나열을 넘어, 실제 현업에서 요구되는 아키텍처 설계 관점과 JVM 메모리 메커니즘을 시니어 개발자의 시각으로 분석하여 정리하였습니다.

#### 1\. 객체지향 프로그래밍(OOP)의 근간: 클래스와 인스턴스

자바 프로그래밍의 본질은 실세계의 오프라인 프로세스를 시스템화하는 '추상화(Abstraction)'에 있습니다. 단순히 코드를 작성하는 것이 아니라, 객체지향적 사고방식(Mindset)을 갖추는 것이 무엇보다 중요합니다.

##### 객체 모델링과 마인드셋의 전환

과거 삼성생명의 차세대 시스템 구축 당시, C언어에 익숙한 베테랑 개발자들이 자바 환경에서 C 스타일의 절차지향 코드를 클래스에 그대로 옮겨 적는 실수를 범하곤 했습니다. 이것은 진정한 OOP가 아닙니다.

* **추상화:**  실세계 오브젝트의 공통 특징을 추출하여 \*\*클래스(Template)\*\*라는 설계도를 만드는 과정입니다.  
* **인스턴스(Instance):**  설계도를 바탕으로 JVM 메모리에 실체화된 결과물입니다. 클래스 멤버(변수, 메서드)는 기본적으로 인스턴스의 소유이며, 외부 클래스는 인스턴스의 주소값을 참조하는  **참조 변수** 를 통해 이 자원에 접근하는 '해저(Has-a)' 관계를 형성합니다.

##### 객체 생성 메커니즘: 빌더 패턴의 가치

* **전통적 방식 (**  **new**  **연산자):**  new 생성자()를 통해 메모리에 할당합니다.  
* **롬복(Lombok)**  **@Builder**  **패턴:**  어노테이션을 통해 컴파일 시점에 specialized constructors, getters, setters를 자동 주입합니다.  
* **So What?**  현업에서 빌더 패턴을 선호하는 이유는 복잡한 파라미터 제어가 용이하고 가독성이 높으며, 불변 객체 생성 및 유지보수성을 극대화하기 때문입니다.

##### 생성자(Constructor)의 역할

* **기본 생성자:**  명시하지 않아도 컴파일러가 자동 생성하며, 강의에서는 이를 \*\*"마음이 착한 사람에게만 보이는 생성자"\*\*로 비유했습니다. 하지만 프레임워크와의 호환성을 위해 명시적 정의를 권장합니다.  
* **생성자 오버로딩:**  매개변수의 개수와 타입을 달리하여 다양한 초기화 옵션(예: 베스킨라빈스 31의 다양한 선택지)을 제공함으로써 객체 생성의 전략적 유연성을 확보합니다.

#### 2\. 메서드 아키텍처와 데이터 전송 모델(DTO)

메서드는 애플리케이션의 비즈니스 로직을 조각내고 레이어 간 협업을 가능케 하는 핵심 단위입니다.

##### 메서드 시그니처와 기술적 정밀도

* **용어의 구분:**  메서드 정의 시 선언하는 변수는 \*\*매개변수(Parameter/Arguments)\*\*이며, 실제 호출 시 전달되는 값은 \*\*인자(Arguments/Parameters)\*\*입니다.  
* **레이어드 아키텍처:**  백엔드는 Controller \- Service \- Persistence 레이어로 나뉘며, 메서드의 반환 타입과 매개변수를 통해 데이터가 흐릅니다. 이때 반환 타입과 매개변수가 모두 존재하는 형태가 가장 이상적인 비즈니스 로직 단위입니다.

##### DTO(Data Transfer Object) 설계 원칙

현업에서는 데이터를 개별 파라미터로 받는 대신  **DTO 객체** 로 바인딩하여 전달하는 방식을 선호합니다.

* **보안과 가공:**  멤버 변수를 private으로 숨기는 \*\*정보 은닉(Information Hiding)\*\*을 실현하고, Getter/Setter를 통해 필요한 데이터만 노출합니다.  
* **유지보수성:**  파라미터가 늘어나도 메서드 시그니처를 수정할 필요 없이 DTO 클래스만 수정하면 되므로 관리가 용이합니다.

##### 실습 블로그 등록 로직의 DTO 바인딩 예시

// 개별 파라미터 방식보다 DTO 객체 바인딩 방식이 업계 표준입니다.  
public BlogResponseDTO register(BlogRequestDTO request) {  
    // 비즈니스 로직: 이메일 비교를 통한 조건 처리  
    // jsl9413@naver.com(성공) vs gmail.com(실패) 등의 분기 처리  
    if ("jsl9413@naver.com".equals(request.getEmail())) {  
        return new BlogResponseDTO(201, "성공적으로 등록되었습니다.");   
    }  
    return new BlogResponseDTO(400, "인증되지 않은 사용자입니다.");   
}

#### 3\. JVM 메모리 구조와 Static의 동작 원리

효율적인 백엔드 개발을 위해서는 JVM이 데이터를 관리하는 물리적 메커니즘을 이해해야 합니다.

##### JVM 메모리 섹터 분석

1. **Static Area (Method Area):**  클래스 정보와 static 멤버가 로딩됩니다.  **프로그램 시작 시점에 가장 먼저 확보** 됩니다.  
2. **Heap Area:**  new로 생성된 모든 인스턴스가 상주합니다. \*\*가비지 컬렉터(GC)\*\*의 주 대상이며, 보통 힙이  **80% 정도 가득 찼을 때**  GC가 동작하여 참조가 끊긴 객체를 정리합니다.  
3. **Stack Area:**  메서드 실행 시 \*\*스택 프레임(Stack Frame)\*\*이 생성됩니다.  **LIFO(Last In First Out)**  구조로 동작하여 메서드 종료 시 즉시 소멸합니다.  
4. **Literal Pool:**  문자열 상수가 키-값(Key-Value) 형태로 관리되는 특수 공간입니다.

##### Static vs Instance: "So What?"

* **Static 멤버:**  프로그램 로딩 시점에 메모리에 올라갑니다. 반면 인스턴스는 런타임 중에 new를 호출해야 생성됩니다.  
* **구조적 제약:**  따라서  **이미 메모리에 존재하는 Static 영역에서 아직 생성되지 않았을 수도 있는 인스턴스 영역으로의 접근은 원천적으로 불가능** 합니다.  
* **Main 메서드가 Static인 이유:**  JVM이 인스턴스 생성 없이도 프로그램의 엔트리 포인트를 즉시 호출할 수 있어야 하기 때문입니다.

#### 4\. 제어문과 포매팅 출력의 활용

##### 반복문 3종 및 중첩 루프 제어

* for: 반복 횟수가 명확할 때 사용.  
* while: 조건에 따른 반복이나 무한 루프에 적합.  
* do-while: 조건 체크 전  **최소 1회 실행** 을 보장해야 할 때 사용.

##### 중첩 루프 레이블(Label) 활용

이중 for문과 같은 행(Row)/열(Column) 매트릭스 구조에서 특정 조건 시 전체 루프를 탈출하려면 레이블(outer:)을 사용합니다.  
outer: for(int dan=2; dan\<=9; dan++) {  
    for(int i=1; i\<=9; i++) {  
        if(dan \== 5\) break outer; // 5단 진입 시 전체 구구단 루프 종료  
        System.out.printf("%d \* %d \= %d\\t", dan, i, dan\*i); // \\t로 간격 조정  
    }  
    System.out.println(); // \\n 또는 println으로 개행 처리  
}

#### 5\. 문자열(String)의 특성과 고급 핸들링

##### 불변성(Immutability)과 리터럴 풀

자바의 String은 불변 객체입니다. 리터럴로 생성된 문자열은 리터럴 풀에서 관리되어 메모리를 절약하지만, new String()은 매번 힙에 새로운 객체를 생성합니다. 따라서 주소값을 비교하는 \== 대신 반드시 실제 값을 비교하는 \*\*.equals()\*\*를 사용해야 합니다.

##### 성능 최적화: StringBuffer

* **문제점:**  String에 \+ 연산을 반복하면 매번 새로운 객체가 생성되어 메모리 낭비가 심각해집니다.  
* **해결책:**  가변(Mutable) 객체인 **StringBuffer**를 사용하십시오.  
* **백엔드 표준:**  웹 서버 환경은 멀티쓰레드로 동작합니다.  **Thread-Safe** 를 보장하는 StringBuffer는 동시성 이슈를 방지하므로 백엔드 개발의 필수 도구입니다. (length(), charAt(), substring() 등의 API 활용 능력이 중요합니다.)

##### 중요 용어 사전(Glossary)

* **JVM:**  자바 가상 머신. OS 독립적인 실행 환경 제공.  
* **GC (Garbage Collection):**  참조되지 않는 메모리 자동 해제 메커니즘.  
* **Stack Frame:**  메서드 호출 시 할당되는 독립적인 메모리 블록.  
* **Literal Pool:**  문자열 상수의 중복 방지를 위한 메모리 영역.  
* **Thread-Safe:**  여러 쓰레드가 동시에 접근해도 데이터 안전성이 보장되는 상태.
